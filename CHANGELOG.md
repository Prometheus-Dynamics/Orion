## [Unreleased]

### Added

- `TypedConfigValue::F64(f64)` for values without a natural fixed point (camera intrinsics, distortion, mount pose), in workload configs, action arguments and outputs, and status entries. Equality compares the bits (`NaN` equals itself, `0.0` differs from `-0.0`) so `Eq` still holds; `as_f64()`; JSON as `{"F64": 1.5}` (config decoding maps non-finite values to `null`); Prometheus exports finite `F64` extra host metrics. `orionctl action run --arg KEY=f64:VALUE` (floats are never inferred, so `version=2.0` stays a string); `orionctl` prints them. It is the last variant, so the rkyv and postcard encodings of the others are unchanged; `orion-link`'s borrowed `wire::Value` gains `F64` too (postcard: tag 5, eight little-endian bytes; `LINK_PROTOCOL_VERSION` stays 1, and the wire property test now covers it). Part of the unreleased control protocol 4: the archived size is unchanged, so the layout fingerprint stays, and the canonical encoding fixture now pins an `F64` argument; peers, clients and `orionctl` must still come from the same commit. `scripts/mcu-size.sh` now honours `CARGO_TARGET_DIR`.
- Observed-state watches: `StateWatch::include_observed` (`StateWatch::desired(rev).with_observed()`, `ControlPlaneEventStream::subscribe_state_and_observed` / `subscribe_state_watch`) also sends a `StateSnapshot` whenever the observed state changes (workload phases, resource health and availability, leases, node records), even when the observed revision does not move, starting with a bootstrap snapshot. Before, `WatchState` fired only on desired-revision changes, so subscribers silently missed observed changes. Part of the unreleased control protocol 4 (layout fingerprint updated).
- Device-agent contract, revised with Atlas: `update` is asynchronous. It reports `Succeeded` with `phase = "staging"` once the download and stage have started (a large image over a slow link can exceed the 10-minute action cap), and the outcome comes only from the `update.*` keys (`staging` -> `staged` -> `rebooting` / `trying` -> `confirmed` | `rolled-back` | `cancelled` | `error`) and the host facts' `boot_id` / `image_version`. New well-known node actions `update.cancel` (abort a download or stage, or forget a staged update; `phase = "cancelled"` or `"idle"`) and `update.rollback` (boot the previous confirmed slot; `phase = "rebooting"`), claimed by the same agent. `update_action` gains `PHASE_STAGING`, `PHASE_CANCELLED`, `PHASE_IDLE` and the `STATE_*` values (now including `cancelled`, `rebooting` and `error`); `OUTPUT_VERSION_STAGED` is gone. The example agent stages in the background and handles both new actions; the contract tests cover cancel, retry, rollback and claim-scoped keys for the new names.
- Operator access on appliances: `ORION_NODE_LOCAL_AUTH=same-user-or-group-or-root` also admits root (so `orionctl` works from a root shell), and `ORION_NODE_LOCAL_AUTH_ALLOW` admits further callers in every mode but `disabled` (`root`, `uid:<n>`, `gid:<n>`, `user:<name>`, `group:<name>`; names resolved at startup, unknown names fail startup). The default stays `same-user`. `orion_node::LocalAccessAllowList`, `NodeAppBuilder::with_local_access_allow`, `PeerSecurityMiddleware::with_local_allow`. See "Local IPC access" in `docs/node-env.md`.
- `packaging/gaia/orionctl.toml`: an optional Gaia layer, imported after `orion-node.toml`, that builds the IPC-only `orionctl` and installs it as `/usr/bin/orionctl`, so images stop building it themselves.
- Device agents (`docs/device-agent.md`): the contract for an out-of-process agent that claims the node actions `update`, `reboot` and `locate` (action names, `update` arguments `image_url`, `sha256`, `size`, result semantics, progress keys, the `update.*` status keys it republishes after every boot, disconnect behaviour, and the path to milestone U3). A client holding a node action claim may now publish `<claimed name>.*` keys for `node/<local node>` in addition to `action.*` keys. `orion_control_plane::update_action` names the arguments, outputs and keys. `orion-client`: `ActionReporter` (from `ActionRequestWatch::reporter()`, reports and publishes while the watch waits), `ActionRequestWatch::{node_id, reconnects, publish_status, node_status_entry}`. Example agent with a fake updater: `crates/client/examples/device_agent/`, tested against a real node in `crates/node/tests/device_agent.rs`.
- CPU utilisation and temperatures in `HostMetricsSnapshot` (`cpu_busy_milli`, `cpu_core_busy_milli`, `cpu_window_ms`, `temperatures`), sampled when the observability snapshot is taken with one shared `/proc/stat` baseline (minimum window 250 ms), and in `HostMetricsSample` (`cpu_busy_milli`, `cpu_core_busy_milli`, since the previous host-facts sample) with the status keys `host.cpu_busy_milli` and `host.cpu<N>_busy_milli`. Prometheus: `orion_host_cpu_busy_ratio`, `orion_host_cpu_core_busy_ratio`. `orion_node::host_facts::{parse_proc_stat, CpuUsageTracker, thermal_zone_temperatures}`.
- `ControlPlaneEventStream::subscribe_status` and `ControlPlaneEventStream::node_id`, so control-plane clients follow host metrics and other status keys on the same stream as state and action changes instead of polling (`docs/host-facts.md`, "Following host metrics without polling").
- `orion_transport_ipc::unix_peer_identity` and `UnixPeerIdentity::{groups, is_member_of}`: supplementary groups of local IPC callers (`SO_PEERGROUPS`, Linux 4.13 and newer).

### Changed

- CI does less work for the same guarantees. The Linux jobs run `scripts/ci-jobs.sh <job>` (also the local entry point, with per-step wall and CPU times); the orion-node clippy matrix keeps one build per distinct `cfg` combination (11 instead of 18), the orion-node test builds drop runs another one already covers (3 instead of 7 plus a duplicate filtered run), lint/build steps that repeated an all-features or test build are gone, orion-link is linted on three cores that differ in atomics instead of five (release builds stay on all five), the MCU template is built once by `mcu-size.sh`, the two allocator jobs are one job on the appliance feature set, and the appliance job verifies the unit against the cross-built binary. `docs/development.md` ("CI jobs") lists what each job covers. Debug builds use line tables only for workspace crates and no debug info for dependencies (`[profile.dev]`; `CARGO_PROFILE_DEV_DEBUG=full` to debug).
- The Gaia layer `packaging/gaia/orion-node.toml` requires `gaia_version >= 2.0.0` (was `>= 2.1.0`): Gaia's development line is versioned 2.0.0 again, so the old bound failed every importing build.
- `ORION_NODE_LOCAL_AUTH=same-user-or-group` now also admits callers whose **supplementary** groups include the node's group (before: primary group only), so `SupplementaryGroups=orion` works.
- The well-known `update` action takes `image_url` instead of `bundle_url` (Atlas's argument name); no handler in Orion used it.
- `HostMetricsSnapshot`, `HostMetricsSample` and `UnixPeerIdentity` gained fields, which changes the archived control-protocol layout. `CONTROL_PROTOCOL_VERSION` stays 4 (unreleased); the layout fingerprint is updated, so `orionctl`, client libraries and `orion-node` must come from the same commit.
- Toolchain pin (rust-toolchain.toml, CI, the Gaia aarch64 cross image) moved to Rust 1.99.0; MSRV stays 1.94.
- Dependencies upgraded to their newest releases. Major jumps: `ed25519-dalek` 3, `hmac` 0.13, `sha2` 0.11, `toml` 1, `syn` 3, and `embedded-io` / `embedded-io-async` 0.7 (the `orion-link` adapters and the MCU template). Wire formats and signatures are unchanged.
- `rand_core::OsRng` is gone upstream: `orion-node` and `orion-client` draw keys and nonces from `getrandom::SysRng` instead of depending on `rand_core`.
- `orion_auth::crypto::{SigningKey, VerifyingKey}` are now the `ed25519-dalek` 3 types, and `orion-link`'s `embedded-io` / `embedded-io-async` features take the 0.7 traits (async `Write::flush` has no default any more).

### Fixed

- `selector_placement_converges_to_the_same_node_everywhere` failed on loaded machines: with a 300 ms liveness timeout a slow round made a node look gone, so observers computed another node. Tests about where placement lands now use a liveness and grace that cannot lapse during the test, so the outcome depends only on the converged state.
- Reconnecting a local stream client under the same local address (a fixed name or a restarted service) failed with "no control message available" for the old session's lifetime: the node resumes the session and flushes the events queued for the address while it was away (by design, within `ORION_NODE_LOCAL_SESSION_TTL_MS`), and `orion-client` took the first of them for the response to its next subscription. `orion-client` stream sessions now keep events that arrive while a request waits for its response and return them from `next_events` first (this also covers a subscription's bootstrap racing the next subscription on the same stream). On the node, the old connection's teardown no longer detaches a newer connection under the same address (or releases its action claims).

## [1.0.0] - 2026-04-19

- Standardized the workspace layout, docs, CI, linting, and helper scripts.
- Added repo-level testing guidance for default, Docker, perf, and soak validation surfaces.
- Added `scripts/check-file-sizes.sh`, `scripts/ci.sh`, and `scripts/repo-clean.sh`.

### Added

- `orion-link` crate: `no_std`, allocation-free, panic-free framing for the MCU link protocol (`docs/link-protocol.md`). CRC-32C message frames (`[version][kind][seq u16 LE][payload][crc32c LE]`, `LINK_PROTOCOL_VERSION = 1`), COBS byte-stream encoding with a byte-at-a-time `StreamEncoder` and a resynchronizing `StreamDecoder<N>` with drop counters, and classic CAN / CAN FD segmentation (`Segmenter`, `Reassembler<N>`, `CanLinkIds`) with unpadded, valid CAN FD segment lengths. Optional `embedded-io`, `embedded-io-async`, and `embedded-can` adapters, and a `crc-table` feature. CI builds it for `thumbv7em-none-eabihf`, `thumbv8m.main-none-eabihf`, and `riscv32imac-unknown-none-elf`.
- `orion-link` link messages and sessions. The `alloc` feature (still `no_std`) adds postcard-encoded messages (`Hello`, `Welcome`, `Reject`, `ProviderState`, `Ack`, `Leases`, `Ping`/`Pong`; stable kind numbers with `ExecutorState`, `Workloads`, and `Status` reserved; unknown kinds ignored) and the sans-IO `DeviceSession<T, RX, TX>` over COBS streams or CAN / CAN FD with fixed const-generic buffers: `Hello` backoff, reject backoff, negotiated frame size, newest-snapshot provider publishing retransmitted until acked and re-sent on every reconnect, heartbeat pings, host-loss detection, duplicate suppression, and lease events. The `std` feature adds the sans-IO `HostSession` and the multi-device CAN `HostBus` for the upcoming node gateway (device allowlist, acks, lease piggybacking on every `Pong`, device-loss detection). A wire fingerprint fixture (`crates/link/tests/link_encoding.rs`) forces a `LINK_PROTOCOL_VERSION` bump on wire changes. `docs/link-protocol.md` now pins kind numbers, reject codes, the session lifecycle, and the retransmission and duplicate rules.
- `orion-link` minimal device path (feature `device`): no allocator, no heap, no dependencies, and no `core::fmt` on the device. `orion_link::wire` is a hand-written postcard-compatible codec (`Writer`, `Reader`, `Encode`) with borrowed, `const`-constructible views (`HelloView`, `ProviderView`, `ResourceView` with capabilities, ownership, health, availability, lease state, and resource state, `StatusView`) that encode to exactly the postcard bytes of the corresponding records, and zero-copy decoding of `Welcome`, `Reject`, `Ack`, `Ping`/`Pong`, and `Leases` (an iterator of `LeaseView`s over a validated payload). `DeviceSession` now runs on this path with fixed buffers only (`2 * RX + 2 * TX` plus about 350 bytes; the lease buffer also carries the outgoing `Hello`; a wrapping 32-bit internal clock; events are small `Copy` values: `LeasesChanged` with `leases()`, `Connected { session_id }` with `node_id()`; `transmit_segment` for CAN without a `Segment` copy; `DeviceConfig<N>` is generic over the name type) and needs no atomics, so it builds for `thumbv6m-none-eabi` and `riscv32imc-unknown-none-elf`. With `alloc` the same session also accepts `ProviderRecord` / `ResourceRecord` / `StatusEntry` and returns `lease_records()`. `LINK_PROTOCOL_VERSION` stays 1 and the wire is unchanged: the fixture, property tests against postcard, and end-to-end tests against the unchanged `HostSession` / `HostBus` over streams and CAN check it. Framing no longer links panic paths (`encode_in_place`, the reassembler). The MCU template uses the minimal path by default (no global allocator; `alloc` / `global-heap` keep a full-record variant): its UART build shrinks from 26.9 KB flash + 1.2 KB RAM + 8 KiB heap to 7.9 KB flash + 0.9 KB RAM on Cortex-M4F, and is 8.0 KB / 0.9 KB on Cortex-M0+. `scripts/mcu-size.sh` reports thumbv6m, thumbv7em, riscv32imc, and riscv32imac (UART, CAN, and the alloc variant, with a per-component breakdown), and the CI `link-no-std` job enforces a size budget.
- `crates/link/examples/sim_device.rs` (simulated device and host over an in-memory serial line) and `examples/mcu-template`, a standalone chip-agnostic `no_std` firmware template (`embedded-io` UART and `embedded-can` ports, a replaceable first-fit heap, C entry points) built by CI for `thumbv7em-none-eabihf` and `riscv32imac-unknown-none-elf`. `scripts/mcu-size.sh` reports its linked footprint (about 26 KB flash and 1.2 KB RAM plus heap on Cortex-M4F).
- `link-gateway` cargo feature for `orion-node` (opt-in, Linux, also in the IPC-only build): serves the serial and SocketCAN links listed in `ORION_NODE_LINKS` (`serial:<path>?baud=...`, `can:<if>?device_base=...&host_base=...&addresses=A-B&fd=...&extended=...`, plus `allow`, `heartbeat_ms`, `missed_heartbeats`, `max_frame`) with termios and `PF_CAN` raw sockets over `libc` and tokio `AsyncFd`, and bridges every device into the node through the local IPC provider path: gateway-owned `node_id`; provider and resource ownership checks against IPC clients, other devices, and other nodes; lease sets refreshed on every desired-state commit; resources marked unavailable on device loss and restored on reconnect; devices marked lost on shutdown. `NodeApp::link_status()` reports per-link counters; the control protocol is unchanged. `ORION_NODE_LINKS` fails startup in builds without the feature. `crates/node/examples/link_device_sim.rs` simulates a device on a pseudo-terminal for trying it without hardware.
- `ORION_NODE_HTTP_ADDR=off` runs `orion-node` without the HTTP control listener for IPC-only appliances.
- `transport-http` cargo feature for `orion-node`, enabled by default. `cargo build -p orion-node --no-default-features` builds an IPC-only node without axum, hyper, reqwest, or rustls. In that build, `ORION_NODE_PEERS`, HTTP TLS settings, `ORION_NODE_HTTP_PROBE_ADDR`, and an `ORION_NODE_HTTP_ADDR` socket address fail startup with an error that names the missing feature.
- `orion-transport-http` gains a default `transport` feature. Without it, the crate exposes only the protocol layer: payloads, routes, codec, errors, and handler traits. `orion-transport-common` gates its rustls helpers behind a default `tls` feature.
- `orion-transport-http` splits `transport` into `client` (`HttpClient`, `HttpClientTlsConfig`; reqwest over rustls, without the axum/hyper server stack) and `server` (`HttpServer` and server TLS / client-auth configuration; axum, hyper, tokio-rustls). `transport` stays the default and enables both, so existing users are unchanged.
- `orionctl` cargo features `http` (`--http` remote targets, using only the HTTP client), `yaml`, and `toml` (output formats and workload spec files), all on by default. `cargo build -p orionctl --no-default-features` gives an IPC-only CLI with JSON and summary output: 1.80 MiB stripped and 57 crates (34 runtime), against 4.38 MiB and 139 crates (111 runtime) for the default build and 2.65 MiB with `--features yaml,toml` (x86_64, release profile). Requesting a transport or format the build lacks fails with an error that names the feature.
- `ORION_NODE_RUNTIME_WORKER_THREADS` and `ORION_NODE_RUNTIME_MAX_BLOCKING_THREADS` size the node's Tokio runtime.
- Single-node appliance profile guidance in `docs/node-env.md`, and an `appliance_memory_soak` suite that checks memory slope and caps under provider/executor/mutation load.
- Opt-in `alloc-jemalloc` and `alloc-mimalloc` features that set the `orion-node` binary's global allocator (jemalloc wins if both are on), with allocator soak measurements in `docs/node-env.md`. The soak gains `ORION_SOAK_NODE_WORKER_THREADS` and `ORION_SOAK_NODE_BIN`.
- `ResourceEndpoint::Custom` accepts any valid URI scheme (for example `styx-frame-lease+unix://`), with `CustomEndpointScheme` for typed downstream endpoints and `Display`/`FromStr` round-tripping.
- `UnixFdLatestServer` / `UnixFdLatestClient` in `orion-transport-ipc`: a bounded latest-value channel that hands out dup'd fds (for example dmabuf frame leases) with sequence waits, max age, and max clients.
- `resource_usage` section in node observability snapshots (process RSS/PSS, state record counts, mutation history vs caps, local stream backlog, worker queue depth, registry sizes), `orionctl get memory`, and matching Prometheus families.
- `no_std` + `alloc` support for `orion-core`, `orion-data-plane`, `orion-control-plane`, `orion-auth`, `orion-runtime`, and `orion-cluster` (and the `orion` facade's model features) for microcontroller targets. Each crate has a default `std` feature; only the Prometheus metrics export and the shared-memory/unix endpoint filesystem helpers require it. Workspace dependencies on these crates and on serde, serde_json, thiserror, rkyv, and ed25519-dalek now use `default-features = false`, with std crates enabling `std` explicitly. rkyv is raised to 0.8.16 (first release that compiles `pointer_width_64` on 32-bit targets); the archived layout and `CONTROL_PROTOCOL_VERSION` are unchanged, which a new canonical-encoding fixture test checks in both std and no_std builds. CI gains a `no-std` job running `scripts/check-no-std.sh`.
- Node clock facts: every node publishes `NodeClockFacts` (clock source `ClockSourceKind`, synchronized, offset, max/estimated error, stratum, PTP grandmaster, declared timebase, checked-at time) in its observed `NodeRecord::clock`. `orion-node` reads the kernel discipline state with read-only `adjtimex` every `ORION_NODE_CLOCK_REFRESH_MS` (default 10000) and republishes only on meaningful change (sync/source/timebase change, offset moved by more than 1 ms, an error bound halved or doubled by at least 10 ms, or 30 intervals elapsed); operators declare the source and timebase with `ORION_NODE_CLOCK_SOURCE` and `ORION_NODE_TIMEBASE`. Orion never disciplines clocks. The latest sample is in `NodeObservabilitySnapshot::clock` and the `orion_node_clock_*` Prometheus gauges; `orionctl get nodes` now also lists nodes known only from observed state and shows clock fields, and `orionctl describe node` prints them. `NodeApp::refresh_clock_facts_from` takes an injectable `ClockStatusSource`.
- Volatile status lane: latest value per `(StatusSubject, key)` (`provider/`, `executor/`, `resource/`, `workload/` subjects; `TypedConfigValue` values) with a publisher-chosen TTL capped by `ORION_NODE_STATUS_MAX_TTL_MS`, held in node memory only (never persisted, not replicated to peers) and bounded by `ORION_NODE_STATUS_MAX_ENTRIES` / `ORION_NODE_STATUS_MAX_ENTRIES_PER_PUBLISHER`. New control messages `PublishStatus`, `QueryStatus`, `WatchStatus`/`ClientEventKind::Status` (coalesced, newest value per key) and `Status`; providers and executors may only publish for subjects they own. `orion-client` gains `publish_status`, `query_status`, and `watch_status` (`StatusWatch`) on the local provider/executor services, apps, and clients, `LocalControlPlaneClient::query_status`, and prelude exports; `orionctl get status [--subject ...] [--key-prefix ...]`; `resource_usage.status_lane` counters and `orion_status_lane_*` metrics. See `docs/observability.md`.
- Link protocol `Status` (`0x14`), previously reserved: `DeviceSession::publish_status` (fire-and-forget, newest batch wins, rate-limited by `DeviceConfig::status_min_interval_ms`), `HostEvent::Status`, and the node link gateway files device status under the device's provider subject (`LinkStatus::status_batches` / `status_rejects`). Additive: `LINK_PROTOCOL_VERSION` stays 1.
- `orion_client::prelude` plus consumer views: `AssignedWorkload`, `BoundResource`, `assigned_workloads`, `resources_bound_to`, and `LocalExecutorService::watch_assigned_workloads`.
- `peer-tcp` cargo feature for `orion-node` (on by default, and usable with `--no-default-features`): peer sync with `orion+tcp://host:port` peers over plain TCP, listener `ORION_NODE_PEER_ADDR`. Frames reuse the control preamble (`[b"OC"][version][len]`), requests are the HTTP codec's signed peer requests, and responses are ed25519-signed by the responder and bound to the request they answer; no TLS (authenticity, integrity and replay protection, not confidentiality; see the threat model in `docs/peer-sync.md`). HTTP and TCP peers can be mixed. `--no-default-features --features peer-tcp` gives an IPC-only appliance build that clusters without axum, hyper, reqwest, or rustls: 2.88 MiB stripped and 74 crates, against 2.65 MiB / 74 crates IPC-only and 5.05 MiB / 151 crates with `transport-http` (x86_64, release profile).
- Per-object conflict resolution for desired state with a hybrid logical clock (`orion_core::HlcTimestamp`, `HybridLogicalClock`, `hlc_node_tag`; `no_std`). Every desired object carries the stamp of its last write (`DesiredClusterState::stamps`) and every delete a tombstone (`DesiredClusterState::tombstones`, all sections); peers merge per object, last writer wins (`DesiredClusterState::apply_stamped`), deterministically and independent of delivery order. Remote stamps more than `ORION_NODE_HLC_MAX_DRIFT_MS` (default 5 min) ahead are rejected and counted; tombstones are collected after `ORION_NODE_TOMBSTONE_RETENTION_MS` (default 7 days). New `desired_merge` observability section and `orion_node_desired_merge_*` / `orion_node_hlc_*` metrics.
- Each node pushes its own observed slice (node record, assigned workloads, resources and leases of its providers and executors) to its peers at the end of a sync round when it changed (at least every 30 s); receivers replace only that origin's slice.
- `discovery-mdns` cargo feature for `orion-node` (opt-in; also with `--no-default-features --features peer-tcp,discovery-mdns`): mDNS/DNS-SD peer discovery with the `mdns-sd` crate (`ORION_NODE_DISCOVERY=mdns`, `ORION_NODE_CLUSTER`, `ORION_NODE_DISCOVERY_TTL_MS`, `ORION_NODE_DISCOVERY_INTERFACES`). Nodes advertise `_orion._tcp` (instance = node id; TXT: node id, ed25519 public key, ports, control protocol version, cluster) and keep a discovered set with last-seen and TTL expiry; other clusters are ignored and other protocol versions listed as incompatible. Discovered peers are never trusted automatically: `orionctl get discovered-peers` shows them with key fingerprints, `orionctl peers enroll <node-id>` pins the advertised key after the operator confirms its fingerprint (`--fingerprint` / `--yes` for scripts), and nodes sharing `ORION_NODE_ENROLLMENT_KEY(_FILE)` enroll each other with an HMAC-SHA256 + ed25519 challenge-response handshake over `orion+tcp` (the key never crosses the wire; nonces are single-use). `orionctl peers remove <node-id>` revokes a peer, stops syncing with it and forgets its enrollment; removed peers are not re-enrolled by the shared key. Discovery requires `ORION_NODE_PEER_AUTH=required` and `ORION_NODE_PEER_ADDR`. Enrollments persist in `discovered-peers.json`. New control messages `QueryDiscovery`/`Discovery`, `EnrollDiscoveredPeer`, `RemovePeer`, `EnrollmentHello`/`EnrollmentChallenge`/`EnrollmentConfirm` (part of control protocol v3), `NodeObservabilitySnapshot::discovery` with `orion_node_discovered_peers` and `orion_node_enrollment_*` metrics, `LocalControlPlaneClient::{query_discovery, enroll_discovered_peer, remove_peer}`, and `orionctl peer` as an alias of `orionctl peers`. See `docs/discovery.md`.
- `docs/peer-sync.md`: merge behaviour before and after this release, sync protocol, transports, threat model, tombstones, upgrade and migration, and hooks for placement, cross-node binding and discovery.
- Leaderless workload placement (`docs/placement.md`). Nodes declare labels with `ORION_NODE_LABELS` (`k=v,k2=v2,flag`, published in their observed node record together with schedulability from maintenance mode). `WorkloadRecord::placement` (`WorkloadPlacement`: `node_selector` of `LabelRequirement` equality/existence terms, `colocate_with_resource`, or `any()`) lets every node compute the same node from the same converged state: eligible nodes (live, schedulable, executor for the runtime type, selector, co-location host) ranked by rendezvous hashing of the workload id over node ids, ties to the smaller id (`orion-cluster`, `no_std`: `ClusterView`, `choose_node`, `ClusterCoordinator`). Only the chosen node writes the assignment, to itself, recording `PlacementDecision { node_id, reason: Placed | Failover { from } }`; concurrent writes converge by the HLC merge. Hysteresis: a workload on an eligible node never moves when nodes join; it moves only after its assignee has been gone or ineligible for `ORION_NODE_PLACEMENT_GRACE_MS` (default 10000). Explicit `assigned_node_id` (without a matching decision) is never moved. Peer liveness: a peer is live while this node heard from it (sync round, signed request, observed push) within `ORION_NODE_LIVENESS_TIMEOUT_MS` (default 5000); `NodeApp::unreachable_peers()`, `NodeApp::cluster_view()`.
- Cross-node binding (`docs/placement.md`). A requirement no local resource satisfies is resolved against resources owned by other live nodes (matching type, ownership mode and capabilities, room under the ownership mode counting lease holders and the owner's local bindings), leased by adding a `LeaseHolder` to the resource's `LeaseRecord::holders` in the HLC-merged desired state (competing leases resolve to one holder everywhere; the owner evicts holders beyond capacity or whose workload no longer runs), and bound as `ResourceBinding { node_id: owner, remote: Some(RemoteBinding { endpoints, available }) }`. Executors get remote bindings in `ExecutorCommand::Start` and in executor watch/query records (`AssignedWorkload::remote_bindings`, `BoundResource::{is_remote, is_available}`); providers see leases held by remote workloads in `QueryProviderLeases`/`WatchProviderLeases`. Data flows over the resource's own endpoints; Orion does not proxy it. When the owner stops being live the binding is marked unavailable; after the grace period the lease is released and the requirement re-resolved; a workload running with a binding it no longer holds a lease for is stopped. `ReconcileReport::unsatisfied`, `LocalRuntimeStore::{unreachable_nodes, remote_leases_for}`.
- Host facts (`docs/host-facts.md`): every node samples a `HostFactsSource` every `ORION_NODE_HOST_FACTS_REFRESH_MS` (default 10000, `0` off). Identity facts (`NodeHostFacts`: hostname, os-release `ID`/`NAME`/`VERSION_ID`, image name and version from `IMAGE_ID`/`IMAGE_VERSION` or the files in `ORION_NODE_IMAGE_VERSION_FILE` (none by default), kernel release, architecture, boot id, board serial and model from the device tree or DMI, machine id, CPU count, total memory, extra labels) are published in the node's observed `NodeRecord::host` only when they change and replicate with the observed slice; volatile metrics (`HostMetricsSample`: uptime, load, available memory, `/sys/class/thermal` temperatures, extra metrics) go to the status lane under the new `StatusSubject::Node` (`node/<id>`, keys `host.*`) and to `NodeObservabilitySnapshot::host_facts`. `LinuxHostFactsSource` is the default; `NodeAppBuilder::with_host_facts_source` replaces it and `with_host_facts_overlay` merges richer facts (for example from a hardware-abstraction crate) on top. `orionctl get nodes` / `describe node` show a host section; Prometheus gains `orion_node_host_info`, `orion_node_host_cpu_count`, `orion_node_host_temperature_celsius`, and `orion_node_host_metric`.
- Generic actions (`docs/actions.md`): `ActionRequest` / `ActionResult` / `ActionReport` / `ActionState` / `ActionTarget` (`Node`, `Provider`, `Resource`, `Executor`) / `ActionQuery` and the control messages `RunAction`, `QueryActions`, `WatchActions`, `WatchActionRequests`, `ClaimNodeActions`, `ReportActionResult`, `ActionResults` (`ClientEventKind::ActionRequest` / `ActionResults`). Node-targeted actions run an in-process `ActionHandler` registered with `NodeAppBuilder::with_action_handler` or go to a local client that claimed the name (in-process handlers own their names; claims are released, and pending actions failed, when the client disconnects); provider, executor, and resource actions go to the local client registered as the handler of the provider or executor. Actions for targets on another node are forwarded once over the signed peer transport and polled until final; peers must be authenticated and enrolled. Results are tracked in memory with deadlines (`ORION_NODE_ACTION_DEFAULT_DEADLINE_MS`, `ORION_NODE_ACTION_MAX_DEADLINE_MS`), a TTL (`ORION_NODE_ACTION_RESULT_TTL_MS`), and a cap (`ORION_NODE_ACTION_MAX_TRACKED`). Well-known names with argument conventions (`reboot`, `restart-unit`, `locate`, `self-test`, `update`; none implemented) and an `action.<id>.{state,progress,error}` status-lane key convention. `orion-client`: `LocalControlPlaneClient::{run_action, query_actions, wait_for_action}`, `ActionWatch`, and `watch_action_requests` / `claim_node_actions` (`ActionRequestWatch`) on the provider and executor services. `orionctl action run <target> <name> [--arg k=v]... [--wait]` and `orionctl get actions`.
- Link gateway counters over the control protocol: `NodeObservabilitySnapshot::links` (`LinkStatusSnapshot`, empty without `link-gateway`; `orion_node::link_gateway::LinkStatus` is now an alias of it), `orionctl get links [-o json|metrics]`, and per-link Prometheus families (`orion_link_open`, `orion_link_devices`, `orion_link_frames_total`, `orion_link_bytes_total`, `orion_link_errors_total`, `orion_link_rejects_total`, `orion_link_sessions_total`, `orion_link_device_timeouts_total`, `orion_link_status_batches_total`).
- `orionctl get workload(s)` shows `assignment=` (`explicit`, `placed`, `failover-from:<node>`, `pending`, `manual`), `placement=` and `bound=` (bindings with their node, `*` for remote); `orionctl describe workload` shows assignment, placement and one line per binding with node, endpoints and availability.
- `systemd-notify` cargo feature for `orion-node` (opt-in, Unix, no libsystemd dependency; works with `--no-default-features`): `sd_notify` over `$NOTIFY_SOCKET` (path or Linux abstract `@` socket) with `READY=1` once state replay is done and every listener (IPC, IPC stream, HTTP/probe, `orion+tcp`, link gateway, discovery) accepts connections, `STATUS=` summaries, and `STOPPING=1` on shutdown; and the service watchdog: `WATCHDOG=1` every `WATCHDOG_USEC / 2` (respecting `WATCHDOG_PID`) only while the reconcile loop keeps finishing passes, so a wedged loop or starved runtime stops the pings and systemd restarts the node. `NodeApp::reconcile_loop_heartbeat()` exposes the loop's pass counter; `orion_node::systemd` exposes `Notifier`, `spawn_watchdog` and the `LivenessProbe` trait. A no-op when the variables are absent. See "Running under systemd" in `docs/node-env.md`.
- `packaging/`: generic packaging for running `orion-node` as a managed service on any systemd + glibc Linux image. `packaging/systemd/orion-node.service` (`Type=notify`, `WatchdogSec=30s`, `Restart=always` with a 1-30 s backoff and no start limit, fixed `orion` user with `dialout`, `StateDirectory`/`RuntimeDirectory`, hardening that keeps IPC sockets, peer sync, discovery, serial and CAN working, `EnvironmentFile=-/etc/default/orion-node.env`, `MALLOC_ARENA_MAX=2`), `orion-node.env.example` (the single-node appliance profile), a `systemd-sysusers` entry, a Buildroot users table, a preset, and `packaging/gaia/orion-node.toml`, an importable Gaia layer that builds the appliance feature set for `aarch64-unknown-linux-gnu` and stages all of it. See `packaging/README.md`.
- Workspace `.cargo/config.toml` links `aarch64-unknown-linux-gnu` binaries with `-z max-page-size=65536`, so one binary loads on 4 KiB, 16 KiB (Raspberry Pi 5 / CM5) and 64 KiB page kernels. The appliance build (`--no-default-features --features peer-tcp,discovery-mdns,systemd-notify`) is 3.07 MiB stripped for aarch64 and needs glibc 2.34 or newer.

- Remote operators (`docs/remote-operator.md`): an embeddable client for desktop and fleet tools, `orion-client` feature `remote` (`orion_client::remote`, also `orion::remote`), with `OperatorIdentity` (ed25519, caller-owned storage, `operator:<name>` ids, `sha256:` fingerprints), `NodeTrust` (first use, pinned key, pinned node), and `RemoteOperator::{connect, hello, enroll_with_key, state_snapshot, nodes, node, status, watch_status, run_action, action, query_action, query_actions, wait_for_action, watch_actions, observability}` over signed `orion+tcp` (watches poll, 500 ms default); feature `discovery` browses `_orion._tcp` with mDNS. No HTTP stack and no node internals: 61 crates, and the example binary is 1.00 MiB stripped (about 565 KiB over a tokio-only binary). Nodes treat operators as a principal kind of their own: enrolled by administrator approval (`orionctl operators enroll <id> --fingerprint ... [--action PATTERN]... [--no-actions] [--no-read]`, `orionctl operators remove`, `orionctl get operators`; persisted in `trusted-operators.json`, pending requests listed for approval) or with the shared enrollment key (the discovery handshake with `EnrollmentHello::role = operator`); authorized per operator (read access, action-name patterns, node default `ORION_NODE_OPERATOR_ACTIONS`); never synced with, never counted as peers, for liveness or placement, and refused for every desired-state write. Actions they submit carry `requested_by = operator:<name>` and are forwarded to the owning node like any action. Status queries (`QueryStatus`, from operators and local control-plane clients) for a subject another node owns are now forwarded once to that node over the signed peer transport. Example: `crates/client/examples/remote_operator.rs`.
- `orion-auth` now holds the `orion+tcp` frame payloads (`peer_tcp`), the `_orion._tcp` TXT layout (`discovery`), key hex helpers, and, behind the new `crypto` / `enrollment` features, ed25519 request/response signing, key fingerprints and the enrollment handshake proofs; `orion-transport-ipc` has the `orion+tcp` exchange client (`ControlTcpClient`). `orion-node` and the remote operator client share them.

### Changed

- The remote operator client (`orion-client --no-default-features --features remote`, and `discovery`) builds on Windows and macOS. `orion-transport-ipc` now builds on every target: the control frame codec (preamble, `ControlFrameReadState`, `write_control_*` / `read_control_*`, moved from the Unix socket module into `stream_frame`), the in-memory transport and `ControlTcpClient` are platform-neutral, while the Unix socket client/server, fd frames and the fd latest-value channel are `#[cfg(unix)]` (`libc` is a Unix-only dependency). The fd frame code also compiles on macOS now (`msghdr` field widths). The workspace `orion-client` dependency no longer enables the Unix-only `ipc` feature by default (`orionctl` and the `orion` facade's `client` feature request it), and the `orion-client` HTTP dev-dependency is Unix-only, so the `remote_operator` example builds on Windows without a C toolchain. Wire format and node behaviour are unchanged. CI lints the Windows and macOS targets on Linux, runs the client unit tests on `windows-latest` and `macos-latest`, and the `orion-transport-ipc` unit tests (including a new `orion+tcp` loopback test of `ControlTcpClient`) on Windows.
- Control protocol v4 also carries the remote operator messages (`OperatorHello`, `QueryOperators`, `Operators`, `EnrollOperator`, `RemoveOperator`, `HttpResponsePayload::OperatorWelcome` / `Status`, the `/v1/control/operator` route) and `EnrollmentHello::role`; the enrollment handshake version is 2 and binds the role into its transcript. The version stays 4 (unreleased); the layout fingerprint and the canonical encoding fixture are updated. The peer trust store format is unchanged (operators live in the new `trusted-operators.json`).
- `CONTROL_PROTOCOL_VERSION` is now 4 for host facts (`NodeRecord::host`, `NodeObservabilitySnapshot::host_facts`, `StatusSubject::Node`), generic actions, and `NodeObservabilitySnapshot::links`; `orionctl`, client libraries, and `orion-node` must be upgraded together. The persisted snapshot format goes from 4 to 5; format-4 state directories are rewritten in place on first start (every record, stamp and revision kept; the old files are kept in `legacy-format-4/`).

- `orionctl` links only the client half of `orion-transport-http` and no longer depends on the `orion` facade; the default build drops from 4.41 MiB / 146 crates to 4.38 MiB / 139 crates with unchanged behaviour. The workspace `reqwest` dependency no longer enables the unused `json` feature.
- The node reconcile loop is event-driven: it wakes (coalesced for up to 5ms) on desired-state commits, observed-state merges, provider/executor state published over IPC, maintenance changes, and integration registration, plus a periodic backstop (`ORION_NODE_RECONCILE_BACKSTOP_MS`, default 5000). `ORION_NODE_RECONCILE_MS` is now the minimum idle gap between passes. With the loop running, IPC provider/executor updates and applied mutations defer their reconcile to it.
- Observed and applied state writes are coalesced while the reconcile loop runs: at most one write per `ORION_NODE_OBSERVED_PERSIST_INTERVAL_MS` (default 2000; `0` restores immediate writes), flushed when the loop shuts down and carried along by every desired-state commit, which stays durable immediately. After a crash, persisted observed state can be up to one interval stale (providers republish). `resource_usage.observed_persistence` reports the coalescing counters. `NodeApp::flush_observed_state()` forces a write.
- `CONTROL_PROTOCOL_VERSION` is now 3 for the status-lane messages and the new `resource_usage` sections; `orionctl`, client libraries, and `orion-node` must be upgraded together.
- Successful reconcile passes log at `debug` and only record a recent observability event when they changed something; reconcile counters and latency still cover every pass.
- `ResourceEndpoint` and `ResourceEndpointError` are now `#[non_exhaustive]`; unknown but valid schemes parse as `Custom` instead of failing with `UnsupportedScheme`.
- Snapshot additions change the rkyv control-protocol layout, so `orionctl` and `orion-node` must be upgraded together.
- Explicit control-protocol versioning: `orion_core::CONTROL_PROTOCOL_VERSION` (now 2, for the `resource_usage` layout) is carried in a fixed 4-byte preamble on every local IPC message (unary and stream frames, including the `ClientHello`/`ClientWelcome` handshake) and in the `x-orion-control-protocol` HTTP header, and checked before any rkyv payload is decoded. Version skew now fails with `IpcTransportError`/`HttpTransportError`/`ClientError::ProtocolMismatch { local, remote }` telling operators to upgrade orionctl and orion-node together, instead of opaque rkyv decode errors. A layout fingerprint test (`crates/orion/tests/control_protocol_layout.rs`) forces a version bump on future layout changes. See `docs/protocol-compatibility.md`.
- `CONTROL_PROTOCOL_VERSION` is now 3 for `NodeRecord::clock`, `NodeObservabilitySnapshot::clock`, and the removed ownership mode; `orionctl`, client libraries, and `orion-node` must be upgraded together. `LINK_PROTOCOL_VERSION` stays 1 because the postcard encoding of the remaining ownership modes is unchanged.
- Observed node records are no longer pruned when desired state does not list the node: the local node's record and those of nodes referenced by desired providers, executors, or assigned workloads are kept.
- CI workflows install the pinned 1.94.0 toolchain (matching `rust-toolchain.toml`) instead of `stable`.
- Peer sync is transport-independent (`PeerSyncTransport`) and bidirectional: one round exchanges `Hello`, compares per-object versions of the differing sections (`SyncSummaryRequest`), pushes the local winners and pulls the peer's (`SyncDiffRequest`). Before, the node with the higher revision counter overwrote whole sections of the other, equal-revision conflicts were merged by "bytewise max" of the rkyv encodings, and deletes other than workload deletes did not survive a merge. A pushed `Snapshot` is now merged per object instead of adopted wholesale, and mutation history is no longer shipped to peers. The cached "skip hello" fast paths are gone; a converged round is one `Hello`.
- `Revision` is a node-local commit sequence number; converged peers usually have different revisions and are compared by desired-state fingerprint (which now covers stamps and tombstones). `MutationBatch` gains `stamps`; unstamped batches (from `orionctl` and clients) are stamped by the node on commit. `DesiredClusterState::workload_tombstones` and `DesiredStateSummary::workload_tombstones` are replaced by `stamps`/`tombstones`, and `StateSectionCounts::workload_tombstones` (metric kind `workload_tombstones`) by `tombstones`.
- The per-object versions are part of the same `CONTROL_PROTOCOL_VERSION` 3 (layout fingerprint and canonical encoding fixture recomputed for the combined release). The snapshot format goes from 3 to 4: existing state directories are migrated on first start (old files kept in `legacy-format-3/`, observed state rebuilt from live reports); a directory that cannot be migrated fails startup without being overwritten.
- `ControlSurface::PeerTcp` and `ControlSource::PeerTcp` for requests from `orion+tcp` peers; peer authentication and authorization treat both peer surfaces alike (`ControlSurface::is_peer`).
- A peer's `ObservedUpdate` no longer overwrites the receiver's observed revision or applied revision.
- Placement and cross-node binding are part of the same `CONTROL_PROTOCOL_VERSION` 3 (`WorkloadRecord::placement`, `ResourceBinding::remote`, `LeaseRecord::holders`; layout fingerprint and canonical fixture recomputed). `orion_cluster::ClusterCoordinator` is no longer a unit struct: `ClusterCoordinator::new(node_id, grace_ms)`; its `assign` helper was removed.
- Each node's observed slice now carries every resource of its providers and executors (not only those also in the desired state), and peers accept them; `QueryProviderLeases` covers leases on resources a provider only reports in observed state.
- The runtime planner only treats this node's own observed report of a workload as "already running", so a workload that failed over from another node is started even while the old node's report is still around; an executor snapshot no longer keeps a local observed workload that the desired state assigns to another node.
- Desired-state validation accepts a local workload whose requirement only a resource on another node can satisfy (cross-node binding resolves it).
- `orion-node` shuts down gracefully on `SIGTERM` as well as `SIGINT` (stopping loops, flushing coalesced observed state, closing listeners); before, `SIGTERM` (how systemd and container runtimes stop services) killed it without cleanup.

### Removed

- `ResourceOwnershipMode::ExclusiveOwnerPublishesDerived`. It was enforced exactly like `Exclusive`; use `Exclusive` (the camera client examples now do).

### Fixed

- `send_unix_fd_frame_async` / `recv_unix_fd_frame_async` no longer spin at 100% CPU on idle connections; readiness is now cleared through `try_io`.
- Background loops no longer busy-spin when their `ReconcileLoopHandle` is dropped without shutdown (for example after a startup error).
- State persistence no longer fails with "cannot rewrite desired snapshot without encoded desired bytes" when a mutation races the snapshot capture; the rewrite is deferred to the next persist.
- Observed resource and workload changes that do not move the observed revision (for example a provider updating a resource's health or labels) are now written to the persisted observed section; previously only the manifest was rewritten until the revision changed.
- Executor and provider subscriptions no longer drop all but the first matching event of a batched `ClientEvents` frame.
