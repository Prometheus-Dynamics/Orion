# liborion

`liborion` is Orion's C library over the stable interface (docs/design/stable-interface.md,
step 7). Software built outside the image, in C or anything with a C FFI, uses it to talk to a
node without linking Orion's Rust crates or speaking the link protocol itself.

- `crates/capi` (`orion-capi`): the Rust core and the `extern "C"` surface. Rust callers can use
  its `link::LinkClient` and `latest::LatestClient` directly.
- `crates/liborion`: the library, `liborion.a` and `liborion.so.1` (`cargo build -p liborion`;
  `--release` for the size-optimized build).
- `crates/capi/include/orion/orion.h`: the header, generated by cbindgen
  (`scripts/capi.sh header`). It includes the hardware repository's shared ABI header, shipped
  beside it in `crates/capi/include/` (byte for byte the ABI crate's, checked in CI): status
  codes, handles, the version handshake and message sinks are that crate's 1.0 (layout hash
  `0xa02cfb4a8dd4545b`), so a program using several such libraries sees each type once. The
  types keep that crate's names (`LemnosStatus`, `LEMNOS_OK`, ...).

## Versions

The surface has a major and a minor (`ORION_ABI_MAJOR`, `ORION_ABI_MINOR`) and a hash of the
layouts that cross it (`ORION_LAYOUT_HASH`, which folds in the shared types' hash). A caller
checks once, before any other call:

```c
LemnosAbiVersion mine = {sizeof mine, ORION_ABI_MAJOR, ORION_ABI_MINOR, ORION_LAYOUT_HASH};
if (orion_check_version(&mine) != LEMNOS_OK) { /* built against another liborion */ }
```

The library accepts a caller with the same major and layout hash and a minor no newer than its
own. The shared library's SONAME carries the major (`liborion.so.1`), so the loader refuses a
library of another major before any call. Symbol version nodes are not used: rustc's cdylib
version script would override them.

Versions move only at a release the user calls. During development the surface changes freely
when something needs it: update the header (`scripts/capi.sh header`), `ORION_LAYOUT_HASH` (the
build fails until it matches), `crates/capi/symbols.txt` and these docs, and note the change in
the CHANGELOG, with the version unchanged. At a release, the changes since the last one set it:

| Change since the last release | Version |
|---|---|
| Functions or constants added | minor + 1 |
| A function removed or its signature changed, a struct changed | major + 1 (new SONAME) |

CI (`scripts/capi.sh check`) fails when the header is not cbindgen's output, the shared ABI header
is not the ABI crate's, the exported symbols differ from `crates/capi/symbols.txt`, the SONAME
does not match the major, or a C program built against the header disagrees with the library
(it recomputes the layout hash from `sizeof` and `offsetof` and runs against both the static and
the shared library).

## Conventions

- Every call returns a `LemnosStatus`: `LEMNOS_OK`, a negative errno (`-ENOENT` for a missing
  socket, `-ETIMEDOUT`, `-EAGAIN`, `-ECONNRESET` when the node closed the session, `-EPROTO`),
  or a shared code (`LEMNOS_E_STALE_HANDLE`, `LEMNOS_E_BUFFER_TOO_SMALL`, `LEMNOS_E_PANIC`).
  `orion_last_error(sink)` gives the text of the calling thread's last failure.
- Handles are generation-counted: a closed handle is refused (`LEMNOS_E_STALE_HANDLE`), never
  reused by accident. `orion_close` closes any of them. A handle may be used from any thread;
  calls on one handle are serialized.
- Structs the caller passes start with `struct_size`, set to `sizeof`. They hold no pointers and
  only fixed-width fields, so their layouts (and `ORION_LAYOUT_HASH`) are the same on every
  target with 8-byte aligned 64-bit integers (all of Orion's; not 32-bit x86).
- No call allocates memory the caller frees. Bytes go into buffers the caller supplies; a buffer
  too small leaves the item in place and says what it needs.
- No thread is started: blocking calls block the caller.

## Link client

A client session on a node's `unix:` link (docs/link-protocol.md, client role): status queries
and watches.

```c
LemnosHandle link;
orion_link_connect("/run/orion/link.sock", "my-tool", 2000, &link);
uint32_t req;
orion_link_status_watch(link, ORION_SUBJECT_PROVIDER, "provider.imu-board", NULL, &req);
uint8_t buf[2048];
OrionEvent event = {.struct_size = sizeof event};
for (;;) {
    LemnosStatus s = orion_link_next(link, -1, &event, buf, sizeof buf);
    if (s == LEMNOS_E_BUFFER_TOO_SMALL) { /* grow to subject_len + key_len + data_len */ }
    if (s != LEMNOS_OK) break;
    /* buf: subject id, key, then the string or bytes value, back to back */
}
orion_close(link);
```

Events: `ORION_EVENT_STATUS` (an entry set: `value_type` says which of `int_value`,
`uint_value`, `float_value` or the data bytes holds the value), `ORION_EVENT_EXPIRED`,
`ORION_EVENT_ANSWERED` (the end of a query's answer or of one change set of a watch;
`ORION_EVENT_BOOTSTRAP` marks the first answer of a watch, the whole current set), and
`ORION_EVENT_REQUEST_ERROR` (the node refused the request: `uint_value` is the link's error code
and the data its reason). One watch per session.

The session stays alive only while the client pings, which `orion_link_next` does while it
waits. A program with its own event loop polls `orion_link_fd` for reading and wakes up at the
latest after `orion_link_service_in_ms`, then calls `orion_link_next(link, 0, ...)` until it
returns `-EAGAIN`.

Not in this version (they follow as minor additions): running and watching actions, record reads
and watches, and stream subscriptions.

## Latest-value client

A blocking client of an fd latest-value channel (`UnixFdLatestServer`): the newest frame, or the
first one newer than a sequence held, with its payload and the descriptors sent with it (a
dma-buf or memfd per plane, for example).

```c
LemnosHandle latest;
orion_latest_connect("/run/camera/latest.sock", &latest);
OrionLatestFrame frame = {.struct_size = sizeof frame};
uint8_t payload[256];
uint64_t seen = 0;
while (orion_latest_next(latest, seen, 1000, &frame, payload, sizeof payload) == LEMNOS_OK) {
    if (frame.status != ORION_LATEST_FRAME) continue; /* timeout, empty, stale or busy */
    seen = frame.sequence;
    /* use frame.fds[0 .. frame.fd_count]; they are the caller's to close */
}
```

A payload larger than the buffer returns `LEMNOS_E_BUFFER_TOO_SMALL` with `payload_len` set; the
reply is kept and the next call on the handle returns it.

## Linking

- Shared: `-lorion` (the loader looks for `liborion.so.1`).
- Static, glibc: `liborion.a -lpthread -ldl -lm`.
- Static, musl: `liborion.a -lunwind` (Rust's panic guard needs the unwinder, which musl does not
  bundle), for example `zig cc -target aarch64-linux-musl ... liborion.a -lunwind -static`.

On `aarch64-unknown-linux-musl` only the static library is built (Rust has no musl `cdylib`).

## Cost

No runtime, no thread, no allocator of its own: a link session holds three 4 KiB buffers and its
pending events; a latest-value connection holds nothing between calls. One `orion_link_next` is a
`poll` and a `read` of the socket, plus decoding.

Size: a C program linked statically against the release `liborion.a` (aarch64 musl, stripped)
is 435 KiB, musl included. It ran on a Cortex-A76 board with the same `ORION_LAYOUT_HASH` as on
x86_64.
