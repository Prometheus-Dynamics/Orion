## Build

- A file can be written straight to where a registered receiver says, so a small board never holds it twice.
- This is the hook board management will use.

## Proof

A large file passes with memory use bounded by the chunk size.

## Built

- Two kinds with vectors, `FILE_SINK` `0x25` and `FILE_SINK_READY` `0x26`. Nothing recorded
  before changed.
- `crates/node/files-sink` (`orion-files-sink`): `Sinks` with `request` (for `FileSink` and a
  receiver's `FileStatus`), `pass` (for the three kinds of a transfer, before the node's own
  store), `gone`.
- `orion-relay` routes the two kinds a receiver sends; `orion-node-app` looks at every
  transfer with `pass` first.
- The client side, which board management uses: `Files::sink(prefix)` in `orion-files` gives
  a `Sink` with `next` (what was handed: `Begin`, `Chunk`, `Commit`) and `status`. It is in
  the `orion` facade under `files`.

## Proved by

- `crates/node/node-app/tests/sink.rs`, against a real comm core, with a board manager that
  is the receiver for `slots/` and writes to a file standing for the slot:
  - A 96 MiB file that is made as it is read is pushed to `slots/b.img`. It ends
    `Committed`, the slot holds it whole (same digest), the sender was paced by over a
    thousand answers, and the node's store and its `.incoming` hold nothing of it. The peak
    memory of the whole process (sender, comm core, node logic and receiver together) grew
    by 0 KiB while it passed; the test allows 8 MiB. With the receiver made to keep the
    bytes it is handed, the same test fails.
  - A file for another destination still goes to the node's store.
  - The receiver goes away: the same destination is then a place in the node's store.
- `crates/node/files-sink/tests/sinks.rs`, 8 tests: frames pass as they came, both ways; a
  destination under no prefix is the store's; the longest prefix; one receiver a prefix; only
  the receiver answers for a transfer; a sender in a new session; a receiver that goes; a
  rejection ends the transfer.

## Different from the brief

"Written straight to where a registered receiver says": the receiver does not say a path for
the node to write to. The node cannot open a boot slot for it (node logic is handed no
descriptors, and how a slot is written is the board manager's business), so the file is
handed to the receiver chunk by chunk and the receiver writes it. What the brief asks for
holds: the board never has the file twice, and memory is bounded by the chunk.

## Found on the way (client, D6)

`Files::push` hashes the whole file before it sends anything, and did nothing with its
session meanwhile. For a large file, or a slow disk, that is longer than the six seconds a
board waits to hear from a session, and the push then failed with a broken connection. The
96 MiB test here hit it in the gate. `push` now looks after its session every quarter of a
second while it hashes. `crates/client/files/tests/files.rs` has a file that takes eight
seconds to hash; it failed before the change.
