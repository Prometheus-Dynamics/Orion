## Built

- `orion-actions`: `Actions::run` starts an action and returns a `Run` (`poll`, `wait`,
  `finish`, `cancel`); `Actions::attach` comes back to a detached run. `Actions::register` adds
  an action with its policy and gives a `Registration`, where its runs arrive as
  `Request::Run` and `Request::Cancel`, answered with `progress` and `finish`.
- Nothing grows without bound: a run keeps its newest progress and its result; runs waiting for
  a program queue up to 64 and the next is answered `Rejected` as busy, at once.
- One kind was added, `ACTION_REGISTERED` 0x37, so a registration is confirmed and not assumed.
  No recorded vector changed.

## Proved by

`tests/actions.rs`: this test is the comm core, with security on, and the caller; it starts
itself again as the program that owns the actions. A run of the other process's action is
followed through three progress reports to its result; one fails with its reason; one is
cancelled half way; one started detached outlives its caller's session and is finished for a
second session that attaches. An action registered for root only is refused to the test's own
user, and the test checks that no such run ever reached the owning process. Ran clean six
times.

## For E (the action router)

The router in the test is a stand-in. What the client expects of the real one:

- `asks` answers a `Run` with the policy the action was registered with, so the one check
  decides it. That is what "runs through the check" rests on.
- `Register` is answered with `Registered`.
- The run's number in `Claim`, `Progress`, `ActionResult` and `Cancel` to and from the owning
  program is the router's own; to and from the caller it is the caller's.
