# C50: A program killed with frames unread is a peer closing, not a broken connection

**Status:** done

**Group:** C. Comm core

**Wave:** 18

**Needs:** C49

Read `AGENTS.md` and `docs/design.md` first.

## Changes

`crates/comm/unix` (`src/lib.rs`), `TODO.md`.

## Build

The board run with C49 showed no stalled writes. It did show two sessions dropped with "its
connection failed: invalid data": a command-line publisher and `drill-publisher`, both killed
by the run itself. A killed program is its peer closing. Find out why it reads as broken, and
make it a clean close if that is right.

## Built

- **Why.** The kill run on the bench, with the receive error printed, gave
  `Io(ConnectionReset)` both times. On a Unix socket, a peer that closes with frames still
  unread in its own queue resets the connection: the comm core had sent these programs frames
  they never read before they were killed. The carrier wrapped every receive error as
  `InvalidData`, the I/O ones included, so a reset read as damage.
- **Now:**
  - a reset is the peer closing (`Ok(None)`), the same as a close with nothing left unread, and
    the session ends with nothing logged;
  - any other I/O failure keeps its own kind;
  - only real damage is `InvalidData`, in fixed words: "a frame larger than the buffer",
    "more descriptors than allowed", "the peer closed inside a frame", or "a malformed control
    message", not the error's `Debug` form. Fixed words rather than the fdpass library's own
    formatted ones, which would have put `orion-recovery` over its size limit.
- **Writes are left as C49 made them.** A write that fails on a gone peer is still
  `WriteFailed` with its kind, such as broken pipe. The reader normally sees the close first and
  ends the session before a write can fail.

## Proved by

- `crates/comm/unix/src/lib.rs`, unit tests on the carrier's receive:
  - `a_peer_gone_with_frames_unread_reads_as_closed`: one end sends a frame, the other drops
    without reading it, and the receive is `Ok(None)`.
  - `a_frame_too_large_is_invalid_data_saying_so`: a header saying 200 bytes against a
    64-byte buffer is `InvalidData`, "a frame larger than the buffer".
  - `a_socket_failure_keeps_its_kind`: receiving on a listening socket fails as
    `InvalidInput`, not `InvalidData`.
- **The kill run on the bench** (C48's board script, run locally on next's binaries): before,
  two sessions were dropped with "invalid data". After, no drop is logged at all.
- **Mutations.** Five were made, and all were caught: the reset not taken as a close, every
  failure taken as a close, I/O failures wrapped as `InvalidData` again, the wrong words for a
  frame too large, and damage given a kind other than `InvalidData`.
- **Size.** `orion-recovery` for this machine is 3,269,776 bytes, under its 3,270,000 limit.
  The first version, with the library's formatted words, was 704 bytes over.
- **Runs.** The gate passed.

## Different from the brief

- No board run. The cause reproduces on the bench, and the change is in the carrier's error
  mapping, not in anything the board does differently. The next board run will show it.
