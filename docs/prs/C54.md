# C54: A program is told a run is detached, and a deadline's end says so

- **Status:** done
- **Group:** C (actions)
- **Wave:** 18
- **Needs:** C53b

## Changes

- `Claim` gets a trailing `detached: bool`. Node logic sets it from the `Run`, and the stub router does the same. A node that doesn't send it gives `false`. The wire vector for `ACTION_CLAIM` is re-recorded: one byte more.
- `Request::Run { detached }` in the client. A program no longer has to infer from the deadline whether `CallerGone` ends a run.
- `orion_msg_actions::DEADLINE_CODE = 110` (the number of `ETIMEDOUT`). When node logic ends a run because its deadline passed, the run is `TimedOut` with that code. This holds both for the caller and for whoever attaches later. Node logic's other ends keep code 0; a program's own codes pass through as given.
- Docs: `docs/client.md`, `docs/node.md`, `docs/wire.md` (an addition with no level).

## Proved by

- `orion-action-list`:
  - the deadline test pins `(TimedOut, 110)` and `claim.detached == false`;
  - the detached-deadline test pins `claim.detached` and `(TimedOut, 110)` through an attach;
  - a program that went, and node logic stopping, pin code 0;
  - a kept program result pins its own code (11).
- `orion-actions`: the provider in the second process asserts `detached` is true only for the run started detached.
- Mutations, each failing a test:
  - the node sending `detached: false`;
  - the client dropping the field;
  - the stub router dropping it;
  - the deadline code set to 0.

## Different from the brief

Nothing. The microcontroller API doesn't expose `detached` yet. It goes with the queued MCU `CALLER_GONE` item, which is where it matters.
