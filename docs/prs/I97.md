## Why

Two writers of one record were settled by its stamp: the later write stood, and the earlier
was lost with nothing said. A program with two writers in ordinary use, two browser sessions
editing one pipeline, lost edits silently. And two sessions that each made the same workload
both succeeded, the second replacing the first.

## Built

- **Workloads.** `WorkloadPut` and `WorkloadRemove` carry an appended `based_on`. With a
  stamp, the write is made only if the workload's record still has it. Zero means "there is
  none yet": make it, never replace one. Absent, it writes whatever is there, as before.
- **Records.** An entry of a client's `Put` already carried a stamp, which a node ignored. Not
  zero, it is now what the write is based on. Zero is unconditional, which is what every
  writer in this repository sends. All of a `Put` is made or none, as before.
- **The refusal** is a new code, `Stale` (24), with words that say when each was written:
  `pipeline.front was written at <ms> ms: this write was based on <ms> ms`, `... is there
  already ...`, `... is not there ...`. `ClientError::is_stale()` on the client.
- **What a put was based on is not kept.** The workload's record is what should run. A put
  that carries `based_on` is stored without it, so the record is the same bytes whoever
  wrote it.
- **The stamp comes back.** `WorkloadStatus` carries an appended `stamp`, the record's, so a
  caller that is told where its workload is holds what its next write is based on
  (`Tracked::stamp`). A record put already answered with the stored records and their stamps.
- **Client:** `workloads().put_based_on(workload, files, stamp)`, `remove_based_on(name, force,
  stamp)`; `records().put` unchanged in shape.
- **Level 7.** `INTERFACE_LEVEL` is 7 and `Feature::BasedOn` is level 7. A write based on a
  version is sent only to a node at level 7: below it the call fails with `ClientError::Level`
  and sends nothing, because that node would write whatever is there.

## Strict on one board, last write wins across boards

The node that takes the write makes the check. Two boards that each take a write based on the
same stamp both make it, and peer sync keeps the later one. `based_on` is not cluster-wide.
The docs say so in those words, in `client.md`, `node.md` and `from-dev.md`.

## Mixed levels, both ways

The boards in the field will mix levels until every pin moves.

- **A level-6 client and a level-7 node.** Its put and remove have no `based_on`: read as
  based on nothing. The node's status has a stamp appended, which it does not read. If it put
  a stamp on a record entry all the same, it is told `already exists`, a code it knows.
- **A level-7 client and a level-6 node.** A write based on nothing carries one byte more,
  which that node does not read. A write based on a version is never sent. A status from it
  has no stamp: read as zero.

Shown by: `orion-msg-workloads` `levels::a_level_6_side_and_a_level_7_side_read_each_others_workload_messages`
(each message as level 6 had it, against each as it is now, both ways); `orion`
`older::a_level_6_board_takes_plain_writes_and_is_never_sent_one_based_on_a_version` (a comm
core that welcomes at level 6: plain writes work, the status's stamp is zero, and each of the
three based-on calls fails with `Level { BasedOn, needs: 7, node: 6 }`); and `orion-server`'s
test of what a session below the level is told.

Not shown: a real level-6 build on the other end. The level-6 node is this build's comm core
told to welcome at 6, and the level-6 messages are written out in the test as they were.

## One change besides

`workloads().remove` now keeps its request, so that a refusal of a remove based on a version
is found by `wait`. A side effect: a `remove` of a workload that is not there is refused to
`wait` at once, `not found`, where `wait` used to run out its time. `orion-ctl workload
remove` of one that is gone says so at once.

## A test that failed once

While this was written, `leases::a_program_that_stops_answering_loses_its_lease_to_a_claimant_and_is_told_by_whom`
(`orion-node-app`) failed in one of three whole-workspace runs, a run that took 57 s where 37 s
is usual. Its output was not kept, so what failed is not known.

Reading the test found a wall-time assumption that a loaded machine breaks: it wanted the
second program's claim refused because the holder "is answering", but the holder stops being
heard at its own claim and the second program connected only after it. More than the quiet
time (1.5 s) between the two, and the lease is rightly taken at once. With 2 s planted between
the two claims the test failed 3 of 3, `taken from a holder that answers`.

Fixed here: the second program connects first, and a claim that comes after the quiet time may
take the lease, since what the code promises is "not before", which the test still checks.
With the same 2 s planted it passes 3 of 3. Recorded in `docs/flakes.md`, with the plain
statement that this may not be the failure that was seen. It does not touch what this PR
changes: the test writes leases with a zero stamp.
