## Changes

## Why

A program receiving files through a sink did long device work at the commit, and the pushes to
it ended on their own with "timed out". The bounds the push keeps were only in the code
(`crates/client/files/src/push.rs`, the `Phase::Sending` and `Phase::Commit` steps): the
docs said how long a session may be quiet, not how long a push waits for the board's answers.

## Built

A paragraph after "A push can be stepped" says:

- **While a push begins and sends**, each answer is due within `Options::reply`'s bound,
  counted from the board's last change of what it says about the transfer. Under the default
  that is `Options::timeout`, 5 s. The same status sent again does not restart it.
- **At the commit**, the wait counts from the commit. Only `Committed` or `Rejected` ends it.
  Under `Reply::Timeout` it is twelve `Options::timeout`s (60 s by default), under `Within` the
  bound, and under `Alive` as long as the node is heard from, up to the ceiling.
- **A long commit** needs `set_reply(Reply::Alive { ceiling })` or `Reply::Within(bound)` above
  the work's longest time, set before the push. The receiver only has to go on pumping.

## Proof

- Each statement was read against `push.rs`: the `last_heard` renewal only when the status
  changes, `since` fixed when `FileCommit` is sent, `self.timeout * 12` under `Reply::Timeout`,
  and `reply_left(since)` under `Within` and `Alive`.
- **The landing gate passed.**
