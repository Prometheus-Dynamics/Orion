# I142: the gate's lanes say when they ran, fuzzing has a budget of runs, and a killed copy cleans up

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I141

Read `AGENTS.md` and `docs/design.md` first.

## Why

When every lane ran, a gate took about 210 s. Of that, 45 to 50 s went on waiting for lanes to
end after the main part had finished. The log could not say why: it gave each lane's steps
their times, but not when the lane started, when it ended, or what its copy of the Cargo home
took.

The short fuzz run gave each target 3 s of wall time, so a loaded machine fuzzed less.
- Across 28 gates, one target made between 348 and 80,118 runs.
- In one gate, fuzzing used 12.6 CPU-s of the 36 it was given, and still passed.

The lane keys' self-test (20 s when it runs) sat on the main part's path, though it builds
nothing.

A gate that stopped early ended its lanes in the middle of copying the Cargo home. Each left a
`lanes/<name>.new.<pid>` behind, for good: one red gate left six.

## Changes

- **Each lane's last line says when it ran:** "lane NAME: started at X s, its Cargo home in Y s,
  ended at Z s", in seconds after the gate began. The wait for the lanes says when it began and
  ended too.
- **The fuzz targets run a number of runs, not a number of seconds.**
  - The numbers are in `testing/fuzz/short-runs.tsv`, one row per target with its runs and its seed.
  - Each target's runs are the median of what it made in 3 s in 11 gates at a 5-minute load of
    85 to 115. The table's header names them.
  - Each target starts from its seed, on an empty corpus of the run's own. The local corpus is not
    in git and grows, so a seed alone would not give the same start.
  - Each target's line gives its runs, its time, its seed and the coverage it reached. The coverage
    is no verdict: it varies by a few percent between runs of one seed.
- **What fails the step:**
  - a target short of its runs when the 45 s cap ends it (SHORT): the step prints every target's
    count, the load and the processor count, and says that it is not to be rerun;
  - a target that made more than its runs (OVER: the table was not used);
  - a row with no runs or no seed, a target with no row, or a row with no target;
  - a crash. The red names the crash's input, in a directory of the run's own under the target
    directory (outside the tree), and prints the command that runs that input alone.
- **The lane keys' self-test is the first step of the other-systems lane,** the shortest. On CI it
  runs in that part.
- **A lane's copy of the Cargo home removes its own unfinished copy** when it is ended (TERM or INT).
  The fetch step at the start of each gate removes every `.new.<pid>` and `.old.<pid>` whose
  process is gone, and says so.

## Proved by

- **Fuzz budget:** every target makes exactly its runs, in 5 to 10 s of wall time at loads 33 to 88
  (nice 10).
- **Fuzz red, crash found:** a crash planted in the frame target (an input starting "OR") is found
  3 of 3 times. Each red names the input and prints the replay command. That command, run alone,
  stops on the planted panic.
- **Fuzz red, starved:** with a cap of 1 s, the step goes red with every target's count and the load.
- **Fuzz mutants, 3 of 3 red each:**
  - a row of 0 runs: refused;
  - the script giving `-runs=0`: SHORT, 2 of N;
  - the script ignoring the table: OVER on every target.
- **Lane copy, killed mid-copy:** TERM removes the unfinished copy (exit 143). KILL leaves it, and
  the next fetch step removes it.
  - Fail-before: the script before this change left it behind on TERM.
  - In the gate: a planted `.new.<pid>` with a dead pid is removed by the gate's fetch step.
- **The gate's wrappers' self-test** checks each lane's line ("started at … ended at …", red or
  green) and the wait's. Without the line it fails 3 of 3. A first gate (i142a) went red there:
  the self-test takes gate.sh's functions one by one and lacked the new `seconds_since`, so
  every lane died, status 127. It now takes it.
- **One gate:** it passed with every lane run in full, since gate.sh changed.

## Not covered

- Fuzzing one seed twice does not reach the same coverage. With libFuzzer's compare tables off,
  all 12 targets would cover the same each time, but the planted crash was not found. A crash
  is what must be reproduced exactly, and its saved input does that.
- Fuzzing does not run on CI, which has no nightly toolchain.
