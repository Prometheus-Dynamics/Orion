## Built

`crates/node/assembly` (`orion-assembly`): `run_node(path)`, `settings(source)`, and
`run_until` passed on from `orion-node-app`, which is where the parts are joined as each was
built (E3 onwards). The assembly adds reading the shared settings file, telling node logic's
unread keys from the comm core's, and the feature `pull`.

## Proved by

`tests/all.rs`: one node logic, started from a settings file as text (with the comm core's
keys in it), against one real comm core, with programs on five other sessions.

- **Records**: a put is stored and a watcher is told.
- **Resources**: a camera driver describes a camera with a label, a topic and an action; it
  is listed with them; it is bound by a lease.
- **Actions**: the camera's action is run by another program through the check and done by
  the driver.
- **Files**: one is pushed and is in place; one is fetched from a local HTTP server and is in
  place; one for `slots/` is handed whole to a receiver and the node keeps none of it.
- **Workloads**: the sample executor runs a workload that needs the pushed file, as a real
  process.
- **Audit**: the log has lines for the put, the registration, the run, the file, the commit
  and the workload.
- **Again after a restart**: node logic is stopped as the service manager stops it and
  started from the same file. The records and the lease are there; the camera's action runs
  without its driver having done anything; the workload is the same process, not started a
  second time; the receiver still receives.

A second test: of the comm core's keys, a typo under `records.` and good keys, only the typo
is reported; a value that is not one is an error naming its key. 40 runs in a row pass.

## Not done here, and where it belongs

The briefs for E8 and E9 said their wiring was E18's. It is not in this commit, and it is not
node logic's alone:

- **Peer sync on real connections** (done in E19). `orion-sync` needs to be told when a peer is there and
  to be handed its frames. Node logic could dial peers itself as E11 does for actions, but a
  node behind another's firewall would then never be reached, and the comm core is where
  connections belong (F1 and the outbound part of group F make them). What is needed here
  when they exist: relay routes for `PEER_SYNC` and `PEER_OBSERVED` for peers only,
  `peer_up`/`peer_down` from the comm core, and `agreed_at` saved in the state directory.
- **Placement.** Needs peer sync's liveness, each node's executor kinds in its observed
  slice, and a record class for "this workload is mine". Until then a workload runs where it
  was put or where it names.
- **Telling the service manager** node logic is ready: it has nothing that listens.
