## Built

- **`orion/state` always ends with `panics contained: N`:** how many requests have made a
  service panic since the comm core started. Each cost its own session and no other. It is
  said when it is zero too, so a board can be asked whether containment has ever fired.
  The topic `orion.comm` already has the same count as its field `panics`; this is where a
  person reading the board's state sees it, in recovery as well.
- `Sessions::panics`, which a service can read while it answers.

## Which lints forbid a panic in a handler

None. The workspace forbids `unsafe_code`, and denies `await_holding_lock`, `dbg_macro`, `todo`
and `unimplemented`. Nothing denies `unwrap`, `expect`, indexing or slicing
(`clippy::unwrap_used`, `expect_used`, `indexing_slicing`).

What is there today, outside tests, counted with grep, not read one by one:

| Where | `.unwrap()` | `.expect(` |
| --- | --- | --- |
| `crates/comm`, the comm core and its parts | 16 | 108 |
| `crates/node`, node logic | 0 | 18 |

Indexing and slicing were not counted. Turning the lints on would be a row of its own: each
of these read, and made an error or shown not to be reachable.

## panic = "abort": measured, and not taken

The service profile with only the panic setting changed, against I86:

| File | Unwinding (today) | Abort | Saved |
| --- | --- | --- | --- |
| `orion` for a board | 5,509,224 | 4,633,160 | 876,064 (15.9%) |
| `orion-recovery` for a board | 2,762,480 | 2,369,792 | 392,688 (14.2%) |
| `liborion_c.so` | 736,296 | 707,944 | 28,352 (3.9%) |

What relies on unwinding:

1. **The comm core's request boundary** (`orion_supervise::contain`, in `orion-server`). A
   request that makes a service panic drops that one session, and every other goes on.
2. **Every task.** The runtime catches a panic in a task, and only that task ends: the
   responder, the time sync, a link's carrier, the SSH way in.
3. **The C library's boundary.** A panic never crosses into the C caller.
4. **Helper threads whose join is checked**, as the roots' digest helper.

Under abort, any of these ends the whole process. The service manager starts it again after a
second, and every session, shell and transfer in flight is lost. With security off, which
means fully open, anyone on the network could send the one request that does it. That is why
it is not taken, for `orion` on a board or the C library. It is not to be asked again without
something new: a count above zero on real boards would be an argument for keeping it, and
handlers shown unable to panic would be the argument for abort.

## What is in orion-recovery, and what could come out

`orion-recovery` for a board is 2,765,480 bytes against a limit of 2,770,000: 4,520 left. The
next change that reaches recovery will need a raise or a cut. This is so that it is a choice.

By section, the board's file:

| Section | Bytes | Share |

What could come out. None of these was built and measured: they are where to look.

| Candidate | About | What it costs |
| --- | --- | --- |
| SFTP in recovery (`russh_sftp`, the `ssh-sftp` feature) | 77 KiB of code | recovery takes files only through Orion's own file service, not `sftp` |
| Key types other than ed25519 (`num_bigint`, `p521`, part of `ssh_key`) | 47 KiB and more | a recovery key must be ed25519; whether the SSH library can be built without them was not checked |
| Port forwarding in recovery (the `ssh-forward` feature) | not measured | no tunnel through a board in recovery |
| Unwinding (panic = "abort") | 392,688 bytes, measured | a panic in recovery ends recovery, which the service manager starts again |

The last one is a different question for recovery than for `orion`: recovery has one job and
few sessions, and nothing ships it today. If recovery is to be carried by an image, abort for
recovery alone is the large cut, and worth deciding then.
