## Build

- Pending until an executor offers the kind.
- If Orion restarts, adopt runs by name from the executor's inventory.
- If an executor restarts with nothing, restart its workloads.
- An unreachable executor marks records Lost.

## Proof

Restart each side in turn with a sample executor.

## Built

- `crates/node/executors` (`orion-executors`): `Workloads` over E4's tracker, with
  `restored`, `request`, `gone`, `tick`, `forget_sessions`.
- One kind with a vector, `EXECUTOR_ASK` `0x5E`, and a record class `Workload` (4). Nothing
  recorded before changed.
- `orion-executor` (client): an ask is answered on the next turn with the whole inventory.
- `orion-relay` routes the workload and executor kinds; `ExecutorOffer` stands.
- `orion-workloads` (E4): an inventory from an executor that never went away no longer counts
  a run it does not list as lost with the executor. Only a run that was `Lost` is.
- `orion-node-app` answers the kinds, starts due restarts, and audits puts and removes.

## Proved by

- `crates/node/node-app/tests/workloads.rs`, with the sample executor (I3) running real
  commands against a real comm core:
  - A workload is `Pending` with no executor; the executor comes and it runs, once.
  - **Orion restarts**: the process keeps running while node logic is dead; afterwards the
    workload is `Running` and it is the same process, never started a second time.
  - **The executor restarts with nothing**: the workload is `Lost` while it is away, then
    started again, once, as a new process.
  - Removed, the process ends, the status is `Gone`, the record goes, and it does not come
    back after another restart of Orion.
  - A command that exits 3 is started again under "on failure" and left alone under "never";
    one that ends well under "never" is `Gone`.
  40 runs in a row pass.
- `crates/node/executors/tests/executors.rs`, 7 tests: put, start with kind, spec and CPUs,
  who is told; remove and forced remove; adoption and strays; one executor a kind; a workload
  for another node; what should run after a restart.

## Different from the brief

- "If Orion restarts, adopt runs by name from the executor's inventory": an executor sends its
  inventory once, when it connects, and its later reports went to the Orion that is gone. So
  Orion has to ask, and the wire had no way to: `EXECUTOR_ASK` was added.
- Workloads needed somewhere to be kept across a restart and shared between nodes. They are
  records, which needed a class.
