# E19: Peer sync on connections

**Status:** done

**Group:** E. Node logic

**Wave:** 13

**Needs:** E8, E11, E18

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Creates

`crates/node/dial`, `crates/node/peer-links`

## Build

E18 left peer sync unwired: `orion-sync` is plain data and needs to be told when a peer is
there and to be handed its frames.

- The comm core passes `PeerSync` and `PeerObserved` from peers, and only from peers, to node
  logic, as it does records.
- Node logic connects to every other node its node records give an address for, as E11 does
  for a forwarded run: with the node's key, asking the other node to prove it holds the key
  pinned for it. Frames for a peer go on that session, or, with none, on the session the peer
  connected with: one side being able to reach the other is enough.
- A helper thread for each node holds the session and wakes node logic when something came;
  nothing is polled.
- When each peer was last agreed with is kept in the state directory across a restart.

## Proof

Two nodes, real comm cores and node logic: a record put on one is on the other; one that
only the other can reach still syncs; a change made while one was away arrives when it is
back.

## Built

- `orion-dial`: a session to another node as this one: the node's key from `keys.dir`, and
  the key the trust file pins for that node asked for. With security on, a node with no pin
  is not connected to. `orion-action-forward` uses it too.
- `orion-peer-links`: a helper thread for each node the records give an address for. It
  holds the session, connects again a second and then up to thirty apart, and passes on
  `PeerSync`, `PeerObserved` and `NodeBack`. Frames to send go to it over a channel and a
  socket pair rings it; what it heard comes back the same way, and node logic waits on its
  bell beside the comm core's session. A helper with nothing to do wakes once a second.
- `orion-relay`: `SYNC` routes. `PeerSync` and `PeerObserved` are passed to node logic from
  peers only.
- `orion-node-app` `peers.rs`: `orion-sync` told when a peer is up (its link is up, or it
  sent something on a session it made here) and down (neither), handed both ways' frames,
  told what changed in the store (`Records::take_for_sync`), and ticked for what is held
  back. Frames for a peer go on this node's link when it is up and otherwise on the peer's
  session. `sync-agreed` in the state directory keeps when each peer was last agreed with.

## Proved by

`crates/node/node-app/tests/sync.rs`, two nodes with real comm cores, security on, and their
own node logic:

- Only the left node has an address for the right one. A record put on the left reaches the
  right, and one put on the right reaches the left over the session the left made.
- The right node is stopped, a record is put on the left, and the right is started again on
  the same port with what it kept: the record arrives, and what it had is still there. The
  left node has written when it agreed with the right.
- A left node that pins another key for the right one does not sync with it.
- With the relay's `SYNC` routes taken out, the first test fails at its first check.

## Different from the brief and from E18's note

- E18 said connections were the comm core's to make. Node logic makes them here, as it does
  for a forwarded run: the comm core has no session of its own to another node that carries
  node logic's frames, and a peer behind a firewall is still reached, since frames go back
  on whichever session is up.
- Placement is still not wired: it needs each node's executor kinds in its observed slice and
  a record class for "this workload is mine". It is its own PR.
- `forgive` for a stale peer has no request yet: a stale peer is logged and stays stale.
  E21 adds it.
