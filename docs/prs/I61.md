## Fault

The executor signalled only the shell it started, by its process id. A child the shell had
started, such as `sleep 300 &` in a command that then waits, was never signalled. It ran on
after a stop, after a kill, and after the executor itself ended.

## Built

- **Each command runs in a process group of its own,** led by its shell
  (`Command::process_group(0)`). This is the standard library's call, so no new `unsafe` is
  needed.
- **Stop, kill, a start again under the same name, and the executor's end** each send their
  signal to that group (`kill_process_group`), and only to it. The number of the group is that
  of the shell, which the executor still holds unreaped, so it cannot be another process's
  number.
- A child that leaves the group by its own choice (`setsid`, `setpgid`) is not followed. Nothing
  else is signalled.

## Proof

- **New test:** `a_command_stopped_killed_or_left_behind_takes_its_shells_children_with_it`.
  - The command `sleep 300 & …; wait` is stopped, then killed, then left to an executor that is
    dropped.
  - Each time, the shell and its child are both gone.
- **Before:** with the executor as it was at `4f332493`, the test fails 3 of 3. The stopped
  command's child is still there after 10 s.
- The six existing tests pass unchanged.
