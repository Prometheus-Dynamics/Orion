# C64: A buffer pool of another layout is said as one, with both layouts

- **Status:** done
- **Group:** C (client)
- **Wave:** 19
- **Needs:** the device library's M34 pin (`e9224a53`)

## Why

C32a left this waiting on the device library: its pool page had no layout word, so a pool
from a publisher of another device library could only be refused as memory that is not a
pool page. M34 gave the pool page a layout word, checked first, and the pin moved to it. A
subscriber should now be told it is a layout, with both numbers, as it is told of a ring, so a
tool can say which side to update.

## Changes

- None in the client's code: the pool's attach already went through `from_ring`, which keeps a
  layout as `ClientError::Layout`. What was missing was the proof.
- `orion-buffers` test `old_pool.rs`: the stand-in comm core hands over either a ring's memory
  (not a pool page at all) or a real pool page of layout 1, written with the device library's
  own `sealed_memfd` and `WriteMap`.
- `docs/ring.md`: the pool page table has the layout word at word 1 (generation and buffers
  move to word 2), and says what a subscriber is told.

## Proved by

- `a_pool_page_of_another_layout_is_said_as_one_with_both_layouts`: `ClientError::Layout`,
  "a buffer pool", found 1, reads 2.
- `a_pool_this_build_does_not_read_is_said_with_the_shared_memory_crates_words`, kept: memory
  that is not a pool page is `ClientError::Memory`, "not a pool page".
- Not vacuous: with the pool's attach error given as `Memory` whatever it is, the layout test
  fails.
