`crates/node/executors/src/place.rs`

## Build

E19 carries the records between nodes; nothing yet decides which node runs a workload that
names none, and a workload record that arrives by sync is not looked at until a restart.

- Node logic looks at the workload records whenever one changes, however it changed: a
  workload that is this node's to run is started, one that no longer is goes.
- Each node observes its own node record, with the kinds its executors run, so the others
  know what it can run.
- A workload that names no node is run by the node `orion-placement` chooses from the node
  records, the observed slices and which peers are up. That node says so by observing the
  workload; the others see whose slice has it.

## Proof

Two nodes, one with an executor: a workload put on the other runs on it. The executor goes
and comes back on the other node: after the grace period the workload moves.

## Built

- `orion-executors` `place.rs`: the view from the store (live nodes are those that observe
  their own node record, which lists their executor kinds under `orion.kind`; desired node
  labels over reported ones; `orion.schedulable`; resource hosts), the owner of a workload
  (whose slice has it; one that can still run it first), and `Workloads::place`, which steps
  `orion-placement`'s coordinator for each workload, observes the ones this node takes, lets
  go of the ones another node has (their records stay), puts the ones that are this node's,
  and ends the runs whose records are gone.
- A put of a workload that names no node is placed at once and answered with where it runs.
- A workload let go here, or one that names another node, no longer has its record deleted
  when its run ends. Before, putting a running workload again for another node deleted it.
- `orion-node-app`: placement runs when a node, workload or resource record changes (from
  any node), an executor comes or goes, or a grace period ends.
  `workloads.placement_grace_ms`.

## Proved by

`crates/node/node-app/tests/placement.rs`, two nodes with real comm cores, security on, node
logic and the sample executor, grace one second:

- Only the right node has an executor. A workload put on the left node runs on the right, once,
  and not on the left.
- The right node's executor goes and the left node gets one: the workload runs on the left,
  started a second time, the run on the right ended, and it stays: not started again, its
  record still there.
- With the claim left out, the test fails at "it runs on the right node".
- The single-node workload tests and the executor bench pass unchanged.

## Different from the brief

- No new record class for "this workload is mine": the owner observes the workload, and
  observed slices already go when the node does.
- A node's kinds are labels on its observed node record, not a field of their own.
