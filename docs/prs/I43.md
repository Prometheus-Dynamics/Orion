## Fault

I31 left a gap. When a gift's source failed mid-transfer (`self.source.read(..)?` in
`Gift::step_once`, or a source that ended before its size), `Gift::step` marked the gift over
and dropped the transfer, but sent nothing. `stop`, `abort` and the drop all return early on a
gift that is over. So the client's fetch never heard why, and waited for the silence limit,
the case I31 was for.

## Built

When the source fails, `Gift::step` sends `FileTaken { Aborted }` first. That covers a read
error and a source that ends before its size. The fetch ends at once with "the program that
offers it stopped giving it: it could not be read: <the error>". The step still returns the
read's error, whether or not the telling got through. If the connection broke too, the next
call says so.

Nothing is sent for other errors:
- a broken connection, where there is no one to tell. Each step takes in what came first, so
  a connection already broken fails there, before the source is read.
- the client's silence, which has already ended its fetch.

## Proof

`crates/comm/file-offers/tests/abort.rs`, with a real comm core:

- `a_gift_whose_file_cannot_be_read_ends_the_fetch_at_once_saying_so`: a 4 MiB source whose
  third read fails. The fetch ends `Aborted` with the read's words, under 1 s after the
  program's step failed. The program's step returns that error. With the `offer.rs` from before
  it fails 3 of 3: the fetch is not over in 10 s.
- `a_gift_whose_connection_broke_says_so_and_never_reads_on`: the comm core stops mid-gift.
  The step returns the connection's error (`Io` or `Lost`), not the file's, and reads at most
  the one chunk it was sending. After that the gift is over: a further step says so, and
  neither it nor the drop reads again.
