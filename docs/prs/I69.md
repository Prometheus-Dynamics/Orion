## Why

A push through `TestBoard::hold_commits` sometimes never had a chunk acknowledged. The test
receiver was not the cause; a real receiver, or a push to the node's own store, hits it too.

- **The window was too big.** A push kept eight chunks of 32 KiB on their way, about 262,400
  bytes with their envelopes.
- **The outbox it has to fit in.** The comm core passes each chunk to node logic as a frame that
  must be sent, and node logic passes it to the receiver the same way. Each of those sessions
  has a 256 KiB outbox (`comm.outbox_bytes`, 262,144 bytes).
- **What a full outbox does.** A frame that must be sent and does not fit drops the session. So
  whenever node logic was slow to read for the length of one window, the comm core dropped node
  logic itself, and with it every transfer it was passing. The log said `session node … dropped:
  it was not reading: a frame of kind 0x0c and 32804 bytes did not fit, with 229626 of 262144
  bytes waiting`. The push then went nowhere until its bound.
- **Since when.** The window has been eight since D6, so every shipped revision has this,
  `d4010a45` included.

The lasting fix, where the sender is paced instead of a third party dropped, is its own row
(I70). This one makes one sender fit and the drop visible.

Separately, a consumer wants to bound a device call made while a commit is held. That needs an
action whose runs are never answered while the board goes on answering the caller.

## Built

- **The window is six chunks.** That is 6 × (32 KiB + 64) = 196,992 bytes. A compile-time
  check in the files client holds a window and one more chunk under
  `orion_wire::OUTBOX_BYTES`, the comm core's default outbox, which `Limits::default` now
  uses. Eight no longer compiles. `docs/client.md` and `docs/comm.md` say why it is six, and
  that a board with `comm.outbox_bytes` set below that loses pushes.
- **The drop names whose traffic filled it.** When the relay cannot pass a request to node
  logic because node logic's outbox is full, it warns:

  > node logic was not reading: a request of kind 0x… from session NAME (N) did not fit in its
  > outbox, so node logic is dropped and what it was passing is forgotten

  This comes on top of the comm core's own warning that the session was dropped.
- **`TestBoard::hold_action(name, target) -> HeldAction`.**
  - A thread registers the action through the real `register_action`, retrying while node
    logic is starting.
  - It takes every run it is handed and answers none, while it goes on pumping its session.
  - `asked()` counts the runs it has been handed.
  - Dropping it ends the program, and node logic ends each open run as failed, "the program that
    runs it went away".
  - `docs/testing.md` has a section on it.
  - The crate is still test support only.

## Proof

- **`pushes_through_node_logic_to_a_receiver_all_commit`** (`tests/board.rs`):
  - **What it does.** Twenty pushes, cycling 100 kB, 1 MB and 4 MB, each on its own session
    under the client's defaults, to `hold_commits("slots/", 300 ms)`.
  - **What it checks.** Every push commits, and the receiver answered 20. The whole run is
    bounded at 60 s.
  - **It passes 3 of 3**, in about 10 s each.
  - **Mutation:** the window back to eight, with the check removed. Every one of 7 runs failed,
    almost always at the first 1 MB push ("timed out with 0 bytes there"). One run failed at
    0.43 s with a message that was not captured, and it did not come back in 5 more runs.
  - The repro before the fix stalled 3–5 of 12 pushes per run.
- **`an_action_left_unanswered_stays_open_while_the_board_answers`:**
  - **What it does.** A caller runs `arm.call`.
  - **What it checks.** For 2 s the run is told nothing, while `node()` keeps answering.
    `asked()` is 1. Once the held action is dropped, the run ends `Failed` with "the program
    that runs it went away".
  - **It passes 3 of 3**, in about 2.2 s each.
  - **Mutation:** the program finishes each run as it gets it. All 3 runs failed with "an
    unanswered run was told Finished".
- **The relay's warning has no test, and I have not seen it in a run.** It is a log line on a
  path the loop test reaches only with the mutation, and the test does not collect logs. It
  compiles, and it is reached exactly where the comm core logs its own drop.
- **The landing gate passed.**
