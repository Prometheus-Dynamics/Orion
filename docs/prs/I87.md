## Why

A file pushed to a destination that a program on the board receives, sent before that program
had asked for its prefix, was taken by the node's own store and answered as committed. The
sender believed the device had the file. The device had nothing, and refused the next step.
It happened right after a board started, and after the receiving program restarted.

Nothing bounded what the store took: any destination no receiver held was the store's.

## Built

- **`files.receivers`**, a list of prefixes the image says are receivers'. The node's store
  never takes a file under one. Empty by default, which is how it was.
- **Begun with no receiver there:** refused `Unavailable`, with words: `nothing receives
  <destination> yet: <prefix> is a receiver's`. This is the code a board already gives while
  node logic is away, so it already means "not yet".
- **Still on its way to a receiver that went:** a chunk or commit of such a transfer is
  refused `Unavailable`, `the program that received it went away: begin it again`, where it
  used to fall through to the store. The sender is still told the transfer is rejected when
  the receiver goes, as before. So a push in the middle ends there, with those words, and the
  next push waits for the receiver.
- **The push asks again.** A `FileBegin` refused `Unavailable` is sent again a few times a second, for
  up to twelve timeouts (60 s by default) from the first refusal. This also covers a push that
  begins while node logic is starting.
- **When the time runs out** the push ends refused, still `Unavailable`: `nothing received
  <prefix> within <bound>`. It is not a lost connection (`is_lost()` is false), so a program
  can say the board's receiver never came up.
- **Roots are not affected.** A root comes from the settings, so node logic knows it before it
  takes a request, and a destination under `roots/` is tried as a root before anything else. A
  test now pins it: a push to a root begun before node logic runs lands in the root.

## Not built

A push in the middle of a transfer does not carry on by itself across its receiver restarting:
it ends rejected, and is pushed again. Carrying on would mean a push that outlives a
`Rejected` status, which is a larger change to the push. Say if it is wanted.

## Tests

- `orion-files-sink`:
  - `a_file_for_a_receiver_that_is_not_there_is_refused_in_words_and_never_the_stores`.
  - `what_is_still_on_its_way_to_a_receiver_that_went_is_refused_until_it_is_begun_again`, which
    also shows that without the setting such a transfer starts over in the store, as before.
- `orion-node-app` `sink::the_receivers_prefixes_are_read_and_one_that_is_not_a_prefix_is_refused`.
- `orion-test-board` (`receivers::`), through the real comm core, node logic and client:
  - `a_file_pushed_before_its_receiver_is_there_waits_for_it_and_is_never_stored`: the push is
    still waiting after 600 ms with nothing in the store; the receiver starts; the push commits
    and the receiver has it; nothing is in the store. A destination the image did not name is
    stored as ever.
  - `a_push_whose_receiver_never_comes_ends_saying_nothing_received_it`: after the bound,
    `nothing received held/ within 3s`, `Unavailable`, not lost, busy or held.
  - `a_file_pushed_to_a_root_while_node_logic_is_starting_lands_in_the_root`.

Six mutants each failed 3 of 3 runs: the refusal at begin removed, the refusal of what was on
its way removed, the words dropped on their way out of node logic, the push not asking again,
the push ending with the board's last words and not its own, and the setting not reaching the
receivers.
