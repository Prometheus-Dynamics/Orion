# C56: The microcontroller side hears what a host program hears

- **Status:** done
- **Group:** C (actions, device)
- **Wave:** 18
- **Needs:** C54

## Changes

- `orion-device-actions`: `Heard::Run` gains `detached`, read from `Claim`'s appended byte. It is false from a host that doesn't send it.
- MCU template C API (`orion_mcu.h`, `src/ffi/runs.rs`, new, split out to keep `mod.rs` under 800 lines):
  - `ORION_EVENT_CALLER_GONE` and `orion_caller_gone()`. Four ended sessions are held, oldest first; once more end than that, the newest are kept. Each is said once.
  - `orion_run_detail(session, deadline_ms, detached)` describes the run `orion_run` last handed over.
  - `orion_cancel_reason()` with `ORION_CANCEL_ASKED`, `_CALLER_GONE`, `_DEADLINE` and `_STOPPING`. A deadline cancel is the run whose caller was told code 110.
- `docs/lock.md`: entries for C52–C56, which consumers read for what changed since the lock.

The API version is not raised, as on dev.

## Proved by

- `orion-device-actions`: `a_detached_run_says_so`; the existing run test pins `detached: false`.
- MCU template `tests/ffi.rs` (UART):
  - `orion_run_detail` is `ORION_ERR_STATE` before any run, then gives (9, 2000, true);
  - the cancel reason is Asked, then Deadline;
  - five sessions gone become [2, 3, 4, 5], then 0, and the event clears.
- `tests/header.rs`: the header declares every new export and value.
- Mutations, each failing:
  - the device reading `detached` as false;
  - the reason not kept;
  - the queue not dropping its oldest;
  - `orion_run` not recording the taken run.

## Different from the brief

"110 and run handles wherever the MCU and C clients lack them": neither applies there. A device runs actions but never calls one, so it never holds a handle or reads a result code. What it can hear is a deadline's cancel, which `ORION_CANCEL_DEADLINE` now says. The host C library has no actions at all.
