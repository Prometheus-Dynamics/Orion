## Why

Three small things from programs that use Orion.

1. **Directories.** A root shared by an application and Orion is the group's: setgid, `2770`,
   with the unit's `UMask=0007`. A pushed file landed `0660`, which is right. A directory Orion
   made was asked for as `0755`, so `0750` under that umask. The application could enter it
   but not make a file in it.
2. **Busy.** A client that asks again on `Busy` asked again for refusals that waiting does not
   clear: a resource another holds, a prefix another offers. Only the words told them apart.
3. **A link with no address yet.** A way in kept to an interface listens before the interface
   has an address. That worked, and no test pinned it.

## Built

- **Directories are made as files are:** asked for with every permission (`0777`), so the
  process's umask is the one rule for both. I chose this over copying the root's own mode: a
  file's mode already comes from the umask, and two rules for one tree would let them disagree.
  Setgid still comes from the parent, as the kernel does it. This is in both places Orion
  makes a directory: `files.mkdir`, and the directories on the way to a pushed file.
- **`is_held()`** on `ClientError` and `orion::Error`: a `Busy` refusal with words of its own.
  **`is_busy()`** is now true only for a `Busy` refusal with none (its detail is `busy`), which
  is what its doc always said: the same request asked again later may be taken. No code and no
  refusal changed on the board. What each is today:
  - want of room (`is_busy`): a full outbox toward node logic, too many offers, fetches,
    standing requests or runs, no room for a topic. No words.
  - held (`is_held`): `<resource> is held by <holder> since <ms> ms: <why>`; `<prefix> is
    offered by <name> (<principal>)`; `<prefix> is under orion/, which the comm core offers`;
    and an enrollment behind 32 others waiting for an administrator.
  A push asks again on `is_busy` only, as before in effect: nothing it met was held.
- **The interfaces test** has a fourth interface, named in the settings, there and up with no
  address. The log says it was opened, and nothing else. When its address comes, both ways in
  take a connection within 500 ms.

## Tests

- `orion-test-board` `modes::what_is_made_in_a_root_the_group_shares_is_the_groups_to_write`. It
  runs itself again as a child with umask `0007` (a umask is the whole process's), in a root
  that is setgid `2770`:
  - a directory from `files.mkdir` is `2770`;
  - the directories on the way to a pushed file are `2770`, and the file `0660`;
  - a file pushed into a directory made the application's way is `0660`.
- `orion-connect` `busy_is_never_lost_and_lost_is_never_busy`: a bare `Busy` is busy and not
  held; the two worded ones are held and not busy; a denial is neither.
- `orion-comm-app` `interfaces::each_interface_named_gets_a_listener_that_follows_it_when_it_is_made_again`:
  the interface with no address.

Four mutants each failed 3 of 3 runs: each of the two directory modes back at `0755`, `is_held`
inverted, and `is_busy` true for any words.

**Not covered:** two users. The tests run as one user, so they check the modes that let a
second user in the group write, not a second user writing. That is for a board: as the
application's user, make a file in a directory Orion made, and push into a directory the
application made. The listening test cannot be made to fail by a small change here: the
behaviour is I72's, and this pins it.
