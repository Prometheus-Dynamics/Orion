## Fault

A program that runs an action on hardware may lose its session while a detached run's job is
still under way: a link drops, or the program reconnects. Node logic ended each run of a gone
program at once as `Failed`. The job went on, its caller was told it failed, and the program,
back a moment later, had no run to report on.

## Built

- **Asked per action.** `Register` gains an appended `keep_ms: u32`, zero for not kept.
  `Actions::register_kept(decl, policy, keep)` sends it, and needs a node at level 6
  (`Feature::KeptRuns`): below it, it fails with `ClientError::Level` and sends nothing. Node
  logic caps the window at `MAX_KEEP_MS`, a minute.
- **Kept, not ended.** When the program's session is gone, each detached run of such an action
  it was doing is held for the program's identity. Its caller is told progress `restoring: …`.
  A cancel asked meanwhile is kept. A deadline does not end a held run: it waits for the program.
- **Given back.** A session of the same identity registering the action again is handed each
  held run before its registration is answered: a `Claim` with the appended `kept: true`, the
  same run number, no arguments and the deadline left. The caller is told `restored: …`. A kept
  cancel is passed on; a run whose deadline passed is told to stop at once, with the usual
  bound. Another identity registering the same name is handed nothing.
- **Not back in time.** The run ends `Indeterminate` (6), code 0, with the words "the program
  that runs it lost its session and did not come back within N ms, so how it ended is not
  known". A report on it after that is refused as `RunGone`: "run N already ended as
  indeterminate: …". Node logic stopping ends every held run `Indeterminate` at once.
- **The client keeps what it is handed.** `Actions::restore` cleared what it had been handed
  only after re-registering, which threw the kept `Claim`s away. It now clears first.
  `Registration::refused(call)` reads node logic's refusal of the program's finish of a run.

## Wire and shared memory

Wire: two appended fields, level 6. The recorded vectors change only by the appended bytes (the
old bytes are a prefix of the new). An older node ignores `keep_ms` and the client asks it of
none. An older program reads a `Claim` without `kept`. No shared-memory layout changes.

## Size

The board's `orion` (aarch64, static) grew by 9,016 bytes, to 5,331,680, over its limit of
5,330,000. Cut first, 1,320 bytes:

- the restoring and restored words go through the one function that passes a program's own
  progress on, in place of a copy of it;
- whether a run is kept is read from the listed actions in place, before they are dropped, in
  place of a list of copies made for it.

What is left (5,330,360, +7,696 over I54) is the feature: holding a run, giving it back,
ending it when its program does not come back, refusing a late report, and the two appended
fields. The limit goes to 5,360,000, the measured size and the usual margin rounded to 10,000,
in `scripts/size-gate.sh`.

## Proof

- **Node logic** (`crates/node/action-list/tests/kept.rs`, 7 tests): given back and ended as
  said; not back in time, then `Indeterminate` and the late report refused by name; another
  identity is handed nothing; a kept cancel; a deadline passed while kept; node logic stopping;
  a run not asked to be kept still ends `Failed`, and the window is capped. With `keep` made to
  keep nothing, all 7 fail, in 3 runs of 3.
- **End to end** (`crates/client/actions/tests/kept.rs`): through the stub board, the program
  registers kept, its session is replaced by `reconnect`, the caller is told `restoring`, the
  program calls `restore` and is handed the same run with `kept`, finishes it, and the caller
  gets `Succeeded` with its output. With `restore` clearing what it was handed after
  re-registering (as before), it fails, not handed the run again, in 3 runs of 3.
