# I124: Each program read once per process, and the video test says where a stream stopped

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I123

Read `AGENTS.md` and `docs/design.md` first.

## Why

CI went red twice in gate (main): the lane keys' self-test went past its 60 CPU-s bound, at
60.5 CPU-s on I121 (run 45979905635) and 60.2 on I123 (run 45982452854). I123 had blamed
process start-up. That was wrong.

The cause is on CI's runner, which has a Chromium of 533 MB under two names, `chromium` and
`chromium-browser`. Every `Keys` read both whole for its programs key, about 1.4 CPU-s a key.
The plan job alone spent 16 CPU-s on it, and the self-test about 64 in all. Locally there is
no such file, so it never showed.

Separately, a gate went red once on
`video_plays_in_a_browser_on_plain_http_over_a_throttled_link`. The page showed 41 JPEG
frames and 40 H.264 frames, with `h264Time` 4.0, and then nothing for 86 s. The page counts
missed frames only by gaps in sequence numbers, so a stream that stops dead reads as
`jpegMissed=0`. The test's message could not say which side had stopped.

## Changes

- **`program_digest`** in `scripts/lane-reuse.py` reads each program once per process. It keys
  the file as it stands, by real path, device, inode, size, and modify and change times. The
  programs key uses it.
- **The self-test reads every program before its workers fork,** so each worker starts with
  them read.
- **A new self-test case** rewrites a planted program in place, with the same inode and size
  and a later modify time. Its digest must change.
- **The video test records what its throttled link carried,** both ways, for each connection:
  the bytes, when the last byte passed, and how each way ended (who closed, or which read or
  write failed, and when). Every assertion prints that with the page's report.
- **The page's report adds** its JPEG and H.264 sample counts, the seconds since the last
  sample, when the client closed (`closedAt`), and how long it ran. Only the test changes; the
  shipped client does not.

## Proved by

- The mutant that keys a program by path, device, inode and size only (leaving out the times)
  went red 3 runs of 3: "a program rewritten where it stands kept its digest".
- On CI's runner (dispatch runs 45983540526 before the change, 45984130107 after it), three
  self-test runs each:

| Version | Wall | CPU-s | Most of it |
|---|---|---|---|
| Before | 29.6 s | 64 to 65 | plan 16.0, each case 1.8 to 2.0 |
| After | 5.8 to 6.1 s | 11.6 to 11.7 | setup 1.4, plan 1.5 |

## Open fault

The video stall is an open intermittent fault, about 1 in 96 runs, with its location not yet
known. It was not caught again in:

- CPU quotas on the browser (25%, 10%), the test process (25%, 10%, 5%), and both (10%, 5%);
- 50 runs of the test alone at load 36 to 119;
- 20 runs of the `orion-web-tests` package at load 63 to 86;
- 10 runs of the full tests step at load 74 to 106.

With both sides at 5%, the test timed out at a different place: not the same signature. The
link record above names where the stream stopped the next time the fault happens.
