## Built

- `examples/mcu-template`, standalone (its own `[workspace]`), on `crates/device`:
  - `UartPort<U>` over any `embedded-io` stream and `CanPort<C>` over any `embedded-can`
    controller (its two identifiers, frames for other devices ignored, a segment the
    mailboxes had no room for kept for the next pass). A Rust firmware's layers implement
    `App` (`handle`, `poll`).
  - The C API (`src/ffi/`), one static, no allocator, no lock (atomic loads and stores
    only, so Cortex-M0+ and RV32 without `A` build it): `orion_init`, `orion_topic` and
    `orion_action` tables fixed by the first `orion_poll`, `orion_rx`/`orion_tx` or
    `orion_can_rx`/`orion_can_tx`, `ORION_EVENT_*` bits, `orion_publish{,_int,_bool}`,
    `orion_subscribers`, `orion_run`/`orion_progress`/`orion_finish`/`orion_cancelled`,
    `orion_state`, `orion_api_version`, `orion_interface_revision`. With `ffi-slots`:
    `orion_firmware(prefix)`, `orion_firmware_confirm`, `orion_boot`, over six
    `orion_port_*` flash hooks the port defines.
  - `include/orion_mcu.h`, written by hand like `crates/client/capi/include/orion.h`.
- `scripts/mcu-template.sh`, run by the gate: fmt, clippy and tests for UART, CAN and slots,
  then a release build of each for thumbv6m, thumbv7em, riscv32imc and riscv32imac.
- `Topics::from_slice` and `Actions::from_slice`, for a table filled at run time; device-core
  re-exports `INTERFACE_REVISION`; `orion-device-host` reads a device's bytes (`Host::read`,
  `Host::welcome`, `Sent::of`).

## Proved by

- `tests/ports.rs`: a firmware with a topic and an action on `UartPort` and on `CanPort`
  (classic CAN, three mailboxes, another device's frames on the bus) against a host that
  reads every body with the general codec: declared, registered, publishing once someone
  listens, and a run answered.
- `tests/ffi.rs` (UART) and `tests/ffi_can.rs` (CAN): the C calls in a C firmware's order:
  bad arguments refused, tables fixed by the first poll, samples on the right handles, one
  frame at a time, a run with its arguments cut to the room given, a second run rejected at
  once, progress and result, a cancel, and starting over.
- `tests/slots.rs`: an image sent in chunks of the size the device asked for goes to slot 1,
  `ORION_EVENT_FIRMWARE` comes after the commit and not before, the bootloader starts it, and
  confirmed it stays.
- `tests/header.rs`: every `#define` equals the library's value, the header declares exactly
  what the library exports and the hooks it calls, and `tests/c/header.c` compiles with
  `-Wall -Wextra -Werror` for UART, CAN, and each with slots.
- Every configuration builds for all four targets. With every entry point kept and
  `--gc-sections`: 16,576 B flash and 2,048 B RAM on thumbv7em for UART (22,660 B with slots);
  no formatting code linked.

## Different from the brief

- Dev's template carried its own A/B slots, boot record, heap and firmware sink; here those are
  `crates/device/firmware`, and the template only wires them to the C hooks. No heap: nothing
  needs one.
- Dev published a provider snapshot (`orion_publish(resource, type, healthy)`) and counted
  leases. On the new wire a device is a resource made from what it declares, so the C API
  declares topics and registers actions instead, and publishes samples.
- The header is written by hand and tested against the library, rather than generated by
  cbindgen, as the C client's header is on next.
- With `ffi-slots`, every test binary would need the port's hooks, so the slots test runs alone
  (`--test slots`), as on dev.
