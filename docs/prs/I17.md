## Build

CI's `gate` job on `next` had failed on every push since 16 November, and from 9c096da on, on
one test:

`orion-ssh-sandbox` `sandbox.rs` `each_kind_of_session_holds_what_it_should_and_no_more`:
`orion: an SSH connection could not be served: bounding set: Operation not permitted`.

The gate on a worker's machine passes it. The test runs itself again in a user namespace of its
own, as that namespace's root, and a connection's child there empties its bounding set. It first
asks whether such a namespace can be made (`unshare --map-auto --map-root-user true`), and skips,
saying so, where one cannot.

GitHub's runners are Ubuntu 24.04. There AppArmor (`kernel.apparmor_restrict_unprivileged_userns`)
lets an unconfined program make the namespace, and gives its root no capabilities. The
namespace was made, so the test ran, and emptying the bounding set was refused.

A red gate job also never saves its cache (`rust-cache` saves on success), so every run since
started from the cache of the last green one.

## Built

- **CI lets the namespace hold capabilities**, setting that sysctl to 0 on the runner before the
  gate. The test runs there in full, as on a worker's machine.
- **The test asks what it needs.** Where `setpriv` is installed, it also asks whether root in such
  a namespace can empty its bounding set
  (`unshare --map-auto --map-root-user setpriv --bounding-set -all true`). Where it cannot, the
  test says so and skips, as where no namespace can be made.
- **CI runs the tests with cargo-nextest** (`taiki-e/install-action`), as the gate does on a
  worker's machine where it is installed. Without it, `cargo test` ran the same cases one binary
  at a time.

## Proved by

- On this machine the test still runs in full: with its expectation of the inside run's words
  changed, it fails.
- With the capability probe made to fail (`setpriv … false`), the test says "a user namespace
  here holds no capabilities" and passes without running the check.
