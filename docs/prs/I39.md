## Why

The gate checked each of the 16 no_std crates alone, on each of two targets: 32 cargo calls,
one after the other. Each paid cargo's start and resolution, and none could build beside
another.

`cargo check -p A -p B` is not the same as two calls. It resolves features once, for the
whole graph, so a crate can be checked with features its own call never turns on. Here,
checked together, all 16 differ:
- `orion-check` gets `default,enforce` from the crates that use it, though alone it is checked
  with none;
- `orion-types` and `orion-check` build `syn`, `quote` and `proc-macro2` with `default` on.

## Built

- **Three groups per target**, found by trying each crate against each group:
  - `orion-types`, `orion-check`, `orion-supervise`;
  - twelve others;
  - `orion-device-actions`, alone.

  In each group every package each crate builds (normal and build dependencies) has exactly the
  features it has in that crate's own call. A no_std crate in no group is checked alone; a
  crate in a group that is not no_std fails the step.
- **`scripts/same-features.py`** compares, per target, each grouped crate's own resolution
  (`cargo tree -e normal,build`, every package and its features) with its group's, and fails
  naming each package that differs.
  - The answer depends only on the manifests, the lockfile, cargo, the flags, the targets and
    the groups. So a check that passed is stamped in the lane's target directory under a key
    over those, and made again only when one changes.
  - CI has no stamp and checks every time (13 s here).

## Proof

- **The check.**
  - The lane as written passed and stamped.
  - Run again, it read the stamp: 0 s, and the whole lane, warm, 8 s.
  - With all 16 crates in one group, the lane failed, naming `orion-check` (`[]` alone,
    `[default,enforce]` together), `orion-msg-actions`'s `orion-check`, and `orion-types`' and
    `orion-check`'s `syn`, `quote` and `proc-macro2`, on both targets.
