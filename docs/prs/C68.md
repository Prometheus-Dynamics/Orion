## Build

Ruled a bug, from a repro by the hardware manager:

1. Start a detached run.
2. Attach to it by handle while it runs.
3. Cancel it.
4. It ends, and the attached caller is told.
5. The first attach by handle after the end works.
6. A second attach by the same handle, from the same starter, is `not found`.

The first attach after the end took the kept end away. As ruled:

- An ended run stays attachable for a bounded time and count, stated in the docs.
- Every attach in that time gets the same end.
- After that, `not found` with a distinct "expired" reason, never mistaken for a run that never
  was.

## Built

- **Kept, not taken.** Attaching to an ended run reads its kept end and leaves it there. How
  long it is kept is unchanged: `ENDED_FOR_MS` (ten minutes) and `MAX_ENDED` (the newest 256).
- **Expired, said so.** An end that is no longer kept, by time or by count, is remembered as
  expired: its number, call and starter, for the last `MAX_EXPIRED` (1,024).
  - Coming back to one, by handle or by number, by its own starter, is refused `not found` with
    the words `expired: run N ended, and how it ended is kept for 10 minutes and for the newest
    256 runs; that has passed`.
  - Another starter, or a run that never was, gets `not found` with no words, as before.
- **Docs.** `docs/node.md` and the crate's module doc say every attach gets the same end while
  it is kept, and when it expires.

## Proved by

- **New `tests/ended.rs`.**
  - `every_attach_to_an_ended_run_hears_the_same_end_until_it_expires`: the repro's exact
    sequence.
    - Three attaches by handle after the end each hear `Cancelled` with the same run and code,
      and the end is still kept.
    - By number too.
    - Past `ENDED_FOR_MS`, both are refused `not found` with `expired:` words.
    - Another starter, and a number that never was, get `not found` with no words.
  - `the_oldest_end_expires_when_more_are_kept_than_the_limit`: past 256, the first is expired
    and said so.
- **Updated tests.** These said the end was handed back once; they now say it is handed back
  again, the same, and that the number never reaches an older run:
  - four assertions in `action-list`'s `handles.rs` and `list.rs`;
  - the client's `handles.rs`. Its test is renamed
    `a_cancel_by_an_ended_runs_handle_never_reaches_the_newer_run_under_its_number`, and it still
    proves by the owner's frame order that the cancel did not reach the newer run;
  - two tests in node logic's `actions.rs`.
- **Mutations.** `/mnt/nvme-wd/scratch/c68/mut.py` made 6, and all were caught:
  - the end taken by an attach, as before the fix;
  - no expiry record when the time runs out;
  - no expiry record when the count runs out;
  - expiry said to any starter;
  - expiry matched on any call;
  - the `expired:` words dropped.
