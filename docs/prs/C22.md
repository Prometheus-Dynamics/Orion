# C22: How long a session may go quiet, settable

**Status:** done

**Wave:** 18

**Runs:** cloud

## Build

A session was closed after three heartbeats of silence, and a client gave up on its comm core
after as long, with only the heartbeat settable. On a slow link, or in a test on a loaded machine,
a 4 MiB push could lose its session to a slow moment alone.

1. **`comm.idle_ms`**: how long a session may go unheard before it is closed. Zero, the default,
   is three heartbeats, as before; otherwise it must be at least two heartbeats.
2. **`Welcome.idle_ms`**, an appended field: the client waits as long for the comm core
   (`Welcomed::idle`). Zero, or a host that does not send it, is three heartbeats.
3. **The test core** takes both: `Board::start_with(dir, Options { heartbeat_ms, idle_ms, .. })`.
   `Options` also holds what the other `start_*` take; those are unchanged.

A device on a link keeps its own `missed_heartbeats` setting (`orion-device-core`); it does not
read `idle_ms`.

## Proved by

- `crates/comm/server/tests/server.rs`, `comm_idle_ms_sets_how_long_a_session_may_go_quiet`: with
  `idle_ms` 20 s, the welcome says so, a session quiet for 19 s is still there, and one quiet for
  20 s is closed. The default welcome says 6000.
- `crates/client/orion/tests/facade.rs`, `a_comm_core_set_to_wait_longer_is_waited_for_as_long`:
  a test core started with a 5 s heartbeat and 60 s idle gives a client those.
- The wire vector for `WELCOME` gains the field.

Also fixed: `a_program_s_own_ring_and_pool_become_a_buffer_topic` (C16) failed about one run in
thirty under load. Its read loop stopped at `Skipped`, so a reader that fell one frame behind
stayed behind: each round it was told of the frame it lost, and the publisher took that buffer
back before the next round. It now reads on past a skip; 100 runs of the file, none failed.
