## Why

A program that uses the board needs to test the case where node logic is stuck and the comm
core is alive. A request is passed to node logic and its answer never comes, while the caller's
pings are answered. Under a session-wide `Reply::Alive` with a long ceiling, such a request
waits that long unless the caller sets a shorter bound before it.

The comm core does not answer such a request itself:

- the relay passes a get on to node logic and keeps it as waiting, with no timer
  (`crates/comm/relay/src/lib.rs`, in `handle`);
- it refuses what is waiting only when node logic's session ends (`fail_waiting`, from
  `closed`);
- pings are answered by the server itself (`crates/comm/server/src/server.rs`, `kind::PING`).

So the case happens, and a test needs a way to make it. `TestBoard::hold_action` leaves a run
open, which is a different request with a different end.

## Built

- **`orion_node_app::slow::unanswered_gets(node) -> Arc<Unanswered>`**, in the `slow` feature
  (tests only; a dev-dependency of the test board, in no shipped build).
  - `hold(prefix)` makes node logic leave every record get whose prefix starts with `prefix`
    unanswered from then on, and `release()` ends that; those already left stay unanswered.
  - `asked()` counts those left.
  - Everything else node logic is passed is answered as before.
- **Node logic** looks at a request before it handles it, only with the feature: one passed
  get that is held is counted and dropped, as a node logic stuck on it would leave it.
- **`slow`'s settings** for a node are kept together, by its name: the delay and the held
  gets.
- **`docs/testing.md`** says how a consumer uses it.

## Proof

`a_get_node_logic_never_answers_ends_at_the_bound_under_timeout_and_waits_under_alive`
(`crates/testing/test-board/tests/board.rs`). It starts a board with a 500 ms heartbeat and
holds gets under `stuck`. Then:

- **Under `Reply::Timeout`** (400 ms), a held get ends with a timed-out `ClientError::Io`, at
  least 400 ms and under 2 s after it was asked. A get not held is answered on the same
  session.
- **Under `Reply::Alive`** (ceiling 60 s), a held get is still waiting after 3.2 s, eight
  bounds and more than the idle window, with only pings heard. Two gets have been left.
- **When node logic is stopped**, the waiting get is refused as unavailable.

It passes 3 of 3. Mutations, 3 runs each, every run failing, each test binary's hash checked:

| Mutation | Fails at |
|---|---|
| No get is ever held | under `Timeout`, the held get is answered: `Ok([])` |
| Every get is held, whatever its prefix | the get not held times out |
| A held get is not counted | `asked()` is 0, not 2 |

**The landing gate passed.**
