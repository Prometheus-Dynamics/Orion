# I113: The lanes start with the gate; a self-test of a tool runs when the tool changes

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I112

Read `AGENTS.md` and `docs/design.md` first.

## Why

The one-minute rule (2026-11-24). After I112, a change to a leaf crate took a 78 s gate at
load 159 to 120.

- **The main part ran 32 s of checks before any lane started.** They are checks that build
  nothing: the push guard's, the step bounds' and the boundaries' self-tests, the boundaries,
  the lockfile, the format. Their result rarely changes. The lanes, which build, waited for
  them.
- **The self-tests test the gate's own tools, not the code.** With the tool unchanged, the
  result is known: the push guard's took 5 s and the step bounds' 4 s, on every gate.

## Changes

- **The lanes start as soon as nothing can make their builds wrong**: after the target owner
  check and the lockfile check (a build not held to the lockfile could write it). The checks
  that build nothing are the main part's first steps, while the lanes build. One that fails
  still ends the gate and its lanes at once.
- **`once FILE... -- COMMAND`** runs COMMAND unless it passed before on exactly those files,
  that git and that Python. It keeps only a pass: a failure runs again next time. The push
  guard's, the step bounds' and the boundaries' self-tests run under it.

## Proved by

- **`once`**: a failing command ran again on its second call, its status kept; a passing one
  was not run on its second call; with a file changed, it ran.
- **The gate**, every lane run in full (the gate's own script changed): 121.6 s, 236 CPU-s,
  load 106 to 108.

Filled in at landing: the leaf and core changes' gates, with the load each ran under.
