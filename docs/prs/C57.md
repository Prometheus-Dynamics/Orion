# C57: A hello on a link always begins a session

- **Status:** done
- **Group:** C (comm, links)
- **Wave:** 19
- **Needs:** C54

## Why

A USB link did not come back after the host went away and came back. The board's side keeps a
link's session through the host going away, so the host's next hello came inside a session the
board still had. The server took a hello inside a session as out of turn: it closed the session
and dropped the frame. The carrier then waited for the next whole frame, and the host waited 30 s
for a welcome that never came. A serial device whose program restarts meets the same.

## Changes

- `orion-link-serial` `StreamCarrier`:
  - A hello, or a request for a signed session, that comes inside an open session on a link
    ends that session and is kept as the first frame of the next. It is not handed to the
    server as out of turn. This holds for unsigned sessions and for signed ones; a sealed frame
    is not a hello, so only an unsealed hello starts over.
  - Each connection on a link has a number, and only the newest writes. What an ended session
    still had to send fails as a broken pipe and never reaches the next session.
- `orion-server`: a frame that is not a hello, where a hello was due, is answered
  `Reject { NoSession }` before the connection closes. Before, it was closed without a word,
  and a far end that thought it had a session found out only at its own idle deadline.
- `orion-msg-session`: `RejectReason::NoSession` (6). It is an open enum, so older readers see
  an unknown reason, not an error.
- `orion-device-core`: a `Reject { NoSession }` in the middle of a session ends it, and hello
  starts again on the next poll, instead of three heartbeats later. Other reasons mid-session
  change nothing.
- `docs/comm.md`: the Links section, and the table of what happens to a misbehaving session.
- `examples/stm32g4-device/size-baseline.txt`: flash +112 to +120 bytes in each variant, the
  cost of a device reading a `Reject` mid-session. 30 bytes were won back by ending the session
  on the same branch as the heartbeat deadline.

## Proved by

- `orion-link-serial` `tests/pty.rs`:
  - `a_device_that_says_hello_inside_its_session_is_welcomed_to_the_next`: a new session on
    the same open port, and the old one gone;
  - `a_frame_where_a_hello_was_due_is_told_there_is_no_session`: a ping first is answered
    `NoSession`, then a hello works;
  - `what_an_ended_session_still_sends_never_reaches_the_next`: at the carrier, the old
    connection's write fails as a broken pipe and the device hears only the new one's.
- `orion-device-core` `tests/session.rs`: `a_host_with_no_session_for_it_is_told_hello_at_once`.
- `orion-connect` `tests/link.rs`: `a_link_plugged_in_again_says_hello_again_as_the_same_program`
  (added in C59) times out at 5 s without this change.
- Mutations, each failing: the old connection's writes not stopped (the late-frame test); the
  hello not kept for the next connection, with the `NoSession` answer off as well (the two pty
  tests did not end, and were stopped at the run's limit).
