## Why

Gap 6 of `docs/from-dev.md`: a `dev` program could ask which boards are on the network and
which of them are enrolled. On `next` nothing gave that to a client, and the shipped `orion`
heard no other board at all: discovery (`orion-discovery`, through the `mdns-sd` crate) is
not in its features. Turning it on costs 431,168 bytes, and its runtime enrolls by itself
when the keys hold an enrollment key.

The way chosen (option C): the responder that already announces the board listens for the
others on the same sockets, and the comm core says what it heard. Nothing connects to
anything and nothing is trusted because of it. Enrolling a board from the list (option B) is
not built: that is the user's to decide.

## Built

- **The browse** (`orion_mdns::Browser`, in the responder's loop, `orion_mdns::run`'s new
  `boards` argument). No socket, task or thread is added.
  - **Sends** one question, `_orion._tcp.local PTR`, to the group on each interface the
    board announces on: when the interface comes, once more 1 s later, then every 60 s and up
    to 2 s more. The answers go to the group, so a board that hears another ask the same of
    everyone puts its own question off a full interval. A quiet network of three boards
    carries about one question and three answers a minute: about 0.07 wakes a second for
    each board, beside the responder's look at the interfaces every 2 s.
  - **Why twice at the start:** a responder does not say again within a second what it just
    announced (RFC 6762 §6, as Orion's responder does). A board that came up in that second
    asked, was not answered, and waited a minute. The two-board test found it.
  - **Keeps** each board's SRV, TXT and its host's addresses, from what comes from port 5353
    and not from this board's own addresses. A board goes at its goodbye, or 150 s after it
    was last heard; an address 150 s after it was.
  - **Bounded:** 64 boards, 8 addresses each, a TXT record of 1,024 bytes. One more board is
    not kept, and is counted once for its announcement. Past the bound the newcomer loses,
    except that, with security on, a board announcing the key pinned for its name takes the
    place of the unknown board heard longest ago. Pinned boards do not evict each other. An
    announcement can copy a pinned board's name and key: this keeps pinned boards listed, and
    does not make the list true.
- **`orion/boards`**, a comm core own file, made when read: one line a board, by name, under
  a header line: `name addresses port key cluster state security clock trust heard_ms_ago`.
  `trust` is asked of the keys each time: with security on `enrolled`, `key-mismatch`,
  `revoked` or `discovered`; with security off `open`; before those `incompatible` (another
  wire) and `unreadable`. Boards of other clusters are listed with their cluster. Not offered
  where the board is not announced (`mdns = false`).
- **The watch is a topic, `orion.boards`**, fields `listed` and `changes`, published only when
  they change. It is not a hello fact: Orion's own facts are made when the document is asked
  for, and cannot be subscribed to.
- **Client:** `Orion::boards()` gives `orion::heard::HeardBoards` (with `Trust`);
  `orion node boards` prints the file as the board says it.
- **No wire change and no level bump.** A board without this answers the fetch `not found`.

## Found on the way, changed here

- **An own file held its bytes for 60 s**, so a fetch that broke off goes on with the same
  digest. `orion/boards` read when `orion.boards` moved could be a minute old: no watch.
  `OwnFiles::live(name)` (default false): a live file is made again by every fetch from the
  start; a fetch going on from where one broke off still gets the bytes it began with. Only
  `orion/boards` is live. `orion/state` and `orion/sessions` keep the hold, and
  `docs/comm.md` now says they can be up to 60 s old when read.
- **A responder's own announcements were told apart only by address.** The browse also takes
  only what comes from port 5353, as RFC 6762 says. It narrows what can put an entry in a
  list people will read as "the boards on my network".

## With security off, boards do not sync today

Asked before this was built: how does the first link between two boards happen in the
shipped build, and what do three cameras with security off need to see each other's records.
The answer, shown by `orion-test-board` `linking::with_security_off_a_board_dials_the_one_its_node_record_names_and_no_record_crosses`
(two real boards, security off, a Node record with the other's address on one): the first
dials, the second hears a session from nobody in particular and takes sync only from a peer,
so the first says `syncing` for good and no record crosses either way.

The test is pinned to what is true today, not to what should be. Whether boards with security
off should sync, and whether cameras on one machine should become one cluster at all, is the
user's to decide. Making it sync is 30 to 50 lines in the relay and node logic (not built).
`docs/node.md` says it as it is. So on a machine of several boards with security off, "the other cameras" comes
from this list in every case; records add to it only with security on and boards enrolled.

## Where enrolling from the list (B) would go

A backend for `orion-discovery`'s `DiscoveryBackend` that feeds it this browse, in place of
the `mdns-sd` one, and the `mdns-sd` dependency can go then. Not written: code nothing calls
does not sit in the tree.

not expect, in the gate's `--all-features` build only. `if-addrs` reads `fe80::` addresses

the shipped features; with the filter taken out, 3 of 3 fail with `--all-features`.
`docs/flakes.md` has the row.
