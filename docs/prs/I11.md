## Build

Make the gate faster without dropping a check: every check still runs and still fails on the
same faults. Measured per step on this tree first, on the PC that runs the gate, with other
repositories' gates running beside it (load 40 to 90 on 32 threads; the gate has 26 of them).
The four slowest steps ran one thing at a time:

- **tests:** `cargo test` runs one test binary after another; the binaries' own run time
  summed to about 240 s, while the longest one takes 25 s.
- **size gate:** nine fat-LTO builds, one after another, in one target directory. Each link is
  one thread.
- **feature matrix:** 108 `cargo check`s, one after another.
- **fuzz:** 12 targets, each 3 s, one after another.

## Built

- **Tests with cargo-nextest.** Where it is installed, `cargo nextest run --workspace
  --all-features` runs every case in a process of its own, all binaries at once. Then
  `cargo test --workspace --all-features --doc` runs the doctests, which nextest does not.
  Without nextest, `cargo test` runs them all, as before (GitHub's runner).
  - The same cases run: `cargo nextest list` gives 877. `cargo test -- --list` gives the same 877
    by name, plus two `#[ignore]`d tests that neither runs, plus 16 doctests, run by the second
    command.
  - No test leans on running in one process with another: no shared lock. Every temporary path
    or socket a test makes carries its process id, and no test takes a fixed port.
- **Size gate in lanes.** Each of the nine builds has a target directory of its own,
  `$CARGO_TARGET_DIR/size-gate/<build>`, and all nine run at once. Their lines are printed in
  the old order once all have ended. The sizes are the same bytes as the serial builds'.
- **Feature matrix in lanes.** Six lanes (`FEATURE_MATRIX_SHARDS`), each with its own target
  directory under `$CARGO_TARGET_DIR/feature-matrix/`. A build is always in the same lane, so
  each lane keeps what it built.
- **Fuzz targets together.** The targets are built once, then all 12 run at the same time, each
  for the same 3 s. One libFuzzer process is one thread. Runs per target are in the range they
  were (19,601–888,604 alone; 54,686–381,709 together, under load 46).

### A flake the parallel runs showed

`orion-ssh` `login.rs` `only_the_comm_cores_user_may_ask` failed 1 in 4 runs under nextest with
`send failed: Broken pipe`. It wanted the helper's refusal.

The login helper refuses an asker of another user from the kernel's word, before it reads the
question, and closes. The client sent its question after connecting. When the helper had
already closed, the send failed, and the client never read the refusal waiting for it.

- **Fixed.** A question whose send fails with a broken pipe, or a reset, still reads the answer
  the helper left. Only if there is none is the send's error given. Other send errors are given
  at once, as before. The send keeps the system error's kind, to tell these apart.

## Proved by

Seconds per step, before → after. Before is the C71 gate after a change to `orion-comm-app`.
After is the same change, under the same load range.

| Step | Before | After |
| --- | --- | --- |
| tests (warm, nothing to build) | 234 | 30 + 15 doctests |
| tests (in the C71 gate, with its build) | 195 | in the I11 gate |
| size gate | 380 | 49 (189 the first time, filling the nine directories) |
| feature matrix | 72 | 26 (167 the first time, filling the six directories) |
| fuzz | 73 | 6 |

Each step still fails on the faults it failed on before, by mutation, each restored after:

- **feature matrix:** a `compile_error!` under `costs` without `alloc-counter` in
  `orion-measure`. It exits 1 with `FAILED: cargo check -p orion-measure --no-default-features
  --features costs` and `108 builds, 1 failed`.
- **size gate:** the armv7 `orion` limit lowered to 5,000,000. It exits 1 with `FAIL: orion for a
  board (armv7-unknown-linux-musleabihf, static) is 5130416 bytes`.
- **fuzz:** the `time` target asserting on a first byte of `0x42`. It exits 1 with `fuzz target
  time failed`.
- **tests:** a wrong value in the `Crc32c` doctest exits 101, after nextest passed. A failing
  unit test in `orion-wire` exits 100.
- **login:** new unit test `a_refusal_sent_before_the_question_was_read_is_heard`. The helper's
  end answers and closes before the question is sent, the order that failed, every run. Without
  the fallback it fails.
