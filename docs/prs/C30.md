# C30: The comm core's own files, `orion/`, running and in recovery

- **Status:** done
- **Group:** C (comm core)
- **Wave:** 19
- **Needs:** D16b

## Why

A board in trouble is explained first by what Orion saw: its log, what it was told, what state
it is in and why, who is connected, and what build it is. A tool reached over the socket or a
USB cable should be able to take those without a login and without any program running, on a
board that is up and on one in recovery. Files from a board (D16) already carry a fetch, paced
and checked; the comm core now offers names of its own the same way.

## Changes

- **`orion_file_offers::OwnFiles`.** What the comm core offers itself: a prefix, its names
  (`OwnName { name, max_bytes, user_data }`) and how to read one now.
  `FileOffersService::with_own(files)` gives them:
  - `<prefix>index` is made from the names, in the index format of D16b, `total` the sum of the
    bounds;
  - each name is made at its first fetch, cut at its bound, and held for `SNAPSHOT_MS` (60 s),
    so a fetch that goes on gets the same bytes and its digest holds;
  - the comm core gives the chunks itself, in the same window the client paces; at most 64 at
    once; a name it does not have, or cannot read now, is rejected saying so;
  - no program may offer the prefix or one under it (`busy`, counted as a clash); the list of
    offers names it first, `OfferedBy::CommCore`.
- **The comm core's names** (`comm-app`, `own_files.rs`): `orion/log`, `orion/settings`,
  `orion/last-good.carriers`, `orion/state`, `orion/sessions`, `orion/version`, with bounds and
  user-data marks in `docs/comm.md`. Running and in recovery; recovery's state says why.
- **`orion_log` keeps a window** of its newest whole lines in memory, `log.window_bytes`
  (256 KiB; 0 keeps none).
- **`orion_config::Source::said`**: each setting that was set and where it came from, the value
  of one whose name may hold a secret left out (`may_be_secret`: the last part ends in `key`,
  or it says secret, password or token). `CommSettings::said` holds it from the start.
- `orion-recovery` is built with `offers`.

## Size

Both board files carry the files service and the names now; recovery did not have the service
before. aarch64, static: `orion-recovery` 2,692,720 bytes (+26,752 for the service and the
names, +11,728 for the log window, the settings text and what came since C52b), `orion`
5,271,120 (+20,952 since D16b). Tried first: the log window trimmed in one drain, not a line at a
time, and copied out as two slices; it saved nothing measurable. What is left is the service
itself (10 KiB of text in `orion_file_offers`) and the names. The limits go to 2,720,000 and
5,300,000: what was measured and the usual margin.

Measuring: build `orion-bin` and `orion-recovery-bin` in separate cargo runs, as the gate does.
One run unifies the comm core's features, and recovery measured that way is 3.5 MB.

## Proved by

- `orion-file-offers` tests (`tests/own.rs`, a stand-in `OwnFiles`):
  - the index reads with `orion_files::index::Index::parse`, with every name, bound and mark, and
    `total` their sum; the offers list names the prefix first, by the comm core;
  - a name larger than its bound is given whole to its bound, past the window, paced by the
    client; a name made from the sessions sees them;
  - a fetch broken off after five bytes goes on and gets the same file, its digest checked;
  - a name it does not have, and one that cannot be read, are rejected saying which;
  - a program offering `own/` or `own/deeper/` is refused naming the comm core, counted twice.
- `orion-comm-app` tests (`tests/own_files.rs`):
  - a running comm core: the index lists the six names with `orion/log` bound by
    `log.window_bytes`; `orion/settings` has `node.name` and `ssh.host_key = (left out)`, never
    the path; `orion/state` is `running`; `orion/sessions` names the collector; `orion/version`
    has the interface level and the kinds' digest; `orion/log` holds a line just logged;
  - recovery: `orion/state` says `recovery` and why; `orion/settings` leaves the key out;
    `orion/last-good.carriers` is the record; the comm core is first in the offers list.
- `orion-config` unit test: what was said leaves out every value that may be secret, from the
  file and the environment. `orion-log` unit test: the window keeps the newest whole lines.
- Not vacuous; each of these mutations fails a test:
  - bytes not held between fetches: the resume test (its digest no longer holds);
  - the bound not cut: the bound test;
  - a program let offer the comm core's prefix: the refusal test;
  - the client's answers not heard for own files: the bound test (it stops after a window);
  - the comm core listed as a program: the index test;
  - secrets not left out: both comm-app tests;
  - log lines not kept: the running comm-app test.
