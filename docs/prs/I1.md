## Proof

Both processes share code pages. All three modes work.

## Built

- `crates/bins/orion` (package `orion-bin`, binary `orion`): modes `comm`, `node` and `ctl`,
  picked by the first word or by the name it was started as (`orionctl`, `orion-comm`,
  `orion-node`). Anything else is the command line, and `node show|peers|time` stays the
  command line's. It answers as the comm core's helper programs first.
- Both services read one settings file and warn only about keys neither reads: each parses
  the file a second time as the other would and keeps the warnings both have.
- `comm` runs `run_or_recover`, so a broken settings file still opens the recovery way in.
- `crates/core/log` (`orion-log`): the one-line stderr log, moved out of `orion-recovery` so
  both binaries use it.
- `RecoverWith::from_env` in `orion-comm-app` reads `ORION_RECOVERY_KEYS` and
  `ORION_RECOVERY_LISTEN`, moved out of `orion-recovery`.
- `docs/comm.md`, "One binary: `orion`".

## Proved by

- `tests/modes.rs`: one settings file, `orion comm` and `orion node` started from it, then
  `orion --address ... node show`, `orion ctl ... resource list` and the same through an
  `orionctl` link all answer. Both services map their code from the same file (device and
  inode), so its pages are in the page cache once. Both stop cleanly on `SIGTERM`. An earlier
  version also asserted `Shared_Clean` above zero in `smaps`; on kernel 7.2 that count
  depends on how large folios are mapped and read 0 on one run, so it is not used.
- Unit tests: how a first word or a program name picks the mode, and that a key read by only
  one service is not reported as unknown by either.

## Different from the brief

- Nothing read on dev was kept: dev's node was one process with its own CLI parser. The modes
  call `orion_comm_app::run_or_recover`, `orion_node_app::run` and `orion_ctl::run`.
- How many pages are shared is not reported here: that is a board number, and I6 measures it.
