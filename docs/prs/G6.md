## Built

- `crates/bins/orion-recovery`: the binary `orion-recovery` (package
  `orion-recovery-bin`). The comm core with the network carrier, SSH with sftp, forwarding
  and the sandbox, and recovery; no node logic. It reads `/etc/orion/orion.conf` or the
  file named, and the environment; with no file it listens for SSH on port 22. It ends in
  recovery instead of ending. It is its own helper programs. It logs to standard error.
- `scripts/size-gate.sh`, run by the gate: builds it with profile `service` and fails past
  a limit a tenth above the last measured size. Always for this machine (2,973,432 bytes
  measured, x86_64); for a board where the target and a C compiler for it are there
  (2,634,088 bytes, `aarch64-unknown-linux-musl`, checked to be static).
- `recovery.listen`, and `ORION_RECOVERY_KEYS` and `ORION_RECOVERY_LISTEN` read by the
  binary itself, so recovery can be told where to listen and whose keys to take when the
  settings file is what is broken.
- From the board run: the host key's random bytes come from the kernel's call, not from
  `/dev/urandom`; a host key that cannot be made is said to be that; the comm core falls
  back from the sandbox to reading in its own process only when there is no account for
  the children, not when the address cannot be listened on.

## Proved by

- [`testing/board-runs/G6.md`](../../testing/board-runs/G6.md): on a CM5, in a root with
  only the static file and a shell, entered with `chroot`: it ended in recovery because
  port 22 was taken, and `ssh` from a PC gave a root shell, a terminal, and `scp` both
  ways; strangers were refused. As root it became another account with its groups, and the
  child that reads a connection ran as uid 65534 with no groups and no new privileges.
- `cargo test -p orion-recovery-bin`, running the binary: it says its version; started as
  a helper with nothing to do it says why and exits 126; as a comm core it is reached with
  `ssh` and `scp` with no helper named, and stops when asked; with a settings file that is
  not one it stays up, lets in who the recovery keys name and nobody else.
- `scripts/size-gate.sh` passes for both builds.

## Different from the brief

- The package is `orion-recovery-bin`: `orion-recovery` is the crate of G5. The binary has
  the brief's name.
- Not booted in the board's initramfs. That needs an image with this file in it, which is
  another repository's, and a reboot of a shared board. The board run is the file in the
  kind of root an initramfs is. Left for the end, with the image.
- In CI the gate measures the build for the CI machine only: there is no C compiler for
  the board's target there. The board's file is gated wherever one is named.
