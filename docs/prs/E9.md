## Proved by

`tests/placement.rs`: dev's eight tests carried over under their names, and five more.

- `selector_filters_by_label_equality_and_existence`,
  `unreachable_unschedulable_and_unsupported_nodes_are_ineligible`,
  `colocation_follows_the_resource_host`,
  `desired_labels_override_reported_labels_per_key`.
- `rendezvous_choice_is_deterministic_and_minimally_disruptive_property`: 300 random sets of
  up to 12 nodes, 8 workloads each: the same answer whatever order the nodes were learned in,
  always an eligible node, unchanged when another node is removed, and after a node is added
  either unchanged or the new node.
- `only_the_chosen_node_writes_and_running_workloads_do_not_flap`,
  `failover_waits_for_the_grace_period_and_explicit_assignment_wins`,
  `exclusive_remote_resource_admits_one_holder_and_owner_evicts_overflow`.
- New: the hash is pinned to values worked out by a second implementation, so nodes of
  different builds agree; a workload nobody can run is taken by nobody; equal resources are
  spread (400 workloads over 4, each given 60 to 140) with the same answer in any order;
  what a workload needs is read from its labels; a workload that is gone is forgotten.

## Different from dev and from the brief

- Dev's `orion-cluster` read the control plane's desired and observed state. Here the caller
  builds the `View`: which nodes there are, their labels, which are live, which kinds each
  has an executor for, where each resource is.
- What a workload needs of resources has no field on the wire. It is written in the
  workload's labels under two reserved keys. Dev had typed requirements with capabilities and
  shared ownership modes; here a resource has one holder (E16), so "admits one holder" is the
  only mode.
- Not built here, and E18's: making the view from the records and from peer sync's liveness,
  writing the "mine" record and reading it back (it needs a record class of its own; the wire
  has `Node`, `Resource` and `Lease`), and binding the resources `Needs` lists with E16's
  `bind` before a workload starts.

## Also in this commit

The broker's two-process test (C3) failed once in the gate under machine load. It assumed the
subscriber attaches within one ring window of the publisher starting, which depends on when
the subscriber's process gets to run. It now checks what holds whenever it attaches: every
value from the first one read is read or counted as missed.
