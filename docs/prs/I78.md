## Why

A program on the board may receive the files under more than one prefix on one session, as a
bridge for several devices does. The node keeps several prefixes for a session and sends each
file to the longest that matches. The client did not: each `files.sink(prefix)` added a part of
its own for the same kinds of frame, a frame goes to the first part that has its kind, and so
the first receiver was handed the files of every prefix and the others nothing.

## Built

- **One part for all of a session's receivers.** `Files` keeps the receivers in one shared
  state, added to the client once. A `Begin` goes to the receiver with the longest prefix of its
  destination, as the node chooses, and the transfer is remembered with it; each `Chunk` and the
  `Commit` go to the receiver of their transfer, and the commit forgets it. Asking again for a
  prefix the session already has gives a receiver on the same queue.
- **Said once.** `Client::add`, given a part for kinds another part already has, says on standard
  error, once for a session, which kinds (by number) and that the second handle will hear
  nothing. No API change.
- `docs/client.md`: one handle for each part on a session, and several prefixes on one session.

## Tests

- `orion-test-board`, `sinks::two_receivers_on_one_session_are_each_handed_their_own_files`: one
  program's session holds `slots/` and `logs/`, another program holds `keys/`. The first asking
  for `keys/` is refused as `AlreadyExists`, and its two go on. Four pushes, two under each
  prefix, are each committed, and each receiver was handed exactly its own two, whole; a chunk or
  commit of a transfer a receiver did not begin fails the test.
- `orion-connect`, `client::tests::a_part_added_for_kinds_another_has_is_told_by_their_numbers`:
  the kinds taken named by number, nothing said for kinds no part has, said once only.

Each mutation run 3 times through `scripts/bounded.py`, the test binary rebuilt, the source put
back with `command cp -f`.

## Size

The first gate went red at the size lane: `liborion_c.so` (x86_64) was 741,400 bytes, over its
740,000 limit. The C library has no files part (`orion` with `topics` only), so none of it was
the receivers: all of it was the warning in `orion-connect`, which every program carries. Naming
the kinds through `orion_wire::kind::info` brought the wire's whole table of kinds in, the only
user of it outside the wire crate, and `format!` and `eprintln!` the rest.

| `liborion_c.so`, x86_64 | Bytes |
| --- | ---: |
| I77 (77d7496) | 728,464 |
| kinds by name, `format!`, `eprintln!` (first gate) | 741,400 (+12,936) |

| **kinds by number, bytes written whole (landed)** | **731,976 (+3,512)** |

The kinds are named by number, as `orion_wire::kind` lists them. No limit changes. The board's
`orion` carries `orion-connect` through node logic: 5,488,712 bytes at the first gate (+1,688),
under 5,510,000.
