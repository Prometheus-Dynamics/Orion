## Build

- Any program adds actions with a policy.
- Routing to a node or resource. Progress as a topic.

## Proof

An action from another process runs, and is refused by its policy.

## Built

- `crates/node/action-list` (`orion-action-list`): `Actions`, the list and the runs, as plain
  data: `request`, `gone`, `tick`, `next_deadline`, `take_events`.
- `crates/node/reply` (`orion-reply`): `Asked` and `Out`, what every part of node logic is
  asked and how it answers. They were inside `orion-node-app`; the list needs them too.
- `orion-relay`: routes for the action kinds, and `Who::ActionPolicy`: a run is checked
  against the policy in the standing `Register` of the same name and target. A session may
  have 1024 standing requests (it was 64, with the oldest dropped: dropping a registration
  silently is wrong), and one node logic refuses no longer stands.
- `orion-node-app` now runs on the client's shared `Client` with node logic as one of its
  handlers, so it can use the client's parts: it publishes runs on the topic `orion.actions`.
  It answers the action kinds and ends runs at their deadlines.
- `orion-stubs`: `Board::start_for_node_with`, with the security switch.

## Proved by

- `crates/node/node-app/tests/actions.rs`, with security on, against a real comm core:
  - The test binary starts itself again as another process, which connects and adds two
    actions: `open` for programs on the board, `wipe` for operators alone. The caller runs
    `open` and gets the progress and the output the other process made. `wipe` is refused
    with `denied`; one that was never added is `not found`.
  - The topic `orion.actions` told the run's three events and nothing of the refused runs.
  - A run with a 100 ms deadline that the other process leaves running ends `TimedOut`.
  - The other process is killed: its action is `not found`.
  - Node logic is killed and started again while the other process stays: runs are
    `unavailable` in between, and afterwards the action runs without having been added again.
- `crates/comm/relay/tests/relay.rs`: with security on, a run of an action registered for
  operators is refused at the door and never reaches node logic; with security off it passes;
  no registration is `not found`, also for the same name with another target; a registration
  node logic refuses does not stand and is not passed again; registrations are passed again
  to a node logic that comes back; the 1025th standing request is `busy`.
- `crates/node/action-list/tests/list.rs`, 12 tests: one registration a name and target, the
  two numbers of a run, cancel, who speaks for a run, each end going away with and without
  detach, deadlines and late words, the limit on runs.

## Different from the brief and from dev

- "Routing to a node or resource": an action is listed under its name and its target, and a
  run is routed to the registration with both. A run for another node, or for a resource this
  node has no action for, is `not found` until E11 forwards it.
- "Progress as a topic" is one topic for all runs, not one a run: a topic a run would be made
  and dropped at the rate actions run.
- Dev's node kept a registry with built-in actions (reboot, update, blob transfers) and its
  own per-action authorization. None is carried: Orion ships none here, and the check is the
  one check.
- `Attach` is E12's. Until then the comm core refuses it as `unavailable`; a detached run
  already carries on when its caller goes.
