## Build

- A shell that works with a full disk, a broken config or a broken state directory.
- Never backed off.

## Proof

Each broken state still lets you in.

## Built

- `crates/comm/recovery` (`orion-recovery`): `Recovery`, an SSH way in that needs nothing a
  board might have broken. Who may log in is a file of public keys in the image
  (`/etc/orion/recovery_keys`), read again while it runs; the trust store is not opened.
  The host key is the board's if it can be read and one for the run if not. Nothing is
  written. If no address can be listened on it tries each one again every second, for
  ever, at the same pace.
- `orion-ssh`: `SshConfig::recovery`. With it, root is an account even if the board's
  account files are gone (when the comm core is root), and an account whose shell is not
  there gets `/bin/sh`. A home that is not there was already no obstacle.
- `orion-comm-app` feature `recovery` (on by default): `start_or_recover` and
  `run_or_recover` start the comm core, and if the settings cannot be read or it cannot
  start as they say, start recovery instead of ending. Settings that could not be read are
  not believed: security is on and the usual addresses (22, then 2222) are used. Setting
  `recovery.keys`. `helper()` is the one place that knows the words the comm core's
  program is started with to be a helper, and `orion-comm-helper` is a program that is
  only that.

## Proved by

`cargo test -p orion-recovery`, with OpenSSH's `ssh`:

- A state directory nothing can be written to, one that is a file, a host key that is
  rubbish, and an account whose shell and home are gone: each still gives the repairer a
  shell. Nothing was written to the unwritable directory.
- With no keys file nobody gets in; when the file appears the repairer does, without a
  restart; a stranger and someone with no key never do; a line with options in front of
  the key lets nobody in; a key taken out of the file is out. A board whose settings say
  security is off is as open as it always is.
- With both its addresses taken it tried 6 to 11 times in each of four seconds, as often
  in the last as the first, and was open within two seconds of one coming free.

`cargo test -p orion-comm-app --all-features --test recovery`, through the real comm core:

- A setting that is not one, a config that is not a config, a state directory that is a
  file, an identity that is rubbish, and a state directory that takes no file: each ends
  in recovery, says why, lets the repairer in and keeps a stranger out. A file is copied
  off the board with `scp` while it is in recovery.
- A comm core that can start is not in recovery: `ssh` gets a shell through a sandbox
  child and `scp` puts a file on the board.

## Different from the brief

- dev's safe mode kept the node running with its workloads off. Here the part that must
  stay up is the way in, and it is the comm core's; node logic is not involved.
- A full disk is stood in for by a directory that takes no file. The code path is the
  same one: a write that fails.
- "Never backed off" is taken to mean the retry pace never grows. Nothing here slows
  down a client that fails to log in beyond the half second every refusal takes.
- The recovery keys file is new: the trust store is in the state directory, which may be
  what is broken, so recovery needs to be told who may repair the board from somewhere
  else. A board with security on and no such file is closed in recovery, and logs that.
