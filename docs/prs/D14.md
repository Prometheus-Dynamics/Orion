# D14: Which key answered, when it is not the one pinned

**Status:** done

**Group:** D. Client

**Wave:** 18

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Changes

`crates/client/connect`, `crates/client/capi`, `crates/node/action-forward`, `docs/client.md`

## Build

A tool pins a session to the key it first saw (`orion+tcp://host#<key>`). When the node there
proves another key, the tool has to show both fingerprints: a board replaced, or not the one
meant. The refusal was `ClientError::Denied("the node is not the one that was expected")`, with
neither key.

- **`ClientError::OtherKey { asked, answered }`**: the key the address asked for and the key the
  node proved it holds (after it signed the handshake, so `answered` is proven, not claimed). Its
  text has both in hex.
- Everything that treated the old refusal as a refusal does the same with this one: the C library
  gives `ORION_E_REFUSED`, and an action forwarded to a node that proves another key is refused
  `Denied`, not `Unavailable`.

## Built

As above. `ClientError` gains a variant: a `match` on it without a catch-all must handle it.

## Proved by

- `crates/client/connect/tests/connect.rs`: a pin of `[9; 32]` to a node with another key fails
  `OtherKey`, with `asked` the pin and `answered` the node's key, and the text shows the pin.
- `crates/node/node-app/tests/forward.rs` (unchanged) refuses a forwarded action to a node with
  the wrong pin as `Denied`; with action-forward mapping only `Denied` as before, it fails
  (`Unavailable`).
