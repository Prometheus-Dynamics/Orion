## Build

- The `node` mode. Connects with the node role.
- Answers record requests and takes up its work after a reconnect.
- One async thread and helpers on demand.

## Proof

Kill node logic and links stay up. It reconnects and resumes.

## Built

- `crates/node/node-app` (`orion-node-app`): `Node::load` and `Node::run`, `run_until`, `run`,
  `NodeSettings`, and the record service `Records` over E1's store and E2's snapshot.
- `crates/comm/relay` (`orion-relay`), which the brief did not name and the design needs: the
  comm and node tiers may not depend on each other and there is no backplane protocol, so
  something in the comm core has to hand node logic its requests on the one wire. It is a
  service with a table of routes. `orion-comm-app` carries it behind feature `node`, on by
  default.
- Four kinds, `NODE_ATTACH` `0x0B`, `NODE_REQUEST` `0x0C`, `NODE_ANSWER` `0x0D`, `NODE_GONE`
  `0x0E`, with vectors. Nothing recorded before changed.
- `Store::version`, the newest version of a record with deletes included, to answer a `Put`.
- `orion-stubs`: `Board::start_for_node`, a board with the relay in place of the stand-in
  store.

## Proved by

- `crates/node/node-app/tests/node.rs`, against a real comm core on a real socket, through the
  `orion` client:
  - Node logic is killed where it stands. A topic goes on flowing between two programs, their
    sessions stay, and record reads and writes are refused with `unavailable`. Node logic
    starts again: the records are back with their stamps, the next write is stamped after
    them, and a watch made before the kill is told of it though its program never asked again.
  - The comm core restarts under node logic: node logic reconnects by itself and still has
    its records.
  - Asked to stop inside the save delay, it saves first.
  - A read of 200 KiB of records arrives whole, in several messages, in key order.
- `crates/comm/relay/tests/relay.rs`: unavailable without node logic and for a kind it did
  not name; only the node role attaches; a request arrives with its session, `seq`, caller
  and payload, and the answer reaches the caller; `NodeGone` when the caller's session ends;
  a watch is passed again to the node logic that comes back, and one made while it was away
  waits for it; a second node logic closes the first.

## Different from the brief and from dev

- Dev's node was one process: its app builder made the listeners, the store and the services
  together. None of that is carried. What is kept is the order of start: load, then serve.
- "Answers record requests" is all it answers so far. Workloads, actions and files add routes
  and services as E4, E10 and E13 are built; until then the client's tests for those use the
  stand-ins.
- A watch that outlives a node logic restart may be told a version twice. The relay does not
  read what it passes, so it cannot move the watch's `after` forward.
- A record is at most one frame, 64 KiB with the defaults.
- Not built: telling systemd it is ready. Node logic has nothing that listens, so there is no
  moment others wait for.
