# I138: A program that dies inside a frame is seen gone, and the comm core goes on serving

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I136

Read `AGENTS.md` and `docs/design.md` first.

## Why

CI on I136 was red: `file-offers` `fetch::a_fetch_whose_program_goes_is_rejected_to_its_client`
failed with `not told after 1.005786794s`. It wasn't rerun.

Run alone in a loop at load 107–160, nice 10, it failed 4 times in 1060 runs. A trace of every
step after the cut showed the client still at its first chunk and never told, and still not told
with the deadline lifted to 20 s. So nothing was late; the program's going was never seen.

Planted delays (test-only) found where it stops:

- **200 ms before the cut:** 0 of 60 failed. The test's own polling isn't it.
- **The relay writing each read in two halves with a pause between, so the cut lands inside a
  frame:** 8 of 8 hung. In each, a second session's `offers()` got no answer within 3 s.

A stack of a hung run showed the comm core's one thread in the Unix carrier's receive
(`crates/comm/unix/src/lib.rs`, `recv`), using 1.64 CPU-s in each 2 s.

The carrier's receive takes whole frames only. A frame that is only partly queued counts as
"would block", and the loop waits for readiness and tries again. Once the peer has hung up after
part of a frame, the rest can never come, and the socket stays readable because of the hang-up.
The loop spins: the session never ends, the client is never told, and no other session on that
comm core is served. Any program that dies in the middle of a send does this.

## Changes

- **The carrier's receive treats a partial frame after the peer hung up as the peer closing
  (`Ready::is_read_closed`).** It returns `Ok(None)`, as it does for a hang-up between frames.
  Frames that are wholly queued are still received first.
  - This works against shm-fdpass as it is (rev 214c0ca). Its own fix comes with a later rev bump,
    as a separate change.
- **A test, `fetch::a_program_that_dies_inside_a_frame_is_gone_and_the_comm_core_serves_the_others`.**
  Its relay (`relay_holding`) follows the carrier's framing (`[u32 length][frame]`). It stops one
  byte short of the end of the first frame that starts past the first chunk, and the test cuts
  only once that byte is held. So the cut lands inside a frame every run. It asks that:
  - the client is told within 1 s, as the test it comes from asks: Rejected, "the program that
    offers it went";
  - a second session's `offers()`, asked right after the cut, is answered.

Nothing on the wire changes, and nothing a program calls.

## Proved by

- **Fail-before:** the new test against the carrier as it was fails 8 of 8 (`not told after
  1.01 s`). **Pass-after:** 8 of 8 pass.
- **The test that was red, alone with the fix:** 0 failures in 400 runs, load ~107.
- **Mutations, each 3 runs of 3:**

| Mutant | Fails on |
|---|---|
| No arm for a partial frame after a hang-up (as before) | the new test: not told after 1 s |
| Any "would block" taken as closed | 4 carrier tests in `unix.rs` (a reader that falls behind, descriptors, …), and the file-offers tests hang or fail |
