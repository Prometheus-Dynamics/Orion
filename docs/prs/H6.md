## Built

- `files.send`, node logic's one action of its own: `FileSend { file, to }` sends a file the
  node keeps to the receiver of `to`. Node logic registers it as a client, so the relay checks
  each run against its policy (programs on the board, operators with a grant). It sends one
  chunk, waits for the answer, ends on committed or rejected, begins again after 2 quiet
  seconds (5 tries), and numbers the transfer from digest and destination as a client push
  does, so either resumes the other.
- `FileSink` gains `max_chunk` (appended; 0 = any). A receiver that names it is sent one frame
  at a time, larger chunks cut to fit (`orion-files-sink`, at most 1 MiB waiting a transfer).
  A sender that begins again is passed on at once and what waited is dropped.
- The device firmware layer names `rx_max - 31` as its `max_chunk`; `Link::rx_max()` added.
- `Files::placed(name)` gives the digest and size of a stored file.
- `FileSend` args body in `orion-msg-files`. Wire vector for `FILE_SINK` re-recorded with the
  new field.

## Proved by

- `crates/testing/device-tests/tests/firmware.rs`, against a device built from
  `orion-device-firmware` on a pseudo-terminal with flash in memory and a 512-byte receive
  buffer:
  - an image pushed to the board by an ordinary client reaches the device's spare slot
    through `files.send`, byte for byte, every chunk fitting the buffer; sent again, it
    succeeds at once; a missing file and a destination nobody receives are rejected;
  - a client pushes 32 KiB chunks, several in flight, straight to the device's destination,
    and the board cuts and paces them;
  - a chunk the device never heard is sent again and the image arrives whole.
- `orion-files-sink`: `a_receiver_that_names_a_chunk_size_is_sent_pieces_one_at_a_time`.

## Different from the brief

- No `crates/comm/device-firmware`. The comm core cannot read the node's file store, and comm
  and node crates never depend on each other, so the action lives in node logic, which keeps
  the files. It is not firmware-specific: it sends any kept file to any receiver, a device's
  firmware slot being one.
- Dev ran firmware through a link-specific transfer protocol. Here a device takes an image
  through the ordinary file kinds; what had to change was the chunk size and pacing for a
  small receiver, which is now part of `FileSink` and the sinks, so any sender gets it.
