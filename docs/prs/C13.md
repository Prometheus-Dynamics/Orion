## Build

- Bulk and gadget transports for the link.
- Takes a device handle from elsewhere, so Orion does not talk to hardware itself.

## Proof

Round trip through a board's USB link.

## Built

- `orion-link-usb`: `UsbLinks`, where a link waits for its handle, and `UsbLinkService`, which
  takes `LinkOffer` from a program on the board with the descriptors attached. The link then
  runs over `orion_link_serial::StreamCarrier`. The comm core opens no hardware.
- Three kinds of handle: a stream (one descriptor that can be waited on: a gadget's serial
  function, an open serial port, a socket), endpoints (two blocking descriptors, a thread in
  each: a gadget function's bulk endpoints), and, behind feature `bulk`, a USB device's
  descriptor with its interface and bulk endpoints, through the `nusb` crate.
- A link with no handle opens nothing and tries nothing. A new offer for a link that has a
  handle ends the old stream and the link goes on over the new.
- Two kinds were added, `LINK_OFFER` 0x09 and `LINK_TAKEN` 0x0A; no recorded vector changed.

## Proved by

- `tests/usb.rs`, on the build machine: a round trip over a stream handle and over an endpoints
  handle, 0 allocations in 2,000 heartbeats over each, a re-offer after unplugging, a device that
  goes with nothing to replace it, and every refusal (not on the board, unknown link, wrong
  number of descriptors, unknown transport).
- The board run (`testing/board-runs/C13.md`): the stream handle over the test board's gadget
  serial function, to a device end on its controller. Hello answered at once, heartbeats both
  ways, a round trip p50 216 µs and p99 1,345 µs over 490 pings, a 3 s gap on the controller's
  port survived, and a new handle offered for the link taken with the device back in a new
  session within one heartbeat timeout.

## Different from the brief

- The board run found `orion` built without USB links (`links.usb` was a key nobody read):
  `orion-bin` now enables `link-usb`.
- The run used the gadget's serial function on the board's current image (the user's choice A
  for this run). The endpoints handle over FunctionFS is proved on the board's next image,
  whose gadget is built new with FunctionFS for the link (see F10).
- The cable was not pulled by hand: nobody was at the board, and its network is the same cable.
  Both halves of a replug were run instead.
- **The `bulk` transport** compiles and has still never met a device.
- The gate turned up a race in `orion-files-pull`'s test server, fixed here: it noted a request
  after answering it, so a client could finish and look before the second was noted. The test
  now waits for the count it expects.
