## Why

I69 made one push's window fit in a session's outbox. Two or more pushes at once could still
fill node logic's outbox, or a receiver's. The comm core then dropped node logic, or the
receiver, for traffic that wasn't its own, and every transfer it was passing went with it.
The rule is that a slow reader paces the sender. It never gets a third party dropped.

## Built

- **`Delivery::Refuse`** in the server. A frame with no room in the outbox is not sent, and
  the session it was meant for carries on as before. The caller tells the sender `Busy`.
- **The relay refuses only where the sender hears it.**
  - These kinds are refused `busy` to their sender when node logic's outbox is full, instead
    of node logic being dropped (`REFUSED_WHEN_FULL`): the push's three kinds, `FilePull`,
    `Put`, `Get`, `ActionRun`, `ActionAttach`, `PeerStatus` and `PeerForgive`.
  - Every other kind keeps `Must`. Those are standing requests, which a refusal would end
    without a word, or messages no one waits an answer to, which a refusal would lose.
  - For those kinds, dropping node logic followed by `NodeBack` and the standing replay is
    still what puts them back. A survey of every routed kind's sender found this. Each kind's
    sender would have to handle `Busy` before it could join the list.
  - A unit test checks that no kind on the list is a standing route.
  - When node logic has just attached, the standing requests are passed to it with `Must`, as
    before. A node logic that doesn't read them is dropped, and its warning names the session.
- **files-sink keeps a receiver within its outbox.**
  - It counts what has been sent to a receiver that takes chunks of any size and not yet
    answered, across all transfers to that receiver.
  - That count is held to `comm.outbox_bytes` minus one chunk's room. Node logic reads the
    figure from its own settings and never takes it above the default.
  - A chunk past that limit is refused `busy`, and so is any chunk after a gap. What a
    receiver is sent stays in order.
  - A chunk that is already on its way, sent again by a sender that went back, is not sent
    twice.
- **The push.**
  - It keeps the seq of each chunk on its way.
  - When a chunk is refused `busy`, it goes back to the board's count and sends from there
    after a wait of 20 ms, doubling to 320 ms. The wait starts over once the board takes
    something.
  - A `FileBegin` or `FileCommit` refused `busy` is asked again after 20 ms.
  - None of this renews the push's bound. A board that stays busy ends the push the way a
    board that goes quiet does.
  - The board may still answer chunks sent before the refused one, after the push has gone
    back. The push moves forward to such an answer rather than calling it "backwards".
- **`ClientError::is_busy`, `orion::Error::is_busy`.**
  - An error for which `is_busy()` is true never has `is_lost()` true, so a program that
    reconnects on `is_lost()` keeps its session through busy.
  - `docs/client.md`, "When the board is busy", lists each request, what it is called through,
    and what this client does on `busy`. It also says what a busy run, `set_state`, `publish`
    and `withdraw` leave behind, and what still drops node logic and what then puts things
    back.
- **`Workloads::wait` finds a refusal.** Its documentation said it does, but it never read one.
  It now keeps the seq of each workload's last put and returns that put's refusal.
- **A test hook.** `orion-node-app` has a feature `slow`, which no shipped build has.
  - With it on, `slow::delay(node)` makes node logic for that node sleep before each frame it
    handles.
  - `orion-test-board` turns it on only as a dev-dependency, so the feature stays out of every
    build except that crate's tests.
- **Older senders.**
  - A sender from before this change, refused `busy` for a chunk, does not read the refusal.
    Its push stops moving and ends at its per-answer bound, as before.
  - Node logic and the other transfers survive, so pushing again carries on from the board's
    count.
- **Nothing on the wire changes.** `Busy` and `Refusal` already exist, and the level stays 6.

## Not in this

- **Limits of what the other front ends tell.**
  - C reports `busy` as `ORION_E_REFUSED`, the same code as a final refusal.
  - `orion` on the command line exits 1 for it.
  - `Run::poll` hands any refusal over once, then returns `Ok(None)`.
  - The ring of 8 remembered refusals per session can push out one that something is waiting
    for.
- **A busy `ResourceDecl::publish` or `Resource::withdraw` takes its handle.** This is fixed
  in I71.
- **A flood of the kinds that still use `Must` can still drop node logic.** This was true
  before, and they are put back after it. `docs/client.md` and `docs/comm.md` say so.

## Proof

- **`pushes_at_once_past_a_full_outbox_are_paced_not_lost`** (`tests/board.rs`):
  - **The setup.** A board with `comm.outbox_bytes = 131072`, less than one window, so every
    push is turned away along the way. 2 and then 4 pushes of 4 MB go at once to the node's
    store, then 2 and then 4 to a `hold_commits` receiver. Each is bounded at 60 s.
  - **What it checks.** All commit, the receiver answered 6, and node logic runs.
  - **It passes 3 of 3.**
- **Mutations, 3 runs each, every run failing:**

  | Mutation | Result |
  |---|---|
  | The relay sends with `Must` again | "refused: unavailable": node logic was dropped |
  | files-sink keeps no limit | The receiver's session is dropped: "the program that receives it went away", or the board's count goes backwards |
  | The push ignores `busy` | Times out at its 5 s bound with progress stuck, which is how an older sender behaves |

- **`a_put_while_node_logic_is_behind_is_busy_and_node_logic_stays`:**
  - **The setup.** `comm.outbox_bytes = 70000` and node logic slowed to 300 ms a frame. A
    filler sends 800 small puts without waiting for answers, and reads what it is told.
  - **What it checks.**
    - A writer's 16 kB put is refused, and `is_busy()` is true.
    - Once node logic catches up, the fills are written and "late" is not.
    - Node logic answered all along.
  - **It passes 3 of 3.**
  - **Mutation:** `PUT` taken off the refused list. The put is refused `unavailable`, because
    node logic was dropped. All 3 runs failed.
- **`a_workload_refused_is_found_by_wait`:**
  - **The setup.** Node logic is stopped, so the relay refuses the put `unavailable`.
  - **What it checks.** `wait` returns that refusal.
  - **It passes 3 of 3.**
  - **Mutation:** `wait` does not read the refusal. It returns `Ok(None)` after 5 s. All 3
    runs failed.
- **`busy_is_never_lost_and_lost_is_never_busy`** (connect) and
  **`no_kind_refused_when_node_logic_is_full_is_a_standing_request`** (relay) pass.
- **Every `orion-test-board` test passes 3 of 3**, I69's twenty-push loop among them.
- **The landing gate passed.**
