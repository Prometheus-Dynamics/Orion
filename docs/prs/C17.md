# C17: Withdrawing one topic

**Status:** done

**Group:** C. Comm core

**Wave:** 18

**Needs:** C16

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Changes

`crates/core/wire`, `crates/core/msg-topics`, `crates/comm/broker`, `crates/client/topics`,
`crates/client/buffers`, `crates/client/provider`, `crates/client/ctl`

## Build

- A program that stops offering one topic says so, and its session goes on. Today a topic ends
  only with its publisher's session, so a provider whose device is unplugged keeps a topic that
  nothing will publish again, and nobody else may declare it.
- `TOPIC_WITHDRAW` (`0x4C`), body `TopicWithdraw { handle }`. The broker takes it from the topic's
  publisher only, does what a closed session does for that one topic (subscribers told
  `PublisherGone`, the ring kept for them), answers the publisher with the same `TopicState`, and
  removes the topic if nobody is left on it.
- In the client: `Publisher::withdraw`, `Topics::withdraw(name)`, `BufferPublisher::withdraw`,
  `AdoptedBuffers::withdraw`. A withdrawn topic is not declared again by `restore`, and its
  publisher cannot publish (`TopicError::Withdrawn`). `Resource::withdraw` withdraws the
  resource's topics before it says the resource is gone.
- `orion topic read` takes in what has arrived before it says whether the publisher is gone.

## Proof

`a_publisher_withdraws_one_topic_and_keeps_its_session` (orion-topics): subscribers on the board
and across the network hear the publisher is gone and keep its last value; a topic withdrawn by
name cannot be published to; the session goes on; after a reconnect another program declares
both withdrawn topics; a session that does not publish a topic cannot withdraw it. The provider
test reads `PublisherGone` on a resource's topic after `Resource::withdraw`.

## Built

As above. The broker's closed-session path and withdrawal share one function,
`publisher_gone`.

## Proved by

- The test above, 30 runs of the topics suite in a row. With `restore` not skipping withdrawn
  publishers it fails (`restore` times out on the old declaration); with the broker not checking
  the publisher it fails (the stranger's withdrawal is accepted).
- `crates/client/provider/tests/provider.rs`: the resource's topic goes `PublisherGone`.

## Different from the brief

- There was no brief: this one is written with the PR, from the plan given to the consumers.
- Two client bugs the test found, fixed here:
  - A withdrawn publisher kept the `seq` of its declaration. After a reconnect the session's
    numbering starts again, and a new request's answer was taken for that publisher's: a
    subscriber's read end was mapped as a writer and refused. Withdrawn publishers no longer
    match answers.
  - The broker keeps one subscription per session per topic, but a program can subscribe to a
    topic twice (a `Subscriber` dropped and made again, as `show` and the provider test do). News
    of the topic (`TopicState`, samples off the board) went to the first only, which might be one
    already dropped. It now goes to every subscriber of the topic on the session.
