# J1: Opaque data: sample times and buffer topics

**Status:** done

**Group:** J. The stack around Orion

**Wave:** 17

**Needs:** none

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Build

- Orion moves bytes with a name, a time and a place in memory. Nothing in it knows what a
  frame, an image or a pose is, and a new kind of data never needs an Orion change. Written
  into the design as a rule.
- `FrameTime` becomes `SampleTime`; "frames are topics" becomes buffer topics; example topic
  names say nothing about cameras. A wire frame (`[version][kind][seq][payload][crc]`) keeps
  its name: that is the protocol's word, not data's.

## Proof

The gate. No `FrameTime` left; the design states the rule.

## Built

- The design's "Orion does not know" now says frames too, and states the rule: movers don't
  know what they move, and a new kind of data never needs a change to Orion. "Buffers: frames
  are topics" is "Buffer topics", about data too large to copy, whatever it is.
- `FrameTime` is `SampleTime` everywhere, `frame_time` is `sample_time`, and "frame time" is
  "sample time" in docs and comments.
- A buffer topic's entry is a `Batch` (`NextBatch` from a reader), not a `Frame`. The example
  topic is `sensor0.data`.
- A wire frame keeps its name: that is the protocol's word.

## Proved by

The gate. No `FrameTime` left in code or docs outside the plan's history.

## Different from the brief

- Test names and some comments still say "frame" where the test is about images or video (the
  drill camera, the browser video page): those are programs using Orion, and they may know.
- The device library takes the same names into its copy of the ring crates (J2), so the two
  never differ.
