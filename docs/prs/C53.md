## Build

From a test rig under heavy load (30 busy processes, tests at nice 19), over TCP on
loopback:

- A client reported the session lost with "Resource temporarily unavailable (os error 11)".
  Find the path that lets EAGAIN out as an error, fix it, and test it with an injected
  WouldBlock.
- `Options::timeout` was one number for both connecting and every reply. A rig that passed its
  2 s connect timeout gave every reply a 2 s wall-clock deadline, which a healthy reply on a
  starved machine missed. Split the two:
  - a reply wait bounded by liveness, meaning nothing heard for a window that any frame
    renews, plus an optional ceiling per request;
  - additive, so that callers who don't opt in see today's behaviour;
  - in Rust, C and the web client.
- `silent_for()` goes here too, since it is the same `last_heard` state.

Then, from the rig's owner, a detached run whose follow came back with another run's result:

- A client's call numbers start over with each session. A session lost after starting detached
  run 1 leaves run 1 going. The next session's run 1 is another run, but a number cannot tell
  them apart: an attach or a cancel by number could reach the wrong one, and a kept answer could
  be given for the wrong run.
- Name each run with a handle the node gives: random per start of node logic, plus node logic's
  own number for the run. Tell it as the run starts (`ACTION_STARTED`), carry it on progress and
  results, and take it on attach and cancel.
- Keep older clients safe without a handle, and refuse a handle from before node logic
  restarted, saying so.
- Test with the rig's sequence: session one starts run N detached and is lost; session two
  starts another run as N; its follow gets its own result; the old answer only by the old
  handle; a stale handle refused; node logic restarted, and an old handle reaches nothing.

And move the shared-memory pin to the device library's `b0a75d93`, in the same commit.

## Built

### The EAGAIN

The session's own reads and writes were not the source: every non-blocking path already takes
WouldBlock as "nothing yet". The TCP handshake was:

- It runs on a blocking socket with `SO_RCVTIMEO`/`SO_SNDTIMEO` set to `Options::timeout`.
- When that expires, Linux returns EAGAIN, and `read_exact` passed it up raw.
- So it was the connect timeout firing, under the kernel's "try again" words.

Each handshake read and write now maps WouldBlock to `TimedOut`, saying "connecting: no answer
from the node within `Options::timeout`". `is_lost()` still holds for it, so a reconnect loop
tries again.

### The bound

`Options::reply: Reply`:

- `Reply::Timeout`, the default: today's rule, each answer within `Options::timeout`.
- `Reply::Alive { ceiling }`: for as long as the node is heard from. The wait fails with:
  - `ClientError::Lost` when nothing at all has come for the idle time the node declared in its
    welcome (`comm.idle_ms`, three heartbeats unless set);
  - a timed-out `ClientError::Io` at the ceiling, if one is given. The session is still good.

How it works:

- The client pings every half heartbeat while it waits, and the comm core answers each ping,
  so a node that is running is never silent that long.
- Under `Alive` the silence rule holds on the board's own socket too. Without it, a local
  session is never ended for silence, as before.
- `Session::reply_left(since)` is the one place a wait asks how long it has left. Every wait
  reads it:
  - `Session::answer` and `Client::answered`, which is every helper: `node()`, resources,
    topics, actions;
  - a push's wait to hear about its transfer, and its commit (twelve timeouts under
    `Timeout`, as before);
  - a shell's wait for credit to write.
- `set_reply` on `Session`, `Client` and `Orion` changes the bound for every later wait until
  it is called again, and a reconnect keeps it.
- `silent_for()` is the time since anything at all arrived.

**C:**

- `orion_set_reply(orion, ORION_REPLY_TIMEOUT | ORION_REPLY_ALIVE, ceiling_ms)`, where
  `ceiling_ms` 0 means no ceiling. Lost is `ORION_E_LOST` and the ceiling is
  `ORION_E_TIMEOUT`, as before.
- `orion_silent_for_ms(orion)`.

**Web:**

- `orion.setReply({ alive: true, ceilingMs })` and `orion.silentFor()`.
- The page had no reply bound before and keeps none by default.
- Under `alive`, a board silent for its idle time closes the connection, and every wait fails
  saying so. A ceiling rejects that wait with `TimedOut`.
- The idle time is read from the welcome. A board too old to send it gives three heartbeats.

The bound itself is no wire change and no change on the node side.

### Run handles

**The handle.** `RunHandle { instance, run }`:

- `instance` is drawn at random each time node logic starts, never 0. `run` is node logic's own
  number for the run.
- It is kept as 16 bytes (`to_bytes`, `from_bytes`, each half little-endian) or written
  `<16 hex>-<16 hex>` (`Display`, `FromStr`).

**On the wire.** Every addition is appended or new, so the revision stays 1:

- `ACTION_STARTED` (0x39) `{ call, instance, run, action }` goes to the caller after the claim,
  and to a session that attaches, before anything else of the run.
- `Progress` gains `instance` and `run`. `ActionResult` gains `instance`, `run` and `action`.
- `Attach` and `Cancel` gain `instance` and `run`. 0 means "by number", which is what an older
  client sends.
- `INTERFACE_LEVEL` is 3. `Feature::RunHandle` is level 3, because an older node reading only
  the number could reach another run. The error `run gone` (23) is level 3, and a session below
  it is told `not found`.

**Node logic.**

- By handle: `Attach` and `Cancel` reach that run alone, for its starter, from any session. A
  handle of another instance is refused as `RunGone`, with words saying the node restarted and
  the run is gone.
- By number alone, as an older client asks:
  - a cancel reaches only a run this same session started under that number;
  - an attach reaches the starter's run under that number that no later detached run took;
  - a detached run started under a number takes it. The starter's earlier runs under it, going
    or kept, are marked and reached by handle only. An attach by that number is then refused as
    `NotFound`, saying to come back by the handle.
- A run that is not detached takes no number from another. Otherwise a program of the same user
  running something under its own 1 would hide the detached run 1.
- The session a run started from is forgotten when that session ends. The comm core reuses
  session numbers, so a later session must not inherit the number.

**Clients.**

- Rust: `Run::handle()`, `Actions::attach_handle(handle)` (level-checked), and `Run::cancel`
  names the handle once it is known.
  - A frame that names a handle is matched to the run with that handle. Only a frame without
    one, from an older node or a run carried to another node, is matched by number.
  - `orion::Orion::attach_handle`; `RunHandle` is re-exported.
- Web: runs are matched by handle the same way. A page never detaches, so it has no attach.
- C: no actions in the C API, so no change.

**Not covered.** A run carried to another node gets no handle. The carrying node sends no
`Started`, and its caller follows and cancels by number as before. If a session is lost before
its `Started` arrives, how the run went is unknown: the docs say to find out from what the
action changes, never by coming back to the number alone.

### The shared-memory pin

Moved from the device library's `bded77a0` to `b0a75d93`:

- The `shm/` tree is the same object at both commits (`252cf4c5`).
- The only change in that library's workspace manifest is its own build profiles, which never
  apply to a dependency.
- `Cargo.lock` changes in the seven source lines and nowhere else.

### Tests that were flaky under load

- `drills` `a_bad_provider_is_contained` looked once at whether the provider had exited, right
  after its sockets closed, which can come before the process is reaped. It now waits up to
  the test's long bound (`exits_within`).
- `orion-shell` `with_a_login_helper_the_helper_starts_the_shell` (from C52) ran two shells
  one after the other with a helper that exits after 500 ms idle. A machine slow enough
  between them let the helper exit, and the second shell was refused. A shell is now held
  open across both and closed before the idle exit is checked. With a 1 s pause put between
  the two, the test still passes.
- This PR's own `orion-connect` `tests/alive.rs` connected with the 300 ms timeout its replies
  are measured against, and under the gate's load the handshake took longer. The test node now
  serves connections in turn, and a connect that timed out is tried again, up to 20 times. The
  reply bound is still measured at 300 ms.

## Proved by

- `orion-connect` `tests/alive.rs`:
  - by default an answer has the timeout;
  - while the node is heard from, an answer waits until the ceiling, longer than the timeout,
    pinged throughout and never silent;
  - a node silent for its idle time is lost before any ceiling, on the board's own socket too,
    and `silent_for` says so;
  - the bound is kept until it is set again;
  - a node that takes the connection and never says hello has timed out, not "os error 11",
    and is still lost to a reconnect.
- `orion-capi`: the C program sets the bound, a bad mode is refused, and `silent_for_ms` is
  small on a live session and 0 for null.
- `orion-web-tests`: in a browser, a run that a program registered and never takes is
  rejected with `TimedOut` at its ceiling, and `silentFor` is under the idle time.
- `orion-action-list` `tests/handles.rs`, with the rig's sequence:
  - session one starts a detached run as 7 and is lost; session two starts another as 7 while
    the old one runs. The old one ends first and session two hears nothing of it. Session two's
    follow is its own result.
  - The number reaches the newer end, once, and never the old one. The old answer is reached
    by its handle alone, and once it has been told, that handle is stale for attach and cancel.
  - The old run still going is cancelled by its handle; the number cancels session two's own.
  - A cancel after coming back by the handle reaches that run, and its end comes to the session
    that came back.
  - Node logic started again with another instance draws the same first number: the handle from
    before is `RunGone` for attach and cancel, with words, and nothing reaches the program.
  - A run that is not detached takes no number from a detached one; each start draws its own
    instance; the handle reads back from its bytes and its text.
- `orion-action-list` `tests/list.rs`: every run's caller is told its handle, which progress and
  the result carry. A bare cancel from a session that only came back is refused, and the
  handle's is taken. Someone else with the handle is not its starter.
- `orion-node-app` `tests/actions.rs`, on a real comm core and node logic through the `orion`
  client: the same sequence end to end, a cancel after `attach_handle`, and after node logic
  restarts, an old handle refused as `RunGone`.
- `orion-server` `spoken`: `run gone` from level 3, `not found` below.
- Mutations of the handles, each killed:
  - a handle of another instance taken as this one's;
  - a bare cancel reaching any session's run under the number;
  - a new run marking neither the starter's running nor its kept runs under the number (each
    on its own);
  - a handle reaching a run whoever asks;
  - a run that is not detached taking the number;
  - the session a run started from kept after it ended;
  - `run gone` told to a session below level 3;
  - the client matching frames by number alone, ignoring `Started`, or cancelling without the
    handle.
- Mutations of the liveness work, each killed:
  - silence never losing the session;
  - the ceiling ignored (the test then waits forever, and the run is ended by a time limit);
  - the ceiling replaced by the timeout;
  - `set_reply` doing nothing;
  - the handshake's WouldBlock left as it is;
  - the web ceiling never firing (the page never reports);
  - the C mode check removed.

## Different from the brief

- The per-request bound is session state (`set_reply`), not a parameter on every helper, as
  agreed with the rig's owner.
- The C ABI minor version is not raised: no version moves on this branch until a release.
- A run that is not detached took no number from another. The brief had every start take it;
  the end-to-end test showed a program of the same user hiding a detached run that way.
  C53b reverses this: every start takes the number again, so a number alone never gives back
  an older run's answer, and that test now ends its runs from numbers past the one in play.
- `Started` on an attach carries the attach's own number, so a client that comes back by handle
  under a new number is told the handle under that number.
- A run carried to another node has no handle: its caller follows and cancels it by number.
- The web client matches by handle but has no attach, since a page never detaches.
