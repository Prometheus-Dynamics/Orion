## What happened

On a board, every operation inside a root failed with "Function not implemented (os error
38)": a push ("its directory cannot be made"), a fetch, and the root's index. The kernel has
`openat2`, and the unit's system call filter lists it.

## The cause

`packaging/systemd/orion-node.service` set `RestrictSUIDSGID=yes`. Under that setting systemd's
seccomp filter answers `openat2` with `ENOSYS`, on purpose: the call's flags are in a struct
the filter cannot look at, so it blocks the call "to force programs to call open() or openat()
instead" (`src/shared/seccomp-util.c`, `seccomp_restrict_suid_sgid`, read at v257 and v258).
Every other call the unit filters returns `EPERM`, which is why this one alone was 38.

Node logic opens everything under a root, and puts a file in place in the store, with
`openat2` and `RESOLVE_BENEATH`. There is no fallback by design: that flag is what keeps a
path inside the root.

The image's unit was this repository's file, byte for byte, so the fault was Orion's.

## Why the gate did not see it

No step runs node logic inside its unit's sandbox. The tests run the binaries as plain
processes, and the packaging step read the units without starting anything under them. So
every hardening line of the two units was untested against what the code calls.

## Built

- **The unit no longer sets `RestrictSUIDSGID=yes`**, with the reason beside where it was.
- **What the setting guarded is not left open.** Node logic never sets a mode from what a
  client sends, and has no chmod. A file it makes is `0666` less the umask and a directory
  `0777` less the umask. `modes::` (I86) already checks, in a setgid root with the unit's
  umask, that a pushed file is exactly `0660`: no setuid or setgid bit. Masking those bits
  again in the files code would guard nothing, since there is no mode to mask.
- **Named, where it is refused.** Node logic looks once at start, at the store and each root
  (`orion_file_store::probe`). Where `openat2` is refused:
  - an error in its log;
  - every push, fetch and listing says `openat2 is refused here (a unit with
    RestrictSUIDSGID=yes does that): nothing under a root or the store can be opened`;
  - the board's hello carries the same words as the fact `files`.
- **No walk by hand** when `openat2` is refused: that is where a path would get out of a root.

## Not as asked: the line in `orion/state`

The line was to be in `orion/state`. That file is the comm core's, and the fault is in node
logic's process, in another unit with another sandbox: a look from the comm core would say
nothing of node logic's. So node logic says it itself, as the hello fact `files`, which
`orion-ctl node show` prints and a client reads. Carrying it into `orion/state` would need a
way for node logic to tell the comm core, which is not there.

## The comm core's unit keeps the setting

Checked: `openat2` is called in two crates, `orion-file-store` and `orion-file-roots`, both
node logic's. `grep -rn openat2 crates` finds it nowhere in the comm core's crates. This is a
check of Orion's own code, not of every dependency's.

## Closing the hole

- **`scripts/packaging-check.sh`** fails if `orion-node.service` sets `RestrictSUIDSGID`. With
  the line put back, it fails; without, it passes. The unit's exposure is 2.0, under its limit
  of 2.5, which is not changed.
- **`sandbox::where_openat2_is_refused_the_board_says_so_by_name_and_not_function_not_implemented`**
  (`orion-test-board`) runs a whole board, the real comm core, node logic and client, under a
  seccomp filter of its own that answers `openat2` with `ENOSYS` and allows everything else,
  loaded by `bwrap`. A push, a fetch and the index are each refused by name, and the hello
  has the fact.
- **What is still not here:** a step that starts the real units under systemd. That would be
  a test against a service manager on the machine that runs the gate. It belongs in the
  image's first boot, in the emulator and on a board.

## Tests

Three mutants each failed 3 of 3 runs: the store not naming it, the roots not naming it, and
the look at start finding nothing.

**Where `bwrap` cannot load a filter** the sandbox test says so and passes: on such a machine
it checks nothing. It runs on the machine the gate runs on.

**Not shown:** the fix on a board. The cause is read from systemd's source and matches what
the board showed; the image's unit was confirmed to be this file. The board itself is the
check.
