## Fault

I50 gave kept runs through `Actions::register_kept` only. A program that registers its actions
as a provider, through `Describing::action`, or through the facade's `register_action`, had no
way to ask for them. A second `Actions` on the same client is no way around it: every handler
that lists a kind is given its frames, so runs would be queued twice.

## Built

- `Describing::action_kept(name, description, policy, keep)`: as `Describing::action`, through
  `Actions::register_kept`.
- `Orion::register_action_kept(decl, policy, keep)`: as `Orion::register_action`, through
  `Actions::register_kept`.
- Both need a node at the kept runs' level and fail below it with `ClientError::Level`, sending
  nothing.
- `docs/client.md` says that a new session of the same program is handed the kept runs, not only
  this session restored. Node logic gives them back on any registration of the action by the
  same identity. A new session can register only once node logic has seen the old one go.

## Proof

- `crates/client/provider/tests/kept.rs`: a provider describes `arm.left` with a kept `move`. A
  caller starts a detached run. The provider's session is dropped, and the caller is told
  `restoring`. A new provider session of the same program describes the arm again and is handed
  the same run as kept. It finishes it, and the caller gets `Succeeded` with its output. With
  `action_kept` registering as `action` does, it fails, 3 runs of 3: the run ends `Failed`, "the
  program that runs it went away".
- `crates/client/orion/tests/kept.rs`: the same through the facade, with `register_action_kept`
  and a new `Orion` session. With `register_action_kept` registering as `register_action` does,
  it fails the same way, 3 runs of 3.
