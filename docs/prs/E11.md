## Proof

Across two nodes, with the owner restarting.

## Built

- `crates/node/action-forward` (`orion-action-forward`): `Forwards` with `run`, `cancel`,
  `gone`, `poll`, `active`, and a helper thread for each other node that holds a client
  session to its comm core.
- `orion-node-app`: a run or cancel the list does not know is tried as one for another node.
- `orion-relay`: a run of an action not registered here is let through to node logic for
  anyone this node knows, where before it was `not found` at the door.
- `orion-stubs`: `Board::start_named`, a board with another name and, to come back where it
  was, a port.

## Proved by

`crates/node/node-app/tests/forward.rs`: two nodes, `left` and `right`, each a real comm core
with security on and its own node logic; `right` trusts `left`'s key as a peer and has a
program with two actions.

- A caller on `left` runs `blink` for node `right`: the program on `right` does it, and its
  progress and output come back to the caller.
- `wipe`, registered on `right` for programs on its own board, is `denied` for the caller on
  `left`: decided at `right`'s door. `none` is `not found`, said by `right`. A run for a node
  with no record is `not found`, said by `left`.
- Cancel from the caller reaches the program on `right`, which ends the run `Cancelled`.
- **The owner restarting.** With a run under way, `right`'s comm core is stopped: the caller
  gets `Failed`, "the node that runs it went away", and does not wait. A run while `right` is
  away is `unavailable`. `right` is started again on the same port, with its node logic and
  its program: a run from `left` succeeds, with nothing done on `left` in between.

## Different from dev and from the brief

- Dev had its own forward and push messages between nodes and re-ran authorization on the
  target with the original caller's identity carried along. Here there is no such message:
  node logic is a client of the other node. What the other node sees is the peer, not the
  peer's caller, so an action is opened to other nodes as a whole, by admitting peers.
- A run that names a resource on another node is routed by the resource's record. Records
  reach other nodes by peer sync, which is not wired to connections yet (E18), so the test
  routes by node name; routing by resource is the same code after one more lookup.
- Not checked: the other node's key. Pinning it needs the trust store, which is the comm
  core's.

## Also in this commit (E12)

Two things about detached runs, found by running the suite many times:

- A detached run's result was only kept when no caller was attached. A session can end a
  moment before node logic hears of it; the result then went nowhere and was not kept. It is
  now always kept for its starter, ten minutes, given once.
- A caller's run numbers start over with each of its sessions, so a kept result could answer
  an attach meant for a later run with the same number. A new run under a number now
  replaces what was kept under it.
