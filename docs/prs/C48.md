## Different from the brief

- **A client fix on the way.** This PR's gate failed in `connect.rs`,
  `a_tool_with_a_key_signs_its_session_on_a_link`: the test C45 had fixed.
  - Run 48 times at once on two cores, it failed once. A print of the frame showed the cause:
    the reply to the signed hello was a `PONG`. It was the board's answer to the previous
    session's last heartbeat, left unread in the link and read by the next tool as the
    board's answer. C45's wait for the board to have no sessions was not the cause, and it
    did not cure it.
  - A link is a stream that outlives its sessions, so a real serial line can do this too.
    While the client waits for the board's handshake answer on a link, it now passes over
    `PING` and `PONG` (`link_sign.rs`).
  - `link_stale.rs`, `the_last_sessions_heartbeat_left_in_a_link_does_not_answer_the_next_signed_hello`:
    a board that leaves a stale pong before its answer. The tool is told the board's answer,
    and without the fix it is told the board takes no signed sessions.
  - After the fix, the same test run 96 times at once on two cores: none failed.

- **One session dropped, not attributed.** The comm core dropped one command-line session
  because it did not read for 5 s. Which call it was cannot be said: the run removed its logs
  with its directory. The same script on the bench did not do it. The script in the tree now
  keeps its logs, so the next run can say.
- **Security on was not run on the board.** The board has no record, and writing
  `/etc/board/security` is not done under the no-hands rules. The tests cover it, in the comm
  core's own and in C46's.
