# I139: The gate reads its crates from a Cargo home of the repo's own, offline

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I137

Read `AGENTS.md` and `docs/design.md` first.

## Why

Every cargo in a gate read ~/.cargo, which the machine's other projects' builds hold too.
Gates printed up to 47 "Blocking waiting for file lock on package cache" lines (21 to 47 in the
gates before this one), each a cargo waiting on another's hold of that home.

## Changes

- **`scripts/cargo-home.sh DIR`:** the repo's own Cargo home, at `DIR/home`.
  - It is filled by `cargo fetch --locked` in the directory of every lock file in git, the
    examples' and the fuzz targets' among them, and of no other.
  - It is fetched again only when a lock file, cargo or the script changes; otherwise the script
    reads only the lock files.
  - Its config says offline and never cleans the cache.
  - The record, `DIR/fetch.log` and printed in the gate's log, holds:
    - each lock file's sha256;
    - the sources the crates come from;
    - the number of crate files and a sha256 over theirs;
    - the git checkouts.
- **`scripts/cargo-home.sh DIR lane NAME`:** one lane's copy, `DIR/lanes/NAME`.
  - It is a reflink copy (`cp -a --reflink=auto`), made again only when the fetch it was copied
    from is not the current one.
  - It is always at the same path, because test and shipped binaries hold the paths of the crate
    sources they were built from.
- **The gate, with `GATE_CARGO_HOME` set** (scripts/run-gate.sh), unset on CI:
  - it fetches first, as a step before any lane;
  - every cargo reads the home, offline;
  - each lane reads a copy of its own, and so does each feature-matrix shard.
- **The tests step starts its run once the doctests' cargo has its crates.** That is when it says
  it compiles, is fresh, is finished, or runs doctests. Cargo holds a home's package cache lock
  while it reads what to build. The doctests, the run's cargo and the test that builds
  (orion-check's trybuild) share one target directory, so they share one home: one at a time
  there, none waits.
- **The keys hold the Cargo home's config by content, not the home's path.** `CARGO_HOME` is in
  `NOT_IN_KEY`; a config in the home is shown as `<CARGO_HOME>/config.toml`.
  - The size key still holds the path. Shipped binaries hold the crate sources' paths: the
    service-profile `orion` 365 of them, `orion-recovery` 219, `liborion_c.so` 18. So a measured
    size depends on where the home is. Not changed, as ruled.
- **The gate's wrappers' self-test leaves `GATE_CARGO_HOME` unset,** so its practice lanes make no
  copies.
- **testing/fuzz/Cargo.lock is committed** (git ignored it until now). The home is fetched from
  committed lock files only, and the fuzz targets build offline from it.
- **The lane keys' self-test is cheaper.** It had grown to about 17.6 CPU-s standalone (21.7 in a
  loaded gate).
  - A source's strings are read once per text (`string_literals`).
  - The tools' versions (`rustc -vV`, `cargo -V`, `cc --version`) are asked once for each PATH,
    toolchain setting and toolchain file (`version`).
  - The base key is taken in the parent first, so each forked worker starts with both read.
  - The three planted Cargo homes are one job taking the three keys in turn. Folding them into the
    base would have run the cases that list their own tree (`cargo metadata`) in a planted home
    with no crates.

## Proved by

- **A gate with one shared home** for every lane: 21 Blocking lines.
- **Each lane with its own copy:** 6, all in the tests step (the doctests beside the run, then
  beside trybuild).
- **With the run started after the doctests' cargo:** 0.
- **The fetch never reads or writes ~/.cargo:** run with HOME set to an empty directory, it left
  nothing there.
- **Cold fetch:** 50 s wall at load ~100, nice 10. 261 crate files, 4 lock files. A fetch again on
  the same lock files: 4.4 s.
- **Disk:** the home and 12 lane copies are 5.4 GB apparent, 348 MB on disk (btrfs: 347 MB shared,
  about 1 MB exclusive).
- **Self-test plants** (scripts/lane-reuse.py), each against a planted home:
  - another copy of the home, its config the same: the key stays;
  - the home's config changed: the key moves.
- **Mutations, each failing the self-test 3 runs of 3:**

| Mutant | Fails on |
|---|---|
| The home's path in the key, as before (the fail-before) | another copy of the home: the key moved |
| `CARGO_HOME` not in `NOT_IN_KEY` | another copy of the home: the key moved |
| The home's config shown by its path | another copy of the home: the key moved |
| The string memo keyed by a text's length | the strings of the lexer's own cases |

- **The self-test, standalone at nice 10, 2 runs each at load ~65-75:** before, 17.8 and 17.4
  CPU-s, 12.4 and 13.4 s wall. After, 14.2 and 14.7 CPU-s, 7.6 and 9.8 s wall. It prints the same
  assertions. I137's two mutants still fail it 3 of 3, and so do the three above.

The move to the home costs one full build of every lane, because each dependency's source path
changes. The first gates with it took 454 s and 357 s.
