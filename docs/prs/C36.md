## Build

After the comm core restarts, every program connects again and says again what it serves. Until
it has, two things were false:

- the records, which node logic keeps across the restart, still said `Ready` for a resource
  whose provider was not back. A program that did the right thing and waited for `Ready` got
  through at once;
- its run then reached a node with no such action registered, and was refused `not found`,
  the same answer as for a name that never existed.

A bridge's test hit this one time in five: the dashboard saw `Ready` a millisecond before the
provider had reconnected.

## Built

- **The records say it.** When node logic connects to a comm core, every resource of this node
  that is not `Lost` is written with the new state `ResourceState::Restoring` (4). It becomes
  what its provider writes when the provider is back, or `Lost` after the two seconds node
  logic already waited (`RECLAIM_MS`). Watchers and peers see both edges. "Wait for `Ready`,
  then run" is now correct.
- **The error `Restoring` (20)**, "not back yet after a restart: ask again", as the backstop:
  - a run of an action that was registered before the restart and is not again yet;
  - a records read of exactly one resource that was provided before and has no record
    (the records were saved before it was written, the list after);
  - a request on a topic id the comm core never gave out, in its first two seconds, with
    words of its own: "topic ids do not survive a restart: this one is from before it. A
    client that reconnects declares and subscribes again, under new ids". `Topics::restore`
    already does that, so a program on the Rust client never holds a stale id.
  After the window, and for a name never served, the answer is `not found` as before.
- **What "before" means** is `<state dir>/served`: a text file of the actions and resources
  programs served, at most 1024 names. Node logic looks once a second, outside the window,
  and a blocking task writes the file only when it changed, through a rename. A name lingers
  for a minute after its program left. When only the comm core restarted, what node logic was
  serving the moment before counts too, so the file lagging costs nothing.
- **First boot**: with no list nothing is restoring, and a miss is `not found` at once. The
  node served nothing before; a window for everything would make every caller of a name that
  does not exist wait two seconds after each fresh flash, to protect nothing. A list that
  cannot be read is the same case, is logged, and never stops the start.
- **Level 2.** `INTERFACE_LEVEL` is 2. An error code has a level like a feature: a session
  below level 2 is told `not found` where a level-2 session is told `restoring`
  (`orion_server::spoken`, used by the comm core's refusals, by `Cx::refuse`, and by the relay
  for node logic's refusals). So an R2 client never sees code 20; it would have read it as an
  unknown code. The state `Restoring` is not gated: an older program reads it as a state it
  does not know, which is not `Ready`, and waits.
- `Cx::refuse(error, detail)` lets a service refuse with words of its own.

## Proved by

- `node-app/tests/restoring.rs`, five tests against a real comm core and node logic:
  - the comm core restarts: the record is `Restoring`, a run of what was served is
    `Restoring`, a run of what never was is `NotFound`, a watcher is told `Restoring` then
    `Ready` when the provider returns, and the run is then taken;
  - the provider does not return: `Lost` and `NotFound` after the wait;
  - the whole node restarts: the list is read from the state directory;
  - a first boot and an unreadable list: `NotFound` at once, and the node starts;
  - a read of one resource that is on the list and has no record.
- `served.rs` unit tests: the window, the linger, the bound, a broken list.
- `broker.rs`: a stale id is `Restoring` with its words for a level-2 session, `NotFound` for
  one below, `NotFound` for an id that was given out, and `NotFound` after the window.
- `relay` and `server` unit tests for the level rule.
- 18 mutations, 18 caught (`c36-mut.py`): each condition above removed or inverted fails a
  test.
- The node-app suite was run 6 times.

## Different from the brief

- The brief asked for the typed error. The records turning `Restoring` was added on review:
  it is the main path, and the error is the backstop.
- `Restoring` on a records read covers only a read of exactly one resource with no record. A
  resource that has a record answers with its state, and a read by prefix is answered as it
  is.
- The gate is on the server side, by the session's level, not a client-side `Feature`: there
  is nothing for a client to ask for. An R2 client therefore reads `NotFound`, not `Internal`.
- Node logic's own action (`files.send`) is on the list like any other. It is registered again
  as soon as node logic connects, so it is never asked for in the gap.
