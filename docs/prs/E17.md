## Built

- `crates/node/audit` (`orion-audit`): `Audit::start`, `record`, `flush`, `dropped`,
  `written`; `Entry` and `Who`; `AuditConfig`.
- `orion-node-app` records each changing request it is passed, with settings `audit.file`,
  `audit.max_bytes` and `audit.keep`. On by default, in the state directory.

## Proved by

- `crates/node/audit/tests/audit.rs`:
  - Rotation under load: four threads record 20 000 entries each as fast as they can into a
    log capped at 16 KiB with three kept. Afterwards there are exactly four files, none over
    the cap, each ending between lines; every line is a whole object; each thread's entries
    are in order across the files; written plus dropped is exactly what was recorded; and no
    call to `record` took a quarter of a second, with the slowest far below. About 600 000
    lines a second reach the disk on the development PC.
  - A line stays one JSON object with quotes, newlines and control characters in it.
  - The log goes on in the file that was there; with one kept the older goes; with none kept
    the file is emptied.
- `crates/node/node-app/tests`: a put and a delete from a program appear as two lines with
  its user id and the keys, and a read does not; the action test finds the two registrations
  and the two runs that passed, and no line for the run the check refused.

## Different from the brief and from dev

- "At the check": the check is in the comm core and the log is node logic's, and the two
  tiers do not depend on each other. What is logged is what the check let through to node
  logic, with the caller as the comm core named it. A refusal at the door is not in the file;
  for that the comm core would have to pass refusals on, which it does not yet.
- Dev logged trust events (enrollment, revocation, TLS) from the node. Those are the comm
  core's here and are not in this log either.
- Dev's log had no cap.

## Also in this commit

The file resume test from E13 asked for more than is true: a sender whose session vanishes may
lose its last frame in flight. It now waits until what is on disk has stopped growing and
checks that the second push goes on from exactly that. 80 runs in a row pass.

## Later (with E18)

The load test asked for four files after the flood alone. On a slow machine nearly every
entry of the flood is dropped, as it should be, and too few were written to fill four: CI
failed there once. The test now follows the flood with 2 000 entries at a pace the writer
keeps up with, so the rotation it checks does not depend on the machine.
