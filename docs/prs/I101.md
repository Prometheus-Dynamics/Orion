## Changes

`crates/comm/link-usb/tests/usb.rs`, `docs/flakes.md`, `docs/lock.md`, `TODO.md`.

## Why

`orion-link-usb` `a_link_runs_over_whatever_the_hardware_owner_hands_over` failed once, at a
gate with the machine's load at 106 to 122: `AllocCount { allocs: 3, deallocs: 9, bytes: 368 }
in 2000 heartbeats over endpoints`, where none was due.

## What allocated

Caught with a probe allocator that kept a backtrace of each allocation on the test's thread
inside the window, with the owner's idle time made to run out there: all three were
`orion_server`'s `say_dropped`, the comm core noting a session it ended.

- 8 bytes: the session's name, `hardware`, copied;
- 8 bytes: its principal as text;
- 352 bytes: the first record in the comm core's list of ended sessions (4 of 88 bytes).

The session ended was the test's hardware owner. The test connected it as a client from
elsewhere, and it says nothing while the device pings, so once the comm core's idle time
(three 2 s heartbeats) had passed it was dropped as gone. Run quickly, the test was over
before then; at the gate's load it took 9.6 s, and the drop fell in the counted window.

## Not the product's

The program that owns the hardware is a program on the board, and a quiet session of a
program on the board is kept, not dropped: its socket says when it is gone. That path was
forced into the window (the owner connected as a program on the board, its idle time running
out in the window, seen by its session's `quiet_since`), and it allocated nothing. Ending a
session is not the steady state the test is about, and the counting is not changed.

## Built

- The owner is connected as a program on the board (`MemConnector::connect_local`), as it
  is on a real one.
- The board's heartbeat is 200 ms, so its idle time is the 1 s floor. The owner pings just
  before the endpoints' window (it is not quiet at the start, checked), and the window begins
  with 1.5 s of slow pings: the owner goes quiet inside the window in every run, checked
  after the count.

## Tests

`a_link_runs_over_whatever_the_hardware_owner_hands_over`, as changed: 3 of 3 pass. With the
owner connected as before (from elsewhere), 3 of 3 fail with the gate's numbers exactly,
`AllocCount { allocs: 3, deallocs: 9, bytes: 368 } in 2000 heartbeats over endpoints`.
`orion-link-usb`: 10 of 10.
