## Build

- A consumer's tests run the real comm core and node logic in the test's own process. The
  stubs have no hook for refusals, and a consumer needs to see them.
- Say whether `orion-stubs` can shrink or go.
- Document it for consumers.

## Built

- **`orion-test-board`** (`crates/testing/test-board`, Linux only). `TestBoard::start(name)`
  runs a board in a directory of its own under the system's temporary one:
  - the comm core as `orion comm` assembles it (`start_or_recover`, so `CommCore::start`),
    in a thread with a current-thread runtime and a `LocalSet`;
  - node logic as `orion node` runs it (`Node::load`, `run`), in a thread of its own;
  - one `orion.conf` text read by both, with node logic's `Config` taken from the comm core's,
    so both have the same switch from the same record.
  - The user running the test is named in `socket.node_uids`, as root or the service's user
    is on a board.
  - `start` returns once node logic answers: a client reads records without being refused.
  - Dropping it stops node logic, then the comm core, and removes the directory.
- **`Options`**:
  - `name`;
  - `security`: no record, `Off`, `On` or `Damaged`, written to the board's directory and read
    through `from_source_with_view`;
  - `network`: the network and WebSocket ways in on 127.0.0.1 at free ports;
  - `heartbeat_ms`;
  - `node`: node logic or not;
  - `operator`: a public key seeded as `operator.seed` (C32a), so a test has a trusted
    operator with security on;
  - `conf`: more `orion.conf` lines. A key set there replaces the board's own line, since the
    last line for a key wins.
- **Taking parts away.**
  - `stop_node` and `start_node`: node logic goes, what is its is refused `unavailable` by the
    real relay, and it comes back with what it saved.
  - `start_in_recovery(name, options, why)` runs `recover`, the real recovery way in, on the
    board's socket, with recovery's SSH on 127.0.0.1 (`recovery_ssh()`).
  - Settings that parse but stop the comm core from starting go to recovery, as on a board,
    and `state()` says `Recovery(why)`.
  - Settings that do not parse panic the test: recovery would then serve the board's usual
    socket.
- **`docs/testing.md`**: for consumers. How to depend on it, what it is, its options, taking
  parts away, and where `orion-stubs` still fits.
- **The stubs (the question asked).** `orion-stubs` cannot go, and shrinks only once the
  client's tests move off its stand-ins.
  - Node logic's own twelve test files need a comm core, and node logic may not depend on the
    comm core, not even for tests (`check-boundaries.sh`: comm and node never depend on each
    other). They use the stubs with no stand-ins (`for_node`).
  - `orion_stubs::older` stands in for a node of an older revision. A real board cannot be
    one.
  - The client's tests (connect, ctl, provider, the C library, the web tests, the facade) use
    the stand-ins. They could move to the test board one by one, and the stand-ins would go
    once none use them. That is not in this brief.
- **A warning fixed on the way.** `recovery_comm.rs` built its `serve` closure even without
  `link-usb`, the only feature that uses it. Building this crate on its own (`-p
  orion-test-board`, which takes the comm core's default features) warned about it. It is now
  under `#[cfg(feature = "link-usb")]`.
- **PARKED, now decided.** The two PARKED sentences in `docs/prs/C38.md` (any session may
  free a lease) and `docs/prs/C39.md` (the other ways in retrying) say what decided them.

## Proved by

- `crates/testing/test-board/tests/board.rs`:
  - `a_board_answers_as_a_board_and_node_logic_can_go_and_come_back`: the hello document
    (name, `running`, security off with no generation); node logic answers; without it
    records are refused `unavailable`; it answers again after `start_node`; the directory is
    gone after the drop.
  - `with_its_record_on_the_board_checks_and_refuses_as_a_board_does`:
    - with `On`, the hello says `On { generation: Some(1) }`, a network client with no key is
      refused, and the seeded operator is let in over the same way;
    - with `Off`, the same stranger is let in, and the hello says `Off { generation: Some(1) }`;
    - with `Damaged`, the hello says `Damaged`.
  - `recovery_is_the_real_recovery_and_a_comm_core_that_cannot_start_goes_there`: forced
    recovery says `recovery` and its reason in the hello document, has no node logic, and its
    SSH listens. A keys directory under `/proc` sends the comm core to recovery with
    `keys.dir …` as the reason.
  - `settings_that_do_not_parse_are_the_tests_fault_not_a_recovery`.
- **Mutations.** `/mnt/nvme-wd/scratch/c46-mut.py` made 8, and all were caught: the `On`
  record written as off, the damaged record written well-formed, the seed not written,
  `stop_node` doing nothing, not waiting for node logic, forced recovery ignored, the
  directory kept, and the network way in not opened.
- **Runs.** The crate's tests ran 3 times in a row, all passing. Workspace clippy with
  `-D warnings` is clean. The gate passed.

## Different from the brief

- **Node logic's switch is the comm core's `Config`, not read again.** Both read the same
  text. Node logic's `Config` is replaced by the comm core's, so the security record is read
  once and both parts have the same view, as the relay gives node logic on a board.
- **Settings that do not parse panic, not recover.** On a board, recovery then serves the
  usual socket, which here would be outside the test's directory.
