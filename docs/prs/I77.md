## Why

A board on a desk or a network should be found by its name, with no address typed: by a PC's
browse for Orion boards, by `ssh <name>.local`, and by the peers of its cluster. Until now the
image announced nothing. Discovery could announce over `mdns-sd`, but it is not in the image,
and its record said nothing of the board's state or security.

## Built

- **`orion-mdns`, a responder written for what the board needs.** It handles DNS messages
  (questions, and A, AAAA, PTR, SRV and TXT records, with name compression read and loops
  refused), probing, announcing, answering and saying goodbye, written without its sockets so
  that tests drive it with a clock. The comm core runs it as a task.
- **A socket on each interface**, port 5353 shared with any other responder on the board, joined
  to the group on that interface by index and kept to it by name. The interfaces are looked at
  every 2 s: a new one gets a socket and is announced on, one that went or was made again under
  its name is opened again, as the ways in follow theirs (I72).
- **Announced only where it can be reached.** Each service is announced on the interfaces where
  its way in can be reached: the address it listens on (or every one) and the interfaces it is
  kept to. Loopback alone, or no way in, announces nothing, not even the name. This also keeps
  every test that starts a comm core on 127.0.0.1 off the network.
- **Name claimed, and defended.** Three probes a quarter second apart, then two announcements a
  second apart (RFC 6762 §8). Another answering for the name makes it `<name>-<4 hex>`, the
  first four hex digits of the key's fingerprint, probed for again. Two probing at once are told
  apart by their records (§8.2), and the lesser waits a second. A probe for a name it holds is
  answered at once. Answers are held 20 to 120 ms when they carry shared records, a record goes
  to the group once a second at most, an answer the asker already has is left out, and a plain
  DNS client is answered alone with its id and short lives (§6.7). What comes from its own
  addresses is its own, come back.
- **The services:** `_orion._tcp` at `peer.listen`, `_ssh._tcp` and `_sftp-ssh._tcp` at
  `ssh.listen`, and `_services._dns-sd._udp` listing them. The same with security on or off.
  `mdns = false` silences it; `mdns.interface` limits it. Recovery does not have it.
- **One `_orion._tcp` record for peers and for clients.** Layout 2, with `level`, `state` and
  `security` added by name. A layout-2 reader, which leaves keys it does not know, reads it
  whole; a test reads the record with discovery's own parser. With the responder built in,
  discovery browses only (`MdnsDiscoveryBackend::browse_only`), so there is one announcer.
- **A cluster name too long to carry** (over 252 bytes) withholds `_orion._tcp` alone. The
  name and SSH are still announced, the log names the setting at start, and `orion/state` says
  it under `mdns:`.

The TXT contract, for a client's browse, is in `docs/comm.md`, "Announced by name (mDNS)".

## The TXT record's size

Each entry is one length byte and its text, at the longest values:

| Entry | Bytes |
| --- | ---: |
| `v=2` | 4 |
| `id=` (63-byte name) | 67 |
| `pk=` (64 hex) | 68 |
| `wv=255` | 7 |
| `rev=65535` | 10 |
| `cl=` (252 bytes) | 256 |
| `tcp=65535` | 10 |
| `level=65535` | 12 |
| `state=flasher` | 14 |
| `security=damaged` | 17 |
| **Total** | **465** |

With a 16-byte cluster it is 229. The whole answer to a browse (PTR, SRV, TXT, A and AAAA, names
whole) is about 800 bytes, against the 1472 a 1500-byte packet carries.
`the_orion_txt_record_fits_and_an_older_reader_reads_it` holds the record to 465.

## Size

aarch64 `orion` (service profile, musl), each tree built in a target of its own:

| | Bytes |
| --- | ---: |
| I76 (7fc2a39) | 5,408,344 |
| I77, first build | 5,504,032 (+95,688) |
| I77, after the cut | 5,487,024 (+78,680) |

The estimate was 30 to 60 KB. It counted the responder's code but not the unwinding tables,
which in this profile add about 40% on top of code, or the generic code from `std` it brings.
The limit is raised from 5,430,000 to 5,510,000, with 22,976 bytes over.

**Cut first** (−17,008): its sockets, its announcement times and its record times in linear lists
(a handful each), not hash and B-tree maps; no sort of an interface's addresses; the tie-break's
sort unstable; three `debug!` lines with fields (a message not read, not sent, a read failing:
each is dropped as the network drops, and asked or announced again).

## Tests

- `orion-mdns` (`tests/all.rs`): `respond::` (19, the responder driven with a clock: probing and
  announcing times, losing a name to an answer before and after it is claimed, its own echo and
  a goodbye being no rival, the simultaneous-probe tie both ways, browse answers with their
  additional records and delay, known answers, plain DNS clients, `QU` questions, the once a
  second limit, defending against a probe, each interface's own addresses, a new interface
  announced on, a service only where it can be reached, goodbye, a long name's fallback,
  messages read back, pointers and loops, the TXT record's size and an older reader of it)
  and `namespace::` (1, real sockets in a network namespace with a veth pair: answered on the
  interface it was given and not on another, a second responder for the name answered and
  taking `cam-bbbb`, the pair taken away and made again and answered again, goodbye).
- `orion-comm-app`: `announce::` (1, in a namespace: the record the comm core says of itself,
  key for key; SSH and SFTP at the SSH port; nothing with `mdns = false`; a too-long cluster
  withholding `_orion._tcp` alone), `own_files::a_cluster_too_long_to_announce_is_said_in_the_state`
  and `own_files::ways_in_on_loopback_alone_are_not_announced`.

Each mutation: the test binary rebuilt (its hash changed), the named test run 3 times through
`scripts/bounded.py`, the source put back with `command cp -f` (its hash checked).

Two mutations passed at first, and the tests were made to see them. Without `bind_device` the
test passed because nothing in the namespace was in the group on `mdc`, so the kernel took
nothing there. With a socket in the group on `mdc`, the kernel hands the group's packets on
`mdc` to every socket in the group (`IP_MULTICAST_ALL`), and only `bind_device` keeps them
from the responder. The test of a start with nothing to announce looked before a responder
could have claimed a name. It now waits 1.5 s, and has a loopback-only case of its own.
