# I118: The size gate's self-test in seconds; the feature matrix measured

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I117

Read `AGENTS.md` and `docs/design.md` first.

## Why

The one-minute rule (2026-11-24). The size gate's self-test runs whenever `scripts/size-gate.sh`
or `scripts/size-key.py` changes, and took 40 to 180 s at load. On its own it nearly used up a
gate's minute. The feature matrix was next on the list, at 158 CPU-s on a core change.

## Changes

- **`scripts/size-key.py` lists the files once.** It used to run `git ls-files` once for each
  directory in each build's closure: 298 runs for five builds, 3.9 s of 6.1. Now one listing is
  filtered by directory. On this tree the inputs are the same, all 2,141 lines of `--explain`,
  apart from the script's own digest. A key now takes 1.4 to 2.9 s wall and 1.0 CPU-s, from 6.7
  to 7.9 s and 3.7 CPU-s (load about 90, nice 10).
- **The self-test takes its keys all at once.** Each case runs on a copy of its own, and a key
  does not depend on where the source is (the test's first check). Its 21 key runs used to go
  one after another. The CI-only cases reuse the outputs of the core and notes cases. One case
  is new: a new file in the notes changes no key.
- **`scripts/matrix-ab.sh ROUNDS N...`** is an A/B of the feature matrix's shard counts. It runs
  `scripts/feature-matrix.sh` whole on a comment in `orion-types`, each count in its own
  target, the order rotating.

## Proved by

- **Mutants of the self-test,** 3 runs each, all red:
  - crates' files left out of a key (16 cases red);
  - only tracked files listed (17 red);
  - the planted change not applied (47 red).

## Measured

The size gate's self-test, at nice 10:

| Version | Wall | CPU-s | Load |
|---|---|---|---|
| Before (I117) | 83 and 180 s | 44 and 45 | 109 and 119 |
| One listing, keys one after another | 53 and 53 s | 19 and 21 | 118 and 136 |
| This change | 6.0 to 10.5 s | 17 to 19 | 97 to 107 |

The feature matrix on a core change, 6 shards (as now) against 3, rounds 2 to 4 (round 1
warmed), load 89 to 121, nice 10:

| Shards | CPU-s | Wall | Median CPU-s | Median wall |
|---|---|---|---|---|
| 6 | 112, 150, 128 | 31, 103, 126 s | 128 | 103 s |
| 3 | 106, 122, 108 | 69, 163, 215 s | 108 | 163 s |

Three shards save a sixth of the CPU and add a minute of wall, so 6 are kept. All of a crate's
builds in one shard was tried too, and it rebuilt more: 520 crates checked against 421 by the
first count. That first count turned out to be low: with `-v`, both layouts dirty 823 units.
Its comparison was dropped, and only the whole-script A/B above is used.

A no-op matrix, nothing changed, costs 27 CPU-s at load 92 (110 cargo calls). The gate does not
run one: a build that passed before on the same inputs is skipped by its record.
