## Build

- Topics to NT4 and back, as a server.
- Names and types are a mapping given in config. Nothing competition-specific in the code.
- An expiry rule for values that expire.

## Proof

A real NT4 client sees mapped topics and writes one back.

## Built

- `crates/gateways/nt4-gateway` (`orion-nt4-gateway`): an NT4 server inside the comm core.
  `nt4.publish` names the fields that go to NT4 and `nt4.accept` the NT4 topics whose
  values come back, each `topic:field=type@name`. Every `nt4.period_ms` the gateway reads
  the newest sample of each mapped field from its ring and sets the NT4 topic if it is
  newer. What NT4 clients write to accepted names is published as topics the comm core
  declares itself, one field for each mapped name.
- The expiry rule: a topic declared with an expiry has its NT4 topic deleted when its
  newest sample has stood longer than that, and announced again with the next sample. A
  topic without an expiry keeps its last value in NT4.
- Conversions in `convert.rs`, both ways, by the field's type and the NT4 type string. A
  pair that does not go together is refused and said once.
- `orion-comm-app` feature `nt4` (on by default): settings `nt4.listen`, `nt4.period_ms`,
  `nt4.publish`, `nt4.accept`, `nt4.max_payload`. No gateway unless `nt4.listen` is set.
- `examples/nt4-gateway-demo.rs` and `interop/run.sh`: the check against ntcore.

## Proved by

- `crates/gateways/nt4-gateway/interop/run.sh` passes against `pyntcore`: an ntcore client
  sees `/Tank/level` as a `double` that follows the board's topic, and the `/Panel/setpoint`
  it writes is published on the board as `panel.setpoint`.
- `cargo test -p orion-nt4-gateway`, with a real comm core and the NT4 client of
  `orion-nt4`: three mapped fields are announced under their NT4 names and types (double,
  boolean, `struct:Shape`) and their values follow; an alarm with a 300 ms expiry is
  announced, withdrawn after it has stood that long, and back with the next sample, twice;
  two values written back arrive on the board as the mapped fields; a value of the wrong
  type from a second client is not published and the next good one is; a topic that is not
  mapped, a mapped one nobody publishes and a field mapped to a type it is not are never
  announced. A mapping that does not hold together is refused with the reason.

## Different from the brief

- The product's `nt4.rs` was not read: it is another repository. The mapping is this design's.
- The gateway has its own port (`nt4.listen`, NT4's is 5810), which is where NT4 clients
  look. `Server::take` (F6) lets it share the WebSocket listener; that is not wired.
- It reads at a period and is not woken by publishers: NT4 carries latest values, and a
  publisher pays nothing for the gateway.
- Expiry is counted from when the gateway read the sample, on its own clock, not from the
  sample's time: a publisher's times need not be on the board's clock.
- `boolean[]` and `string[]` have no field type here and cannot be accepted or published.
- The interop script is in the crate and not in the gate, as F6's.
