## Built

### The +36% was two days, not the code

I6 and next were run on the same test board in one run, each under I6's own setup (comm core,
node logic, the drill workloads), with the code each touched counted the same way: pages of
the binary resident in each process after `clear_refs` and 10 s of steady work.

| Build | comm core used | node logic used | Total used | Code mapped | Data |
| --- | ---: | ---: | ---: | ---: | ---: |
| I6 (`1fa0ca7`) | 1,135 KiB | 376 KiB | 1,511 KiB | 2,866 KiB | 1,618 KiB |
| next (C49) | 1,243 KiB | 443 KiB | 1,686 KiB | 3,322 KiB | 1,810 KiB |

Code in use grew by 175 KiB (+11.6%). The 1,345 KiB I6 figure came from a different day and
a different board state; side by side, the gap is a third of what C48 suggested.

This is the same picture as C41's account of I6 to C40, which looked at every symbol over
1 KiB and cut the two that were copies: the growth is features (leases and contests, peers,
placement, the shell, the serial and USB links, record sync, the ways in that try again), and
the generic code they instantiate. C42 to C49 added little: on x86_64, `.text` went from 4,331,559 bytes after C41's cut to
4,335,079 (+3,520 bytes).

### Is it needed

Yes, by C41's account, which this run confirms on the board. Code in use grows by about as
much as the code does (+11.6% against +11.1%): nothing large was added that runs without
being asked for. The budget stays where it is.

### Which symbols, per page

`orion-drill pages mark|read <pid> <file>` marks a program's code pages idle and reads back
which it touched (the kernel's idle page tracking and `/proc/<pid>/pagemap`), and
`scripts/code-used.py` joins those pages to a build with symbols, by crate and by symbol.
The test board's kernel has neither `/sys/kernel/mm/page_idle` nor the accessed bit in
`kpageflags`, so the per-symbol attribution could not be run there. It needs
`CONFIG_IDLE_PAGE_TRACKING` in the image; when an image has it, the run is one command.

## Proved by

- **The board run** above: one run, the same board, both builds, the same setup.
- **`pages.rs`** has a unit test reading its own process's code pages: every page of its
  executable mapping, page aligned, stepping by the page size, and starting at the file offset
  the kernel's map gives. Two mutations, both caught: pages skipped, and offsets counted from
  the mapping instead of the file. On the bench, `code-used.py`
  over every page of a build adds up to its `.text` (16,696 KiB against the section's size).
- **Runs.** The gate passed.

## Different from the brief

- **No per-symbol account of what is touched.** The board's kernel cannot say. The static
  account by crate, and C41's by symbol, stand in for it.
