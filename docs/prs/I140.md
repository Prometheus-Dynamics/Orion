# I140: shm-fdpass at 98fbe0c2: a frame cut short is the peer closing, and said

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I139

Read `AGENTS.md` and `docs/design.md` first.

## Why

I138 made the Unix carrier take a partial frame after the peer hung up as the peer closing. It
did so by seeing the hang-up beside shm-fdpass's "would block", because shm-fdpass said "would
block" for ever there.

shm-fdpass 98fbe0c2 says it itself: `RecvError::ShortRead`, when the peer hung up with part of a
frame queued, blocking or not. The carrier made `ShortRead` an error ("the peer closed inside a
frame", InvalidData), so with the new rev alone a program that dies mid-send was an error, not a
close.

## Changes

- **The shm crates move from 214c0ca to 98fbe0c2,** all seven, one rev of the one git repository they come from.
  Under `shm/` only shm-fdpass's source changed between them; the others changed only in their
  tests. Every lock file in git moves with them: the root's, and the examples' and the fuzz
  targets' (which use shm-sample-time). A first gate found those three still at 214c0ca: the
  Cargo home's `cargo fetch --locked` refused them (I139 doing its job).
- **The carrier's receive takes `ShortRead` as the peer closing (`Ok(None)`).** I138's arm for a
  hang-up beside "would block" stays, for a shm-fdpass before 98fbe0c2.
- **Both say so in the log** (`tracing::warn!`, "a connection closed inside a frame: the part of it
  sent is dropped"), so a message cut off is not lost unseen. orion-unix now depends on tracing
  (already in the workspace).
- **A carrier test, `a_peer_that_hangs_up_inside_a_frame_has_closed`:** a peer sends a frame's
  length (100) and 10 of its bytes and hangs up. The receive says closed within 5 s, not an error
  and not a wait.

Nothing on the wire changes, and nothing a program calls.

## Proved by

- **Fail-before:** with the new rev alone, the carrier test fails 3 of 3:
  `closed, not an error: Custom { kind: InvalidData, error: "the peer closed inside a frame" }`.
  - I138's file-offers test still passes then. The comm core ends the session on that error as on
    a close, so the client is told the same.
- **Pass-after:** the carrier test passes 3 of 3, and so does I138's
  `fetch::a_program_that_dies_inside_a_frame_is_gone_and_the_comm_core_serves_the_others`. The
  orion-unix and orion-file-offers tests all pass.
- **Mutation:** without the `ShortRead` arm, the carrier test fails 3 of 3 (InvalidData, "a
  malformed control message").
