## Build

1. **Three board targets in the size gate**: aarch64, armv7 (`musleabihf`) and riscv64gc, static
   musl, `orion` and `orion-recovery` each. A target is built where its Rust target is installed
   and a C compiler is found for it (the SSH way in brings `ring`): `CC_<triple>`, or
   `scripts/zigcc/<triple>` when `zig` is on `PATH`, with `-ar` wrappers for archives. Linked by
   `rust-lld`. armv7 and riscv64 build and are gated; neither has run on a board.
2. **riscv64 is static** through `.cargo/config.toml` (`+crt-static`): that target links
   dynamically otherwise and fails. `chacha20_force_neon` stays for aarch64, with the reason it
   has now (sealed links), not dev's (the `tcp:` link channel, gone).
3. **BusyBox init** (`packaging/busybox/`): `S40orion-comm` and `S41orion-node`, and a supervisor
   (`orion-supervise`) with the units' failure rule (1 s doubling to 30 s, never giving up), clean
   stop (TERM, 30 s, KILL), the comm core's socket given to `orion`, node logic as `orion`.
   What is lost without systemd is listed in `packaging/README.md`.
4. **A flasher's recovery.** `orion-recovery` has the USB link (`link-usb`), so a board in a
   flasher image is reached over its gadget. `S40orion-recovery` starts it with BusyBox init;
   `orion-recovery.conf.example` names the USB link, SSH on the gadget's network only, and
   security off while the cable is the only way in. The README says what recovery does with no
   settings file (SSH on port 22 of every address, security off) and when that is not enough.

## Proved by

- The size gate builds and gates all three targets here, each `statically linked`.
- `packaging-check.sh`: every BusyBox script parses (`sh -n`); the supervisor, given a binary
  that ends at once, starts it three times in 4 s (after 1 s, then 2 s) and stops on TERM.
- `crates/bins/orion-recovery/tests/binary.rs`, `the_flasher_example_is_read_whole_and_starts`:
  the shipped example is read with no unknown key, starts as it says (not in recovery), and with
  security off lets SSH in without a key. With an unknown variable added it fails.
- On the test board (aarch64), the scripts were run under BusyBox: backoff, TERM stop, the
  socket `root:orion`, node logic as `orion`, the comm core started again after a kill.
