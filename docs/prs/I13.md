## Build

- **Incremental.** The gate set `CARGO_INCREMENTAL=0` for every step, from the skeleton, with no
  reason given. A change then rebuilt each workspace crate it touched whole, in clippy, the tests
  and the checks.
- **The GPU.** The web tests' headless Firefox, which plays the video example and runs the web
  client, opened this machine's GPU (`/dev/dri`). Tests must not load the desktop GPU.

## Built

- **Incremental where it is not measured.** The gate no longer sets `CARGO_INCREMENTAL`: debug
  and test builds are incremental, cargo's default. The steps whose output is measured set it to
  0 themselves, whatever the caller set:
  - the size gate and the device size measure bytes of a build made whole, as it ships;
  - fuzz builds as cargo-fuzz does.
- **Software only.** Before it starts, the test's Firefox gets a profile `user.js` that turns
  off:
  - WebRender on the GPU (`gfx.webrender.software`);
  - acceleration (`layers.acceleration.disabled`);
  - canvas acceleration;
  - WebGL;
  - hardware video decoding, and VA-API.

  Both browsers start with `LIBGL_ALWAYS_SOFTWARE=1`. Chrome, the fallback, adds
  `--disable-gpu-compositing` and `--disable-accelerated-video-decode` to `--disable-gpu`.

## Proved by

- **Incremental, timed against not, interleaved.** Each side had a target directory of its own,
  warmed first. Times are clippy plus building every test, at load 70–100 (s):

  | Change | Round 1 | Round 2 |
  | --- | --- | --- |
  | `orion-comm-app` | 15 → 7 | 90 → 16 |
  | `orion-wire` | 48 → 45 | 37 → 25 |

- **No GPU.** While `orion-web-tests` ran, every test Firefox process's descriptors were read.
  - With the settings, 0 of 2 held `/dev/dri`, and the 4 tests passed.
  - Without them (mutation), 2 of 2 did.
  - Nothing else in Orion opens a GPU: no wgpu, Vulkan, GL or EGL, and no test names a DRM
    device.
