## Changes

`src/lib.rs` of each crate under `crates/comm` and `crates/node` (47), `docs/prs/I92.md`,

## Why

A panic in a handler is contained and counted (I92), so this is hardening. There is no
`.unwrap()` outside tests in either place today. The lint keeps it that way for nothing.

## Built

- **`#![cfg_attr(not(test), deny(clippy::unwrap_used))]`** at the top of each of the 47
  crates' `lib.rs`. Tests are left as they are. A planted `unwrap()` in `orion-hello`'s handler
  is refused by clippy; taken out again, clippy is clean.
- **`docs/prs/I92.md`'s table is corrected.** It said 16 `.unwrap()` and 108 `.expect(` in the
  comm core, and 0 and 18 in node logic. Those counts took in the test modules inside source
  files. Outside tests there are 0 and 6, and 0 and 1.

## The seven expects, each read

None can fail on what a peer sends.

| Where | Why it cannot fail |
| --- | --- |
| `comm/server/src/service.rs`, `Cx::caller` | the caller's session is there while its request is handled. It would fail only if a service ended its own caller's session and then asked for it: a service's bug, not a peer's input |
| `comm/server/src/driver.rs`, a session just opened | opened a few lines above, with nothing between |
| `comm/tcp/src/lib.rs`, the server's hello | the first 96 bytes of an array that is longer; the dialling side |
| `comm/comm-app/src/recovery_comm.rs`, two | start-up, on constants: a name that is one, a key kept nowhere |
| `comm/recovery/src/lib.rs` | start-up: a trust store that keeps nothing |
| `node/files-sink/src/lib.rs` | the transfer was looked up a few lines above, in the same call |

`clippy::expect_used` is not denied: each of these would need an allow with this reason beside
it. `clippy::indexing_slicing` is not denied either, and nothing has been read for it: I95.
