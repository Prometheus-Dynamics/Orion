## Build

As ruled: the precheck `0xB0`/`0xB1` now, so the device library can stop refusing "on" because
Orion cannot be asked. The writer (`orion node security on|off`), the signed turn-off and live
apply are not here: the writer and the signed turn-off are C32c, live apply its own follow-up.

## Built

- **Wire.** A new concept, `Security`, `0xB0` to `0xBF`, because the session and node ranges
  are full. `SECURITY_PRECHECK` (`0xB0`) carries `to: SecurityTo` (`On` 1, `Off` 2).
  `SECURITY_PRECHECKED` (`0xB1`) carries `request_seq` and `lines: List<PrecheckLine>`, each one
  line in the words of `system.security-precondition/1`. `INTERFACE_LEVEL` is 5, and
  `Feature::SecurityPrecheck` is at 5. A client asks it only of a node at 5 or above;
  below, `ClientError::Level` and nothing is sent.
- **The answer** (`crates/comm/comm-app/src/precheck.rs`, a service in the running comm core
  and in recovery).
  - **To on.** One `missing: orion: nobody but root could get in once it is on: enroll an
    operator, add a key to <recovery keys file>, or set enrollment.key` unless one of these exists:
    - an enrolled operator, not pending and not revoked;
    - a key the recovery keys file lets in, read when asked;
    - `enrollment.key`.

    In recovery the trust store is not opened, so only the recovery keys file counts.
  - **To off.** Nothing. Whether the turn-off is authorized is the writer's to check (C32c).
  - **Never `busy`.** Orion installs and tries nothing a turn would cut short.
  - **An unknown `to`** is refused as malformed.
- **Who may ask.** `What::Read("security")`, for programs on the board (the bridge) and for
  operators granted read.
- **Client.** `Orion::security_precheck(to) -> Vec<String>`, `node::SecurityTo`.

## Proved by

- **`tests/precheck.rs`.**
  - `turning_it_on_needs_a_way_in_other_than_root_and_turning_it_off_needs_nothing`, against a
    running comm core:
    - with no way in, one line naming the recovery keys file, and nothing against off;
    - a key written to the recovery keys file counts at once, and a line that is not a key does not;
    - a flash-seeded operator counts;
    - `enrollment.key` counts.
  - `recovery_answers_from_its_recovery_keys_alone`: in recovery, with `enrollment.key` set, the
    answer is still "missing" until the recovery keys file names a key.
- **The unit test** `only_an_enrolled_operator_is_a_way_in`: a pending operator is not a way in,
  an approved one is, and a revoked one is not again.
- **The wire vectors** for both kinds are recorded.
- **Mutations.** `/mnt/nvme-wd/scratch/c32b-mut.py` made 6, and all were caught:
  - off answered like on;
  - the enrolled operator dropped;
  - any operator counted, whatever its state;
  - the enrollment key dropped;
  - the recovery keys file dropped;
  - any readable recovery keys file counted, key or not.
- `own_files` now expects `interface_level 5` in `orion/version`.

## Different from the brief

- **The words name no tool.** The proposal said "enroll an operator (orion keys)". The command
  line has no `keys` verb, so the words say "enroll an operator" and name the recovery keys file
  by its path.
- **A test fixed on the way.** The gate failed `a_watcher_that_falls_behind_catches_up_and_misses_no_record`
  (`orion-records`) with a broken pipe. Its comment said the watcher's session keeps turning, but
  nothing turned it, and under load the writes outlasted `comm.write_ms`, so the comm core dropped
  the session as stalled. The test now pumps the session between writes. Its board has `write_ms`
  300 and the writes pause, so the stall would happen on every run: without the pump it fails 5
  of 5, and the binary passes 30 of 30 under load. `docs/flakes.md` has it.
