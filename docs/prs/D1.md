## Proof

The same test runs on local and network addresses.

## Built

- `orion-connect`: `Session::connect(address, name, options)`. An `Address` is the board's
  socket, `orion+tcp://host[:port][#key]`, or `serial:<path>[@baud]`; `Session::over_link` takes
  a link someone else opened. The calls are the same on all of them: `send`, `send_with_fds`,
  `next`, `answer`, `take_fd`, `as_fd`.
- Blocking, with no thread and no timer of its own. `next` does the housekeeping while it
  waits: answers pings, sends its own, and reports the session lost after three silent
  heartbeats. `as_fd` is for a program that waits on other things too.
- One way back: `reconnect` connects again to the same address as the same program, 250 ms
  between tries, for as long as the caller says. An answer of "no" is returned, not retried.
- Feature `tokio`: `next_async` waits inside a runtime without blocking it.

## Proved by

`tests/connect.rs`: one function, `exercise`, run against the board's socket, the network
plain, the network signed, and a serial link over a pseudo-terminal: hello, a request and its
answer, a session kept through eight heartbeats of the program saying nothing, 0 allocations in
500 requests, and an oversized frame refused before it is sent. Reconnecting is run on the
socket and the network: tries 250 ms apart while nothing is there, whole again when the comm
core is back.

## Changed outside this crate

A tool on a PC is "wire and client" and must not carry the server. The client needs the
identity key and the network handshake, which lived in comm crates that depend on the server.
They moved, unchanged, to two core crates: `orion-identity` (from `orion-keys`, which re-exports
it) and `orion-net-handshake` (from `orion-tcp`). Both sides now share one copy.
