# C58: A USB reader that is let go hands on what it reads

- **Status:** done
- **Group:** C (comm, links)
- **Wave:** 19
- **Needs:** C57

## Why

This is the other half of the link that did not come back after a USB bounce. The holder of a
gadget hands the comm core the same endpoint files again after the host returns (it keeps them
open through the host going away). The old stream's reading thread cannot be called back from a
read already in flight. In the trace, it was back in `read(2)` when the host returned, so the
host's hello came to it. The thread saw that it had been let go and threw the hello away. The
new stream never saw a frame, and the host timed out.

## Changes

- `orion-link-usb` `blocking.rs`:
  - When a stream is let go, what it still holds goes to the stream that took it over. So does
    anything its thread reads afterwards, which used to be dropped.
  - Handed-on bytes go ahead of the new stream's own, in the order they came. They come first
    because the old thread's request was queued at the endpoint first.
  - The thread checks before every read whether it was let go, not only while the host is away.
- `orion-link-usb` `lib.rs`: an offer for a link tells the current stream, and any stream offered
  but never taken, what took it over.
- `docs/comm.md`: "A reader let go hands on what it reads."

## Proved by

- `blocking::tests::a_reader_let_go_inside_a_read_hands_what_it_reads_to_the_stream_that_took_over`.
  The old thread is held inside a read while the new stream takes over. What the old stream
  held, and what its thread then reads, arrive at the new stream ahead of the new stream's own
  bytes, as `hello after`.
- Mutations, each failing that test: the thread not handing on what it reads; handed bytes put
  after the new stream's own.
