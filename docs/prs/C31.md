# C31: Files the settings name, served while no program offers their prefix

- **Status:** done
- **Group:** C (comm core)
- **Wave:** 19
- **Needs:** C30

## Why

A board with no program to offer its kernel log, or one in recovery, where nothing else runs,
should still hand it over. So the comm core serves what its settings name: a file read as it
is, or a command's output. It is the fallback: a program that offers the same prefix serves it
while its session lives, and the settings serve it again after.

## Changes

- **`orion_file_offers`.**
  - `OwnFiles::read(name, sessions, ready)` gives a `Reading`: the bytes `Now`, `Not` with why,
    or `Later`, handing them to the `Ready` when they are made. Every fetch of a file being
    made waits for that one making; each is held for `SNAPSHOT_MS` after, as before.
  - `FileOffersService::with_configured(comm, files)`: a prefix served while no program offers
    it. The longest prefix serves a name; a program's prefix serves before a configured one of
    the same length. A program offering a configured prefix takes it over, logged, no clash.
    A fetch under way keeps the side it began with.
  - The list of offers names the side that serves each prefix: the program, or `Configured`.
  - `with_own` takes the comm core too.
- **`comm-app`, `configured.rs`.** `offers.file` (`/etc/orion/offers.conf`), its format in
  `docs/comm.md`: `<prefix> <name> = path /P bound B [user-data]` or `= command /PROGRAM [args]
  bound B timeout MS [user-data]`.
  - It must be root's and written by no one else, or none of it is served: a comm core does
    not start, and recovery passes it over, logging why. No file is no files.
  - A path is opened without waiting and read up to its bound.
  - A command runs with no shell and no environment but `PATH`, in `/`, input closed, on a
    thread of its own that polls its output against its deadline: ended at its bound (what
    it wrote is the file) or at its timeout (rejected, saying so); an exit not 0 is rejected
    with its status.
  - `offers.user`: the comm core's own user, or another if the comm core is root, by starting
    itself as the new `offers-command` helper, which takes the user's groups, group and user
    and checks it cannot go back before the program.
  - Served running and in recovery.

## Size

Paths, commands, their parsing and the helper, and std's process and poll code, in both board
files. aarch64, static: `orion-recovery` 2,733,120 bytes (+40,400 since C30), `orion` 5,308,480
(+37,360). Cut first: a file made later that is never handed over no longer rejects its fetches
from a task of its own (one task type fewer, about 7-10 KB in each); a `Reading::Later` must be
handed over, and the comm core's one maker always does. The limits go to 2,760,000 and
5,330,000: what was measured and the usual margin.

## Proved by

- `orion-file-offers` tests (`tests/configured.rs`, a stand-in `sys/`):
  - two fetches of a file made later both wait and get it, made once (a fetch after holds the
    first making's bytes);
  - a file not made is rejected with its maker's words;
  - a configured prefix is served and listed `Configured`; a program offering it takes it over,
    no clash, listed as the program; when the program goes it is the settings' again;
  - a fetch waiting on a file being made when a program takes the prefix over is given it.
- `orion-comm-app` tests (`tests/configured.rs`), a real file and real commands:
  - running: the index, its bounds and marks; a path; `echo`; `yes` ended at its bound of
    1,000 bytes; `sleep 5` with a timeout of 200 ms rejected, saying so; `false` rejected with
    its exit status; `sys/` listed `Configured`;
  - a file the group may write: the comm core does not start, naming `offers.file`; recovery
    serves its own files and not those;
  - recovery serves a path and a command.
- `orion-comm-app` unit tests: every form of entry; each kind of line that is not one, with its
  line and why; a file not root's, or that the group or anyone may write, is not served;
  `offers.user` as oneself needs no helper, an account that is not there and root (from a
  comm core that is not root) are refused; the helper given too little runs nothing.
- 20 runs of both test files quiet, and 20 with every core of the machine busy: all passed.
- Not vacuous; each of these mutations fails a test:
  - a configured prefix listed though a program holds it: the take-over test;
  - every fetch of a file being made making it again: the made-later test;
  - the group allowed to write the file: the start test; any owner: the unit test;
  - a command's output not ended at its bound: the running test (it times out);
  - no timeout: the running test; an exit not 0 taken: the running test.
- The routing first checked that no program held a configured prefix as well as that it was
  longer; with that check gone every test passed, since a program's prefix of the same length
  already wins. The check was taken out.
