# I117: A core change's size builds run on CI; heavy work at CPU weight 100

**Status:** done

**Group:** I. Finish

**Wave:** 19

**Needs:** I116

Read `AGENTS.md` and `docs/design.md` first.

## Why

The one-minute rule (2026-11-24), and the user's ruling on its one exception: on a core change
or a cold rebuild, only the heaviest steps may leave the local gate for CI. Those are
shipped-profile release and LTO builds, size measurements, and toolchain-change seed bakes.
The local gate says so, `not-run(ci-only:WHY)`, and a release takes that only where CI ran
the lane green at that commit. Leaf changes, and every other run, keep every lane local.

Here that is one step: the size gate on a new key. Three shipped-profile fat-LTO links (two
binaries and the C library), each one thread, are most of a core change's gate:

| Core change | Size gate CPU | Size gate wall | Conditions |
|---|---|---|---|
| I113 | 360 CPU-s | 133 s | — |
| I114 | 418 CPU-s | 213 s | nice 10, load 124 to 109 |

They already run at once. One target directory for all of them, the crates they share built
once, was measured and not kept (I115). The approved list has this step only.

And a ruling on CPU shares: nice ranks processes inside one cgroup only. Between systemd's
units and scopes, CPUWeight decides, and weights of 1, 50 and 100 are in use on the machine.
Every project's heavy unit or scope runs at CPUWeight=100 with nice 10 inside it.

## Changes

- **`scripts/size-gate.sh`, CI only where a key is new.** With `SIZE_GATE_CI_ONLY=1` and any
  build's key unmeasured, it builds nothing, says how many keys are new, and writes the lane's
  status: `not-run(ci-only:N-of-M-size-keys-new)`. With every key measured it runs as before,
  each record held to today's limit, in seconds.
- **`scripts/gate.sh`** sets `SIZE_GATE_CI_ONLY=1` for the whole gate only. Asked for the size
  lane alone (`--part size`, as CI runs it), it builds. CI also sets `SIZE_GATE_MEASURE=1`,
  which measures everything whatever the keys say.
- **`scripts/release-check.sh`** takes `not-run(ci-only:...)` only where CI's `gate (LANE)`
  job passed at exactly that commit (asked with `gh`). It refuses any other not-run, a reused
  lane, or a ci-only lane CI failed or never ran, as before. `--self-test` covers every answer
  on planted commits and a planted `gh`. It is a gate step, run through `once`.
- **`scripts/work-env.sh`, `at_gate_weight`**, called by `at_gate_nice`. Heavy work started in
  a cgroup whose `cpu.weight` is not 100, or which is idle, fails, saying where it started. It
  does not check on CI.

## Proved by

- **The size gate's self-test**, on its copy of the source, all keys recorded:
  - a change to a core crate makes all five keys new (CI only);
  - a change to the notes makes none new (it runs here).

  With the count always 0, it failed 3 of 3 on the core case. With it always every key, it
  failed 3 of 3 on the notes case.
- **The release check's self-test** passed 3 of 3. With CI always taken as passed, it failed 3
  of 3: a ci-only lane taken with no CI run and with CI failed. With the ci-only branch taken
  out, it failed 3 of 3: one CI passed was refused.
- **Against GitHub:** I115's size job passed at its commit, and a lane with no job is not
  taken.
- **The weight check,** run under `systemd-run --user -p CPUWeight=W`: it took 100 and refused
  50, 1 and idle, each naming its cgroup.

## Measured

The size gate's own self-test, run when that script or the key's changes, takes 40 to 73 s at
load. It was so before this change, and a change to either script makes every size key new.
