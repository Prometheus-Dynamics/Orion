## Why

The last part of the clock row. On a field network there may be no date anywhere, but there
is one clock everything can reach: the NT4 server's, which the protocol gives every client.
It is not a date. It is a base that a board, another board and the controller can compare
times on. Two things were missing for a board to use it.

- **Nothing said the offset.** The NT4 client measured it and kept it to itself.
- **A value's time was when it was sent on,** not when it was measured: a camera frame taken
  40 ms before the gateway's next turn was stamped 40 ms late.

## Built

- **The offset, in `orion.time`:** `nt4_offset_us` and `nt4_rtt_us`. The offset is the server's
  clock less this board's sample clock, so a program adds it to a sample time (in
  microseconds) and has the time on the server's clock. It is published at once when the
  gateway measures it anew (a move of 250 µs or more), not at the time sync's next poll.
  While the server is lost both fields are published with no bytes.
- **Each value carries the time of its sample** on the server's clock. A sample whose time is
  not on the board's sample clock, ahead of now or over a minute before it, is stamped as it
  is sent, as before.
- **Orion's own NT4 server keeps the time a client gives a value.** This is a fix to a bug
  found here: the server form stamped every client's value with its own clock on arrival, so
  a value lost when it was measured. It now holds and sends on the client's time, whatever it
  is, as ntcore's server does (`ServerStorage::SetValue`, 2025.3.2: the value is kept as it
  came, zero and future included). A value set on the board is stamped with the server's
  clock, as before. **Behaviour changed** for anything that read a client's value from an
  Orion NT4 server and took its time as arrival time.

## Units

Microseconds. Released ntcore counts microseconds (`wpi::Now`, 2024.3.2 and 2025.3.2), as NT4
4.1 says. The unreleased ntcore counts nanoseconds. Nothing here detects which a server
counts; the docs say so.

## Where it is not

`orion.time` exists only with `time.sync` on, so with it off the offset is not published. The
values are stamped either way.

## Size

No limit is raised: I88 raised the board's `orion` limit for the whole clock row.

## Tests

- `orion-nt4` `the_server_keeps_the_time_a_client_gives_a_value_and_stamps_its_own`: a time in
  the past, zero, and one far ahead are each what the server holds and what a subscriber is
  sent; a value set at the server is stamped now.
- `orion-nt4-client-gateway`, a real comm core against a real server:
  - `the_servers_clock_is_a_shared_base_said_in_orion_time_and_values_carry_their_own_time`:
    the offset is within 20 ms of the true one; a value measured 300 ms before it is published
    is stamped with when it was measured; both fields are empty once the server is lost, and
    said again when another comes.
  - `a_board_joins_a_server_and_the_mapping_works_both_ways` now also shows a program that
    counts its own sample times stamped as sent.

Seven mutants each failed 3 of 3 runs: the server stamping on arrival; the gateway stamping as
sent; the offset left on the client's own clock; a lost server not told; the guard on a
sample's time removed; the comm core not passing the offset on; and the fields zero, not
empty, once the server is lost.

**Not covered:** a real controller. The server in the tests is Orion's own, in the test's
process. It is for a board on a field network: `orion.time` says an offset, and a value's time
on the controller is its sample's.
