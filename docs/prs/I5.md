## Built

- `crates/testing/drills` (`orion-drills`), with the binary `orion-drill`: `orion` itself
  (anything that is not a drill role goes to `orion_bin::main`, so the comm core and node
  logic are the real ones, from the real settings file), and the programs a board has as
  roles, each its own process printing what it sees: a publisher counting on a topic, a
  subscriber that checks it gets every value in order, a camera filling 4 KiB frames, a
  viewer that checks each frame is whole, the sample executor, and a provider with an action
  that answers, one that never does and one whose provider exits while running it.
- `tests/node_logic.rs`, `tests/comm_core.rs`, `tests/workloads.rs`: the table's four rows.
- `tests/contained.rs`: a bad client, peer, provider and link.
- `crates/bins/orion` is a library as well (`orion_bin::main`), so a program can be `orion`
  and more. `orion` now serves serial and CAN links (`link-serial`, `link-can`).

## Proved by

Each row of the table, with `SIGKILL`:

- **Node logic.** Topics and frames go on, every value in order and every frame whole; a new
  program gets in and reads a topic; SSH answers; a request for records is refused at once
  with "unavailable". Started again, it answers within tens of milliseconds and a provider's
  action runs again. Nobody else had to connect again.
- **Comm core.** Values and frames keep flowing between publisher and subscriber with nothing
  between them; nothing new gets in. Started again, the command line is in at once (under
  2 s is asserted), node logic and every program connect again, and a subscriber and a viewer
  new to it get the same publisher's values and the same camera's frames. The first readers
  never missed a value nor saw a torn frame.
- **An executor.** Its command dies with it, the workload is on record as lost, everything
  else goes on; when an executor is back the workload is started again, once.
- **Orion, both parts.** The workload keeps running and values keep flowing; Orion comes back
  and takes the workload back by name: the same process, never started a second time.

And contained:

- **A client** that sends 256 KiB of noise is let go; one that never says hello, one that
  subscribes and never reads, and 200 that connect and go change nothing for the others.
- **A peer** that sends noise, one that says nothing and one that stops reading: the board's
  traffic, and a second board reading its topic as a good peer, go on.
- **A provider** whose action never answers: the run ends at its deadline and another action
  runs meanwhile. One that exits during a run: the run ends at once ("the program that runs
  it went away").
- **A link** flooding noise beside a device on another link: the device's topic goes on.

Every drill also checks the board's ordinary traffic was untouched: no gap, no reconnect, the
command line working, the comm core up.

## Different from the brief

The drills found three things, fixed here:

- **A camera did not offer its pool again** to a comm core that restarted when its topic got
  the same number there as before, which is the usual case: a restarted comm core numbers from
  the start again. Viewers new to that comm core got no frames. `BufferPublisher` now offers
  again whenever the session has connected again. `tests/facade.rs` in `orion` shows it: it
  fails without the change.
- **A command outlived its executor.** The sample executor's commands kept running when it
  was killed, so the executor after it, knowing nothing of them, was told to start them again:
  two copies. Its commands now die with it (`PR_SET_PDEATHSIG`), in `src/spawn.rs`, the one
  file of the crate that may use `unsafe` (as `orion-wire`'s `crc.rs` is for that crate).
- **`orion` could not serve serial or CAN links:** it was built without `link-serial` and
  `link-can`. Both are on now.

Also: a put is kept only once saved, `records.save_after_ms` after it plus the time a save
takes; node logic killed before then starts without it. That is how the store is built (a
save is one step, debounced). The drill that kills Orion whole waits for the save, and says so.
