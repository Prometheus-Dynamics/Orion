## Build

C33 left a gap that the coordinator says is the product's normal path. A run carried to another
node is claimed there from the peer link's session. So a program on that node heard
`CALLER_GONE` only when the link between the nodes ended, which may be never. A tool on a laptop
reaching a board through a controller would leave its holds on the board for as long as the two
boards stay linked.

The requirement: the token travels with a forwarded run and stands for the original caller's
session. When that session ends, the forwarding node sends `CALLER_GONE` to the far node, hop by
hop. The far program sees one token per original session and one `CALLER_GONE`.

Today's `Target::Node` forwarding already carries every run over one session per far node, so
this is built now, without waiting for F10b.

1. `Run` gains an appended `on_behalf: u64`: the forwarding node's token for the session that
   asked. Only a peer's is read; from anyone else it counts as zero, the asker's own session.
2. The far list keys callers by (session, on_behalf). Each original session behind a peer link
   is a caller with its own token there.
3. `ACTION_CALLER_GONE` is also a request, from a peer only, naming the forwarding node's token.
   The far list ends that caller: each program given a run from it is told once. Nothing is
   cancelled; cancels go as before. When the link ends, every caller behind it ends, each told
   once.
4. Hop by hop: the list hands node logic the tokens of callers that ended, both real sessions and
   callers behind a peer. Forwarding keeps which caller's runs went to which node, and sends
   `CALLER_GONE` down each such link.

## Built

- `Run.on_behalf`, appended. `ACTION_CALLER_GONE` routed at the door for peers alone
  (`orion-relay`), and answered by node logic (`Logic::KINDS`).
- `orion-action-list`:
  - callers are `(session, on_behalf, token)`;
  - `caller_token(asked)` gives the token for a `Run`'s asker;
  - `take_ended()` gives the tokens that ended;
  - `gone` ends every caller on the session;
  - the peer's `CALLER_GONE` request ends one caller, a non-peer is refused `Denied`, and an
    unknown or repeated token is ignored.
- `orion-action-forward`:
  - `Forwards::run` takes the caller's token and sends it as `on_behalf`;
  - `Forwards::caller_gone(token)` tells each node that caller's runs went to, once;
  - the link sends nothing when its session is down, because the far node has then already
    ended every caller behind it.
- Node logic gets the token from the list before it forwards, and passes on the ended tokens
  after each request and after each session ends.
- The client always sends `on_behalf: 0`.
- Vectors: `ACTION_RUN` gains `04`.

## Proved by

- `orion-action-list`, `tests/caller_gone.rs`:
  - `each_caller_a_peer_carries_runs_for_is_a_caller_of_its_own`: callers 7, 8 and 0 behind one
    peer session each get their own token, and 7 again gets the same one. The peer's
    `CALLER_GONE` for 7 tells the program once, cancels nothing, and is handed on. A repeated or
    unknown token is nothing. When the link goes, the other two each end once.
  - `only_a_peer_speaks_for_another_session`: a local caller naming 7 is still itself, its
    `CALLER_GONE` is refused `Denied`, and its own end is handed on.
- `orion-node-app`, `tests/forward.rs` (two nodes, a real link): every run from one caller on the
  left reaches the right node's program with one token. A second caller gets another. When that
  caller disconnects, the right program hears `CALLER_GONE` for its token while the link lives on,
  once, and not for the caller still connected.
- Not vacuous:
  - with `on_behalf` read from anyone, the peer-only test fails;
  - with only one caller per session ended, the link-goes test fails;
  - with the ended tokens not passed on, the two-node test fails;
  - with `on_behalf` sent as zero, the two-node test fails on the tokens;
  - with `ACTION_CALLER_GONE` missing from node logic's kinds, the two-node test failed. That is
    how the missing entry was found.

## Different from the brief

- A three-node chain is not run as a test. Each hop is the same code: the list test shows a
  peer's end is handed on, and the two-node test shows a handed-on end crosses a link.
- F10b's forwarded tool sessions should use the same rule: a forwarded session's caller is its
  `on_behalf`.
