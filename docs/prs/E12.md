## Creates

`crates/node/actions-detached` was not made. Detaching is what the list does with a run when
its caller goes, and needs the run's caller, starter and latest progress: a second crate would
have had to be handed the inside of the first. It is part of `crates/node/action-list`.

## Read on dev

- `crates/node/src/app/actions/wait.rs`
- `docs/actions.md`

## Build

- An action keeps running if the caller leaves. The caller can reattach.
- Cancel, and deadlines.

## Proof

Disconnect mid-action and reattach to the progress.

## Built

In `orion-action-list`: a run remembers who started it and, when detached, its latest
progress; `Attach` puts the starter's new session in the caller's place; a detached run that
ends with nobody attached is kept ten minutes for its starter. `orion-relay` routes `Attach`
and node logic answers it. The rules are in `docs/node.md`, "The open list of actions".

## Proved by

- `crates/node/node-app/tests/actions.rs`, against a real comm core with a provider in another
  process: a caller starts a detached run, sees 30 % and drops its session; a new session
  attaches with the run's number and is sent that progress at once, then the result when the
  run is let finish. A run that ends while its caller is away is given to the session that
  comes back, once. A run that was not detached is cancelled with its caller and cannot be
  come back to.
- `crates/node/action-list/tests/list.rs`: the latest progress on attach and everything after
  it; the kept result, its ten minutes and its limit of 256; another user with the right
  number finds nothing; cancel only from the session that came back; a detached run still
  times out and still fails with its program.

## Different from the wire's comments and from dev

- `Attach` carries only the caller's own number, which another caller may also have used. So
  a run is come back to by its number and its starter, as the comm core names them. This is
  also what keeps one user from attaching to another's run.
- Dev kept waiters in the node and polled; here the list sends as things happen.

## Found on the way

A request passed to node logic a moment before it died was never answered: the caller waited
for ever. The relay now keeps which passed requests are still owed an answer (a read or write
until its answer, a run until its result) and refuses them with `unavailable` when node logic
goes. `relay.rs` has the test; the node logic restart test in `actions.rs` hit it one run in
a few.
