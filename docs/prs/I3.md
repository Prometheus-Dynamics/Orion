## Built

`crates/testing/sample-executor` (`orion-sample-executor`): `Sample`, an `Executor` that runs
each workload's spec as `sh -c <spec>`; `run`, the loop around it with reconnecting; and the
program `orion-sample-executor`. It uses only the `orion` facade and `rustix` for signals.

## Proved by

`tests/sample.rs`, with real child processes:

- A command runs, is stopped with `SIGTERM`, and its process is gone; one that ignores
  `SIGTERM` is `Stopping` until it is killed; one that ends well is no longer listed, one
  that exits with an error is `Failed` until started again or stopped; a spec that is not a
  command line cannot be started; an executor that is dropped takes its commands with it.
- Against a comm core: Orion is asked for a workload of kind `process`, the executor starts
  it and Orion says `Running`; one that exits 3 is `Failed`; removing the first ends its
  process and Orion says `Gone`.
- The same as a separate program, started with `--socket` and `--kind`; a forced remove
  kills the command; wrong arguments print how it is used and exit 2.

"Used by E5's tests" is E5's to show.

## Limits, which a real executor would not have

If the executor is killed outright its commands are orphaned and keep running, and a new
executor does not know them. It does not pin a workload to the CPUs it is given.
