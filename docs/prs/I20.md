## Build

CI's gate job ran the whole gate on one 4-CPU runner: 12 minutes on the I17 push. Its lanes
(feature matrix, other systems, size, devices) ran beside clippy and the tests, all on those
4 CPUs:

| step | s |
| --- | --- |
| clippy | 157 |
| tests | 493 (the run itself 119) |
| feature matrix | 605 |
| size gate | 610 |

The cache did not help either. rust-cache saves only after a job passes, and CI had been red
since 16 November. Its key does not see the root manifest's profiles: I18 changed one, and the
I18 run matched the I17 cache whole (`full match: true`). A whole match is never saved again,
so the cache would have kept builds made under the old profile.

## Built

- **`scripts/gate.sh --part <part>`** runs one part of the gate. The parts are `main` (every
  step not in a lane) and the four lanes `matrix`, `other-systems`, `size` and `devices`.
  - A lane run as a part runs in front, with its output as it comes.
  - A part never stamps the tree, so `scripts/push.sh` still takes only a whole gate.
  - Without `--part`, the gate is as before.
- **CI runs the five parts at once**, each on a runner of its own. Together they are the whole
  gate. `fail-fast` is off, so each part says how it ended.
- **Each part has a cache of its own**, keyed on the root `Cargo.toml`, `.cargo/config.toml` and
  `rust-toolchain.toml` on top of rust-cache's own key. The client jobs' caches are keyed the
  same way.

## Proved by

- Each part on its own on this machine, after a full gate: `main` 64 s, `matrix` 19 s,
  `other-systems` 13 s, `devices` 24 s, `size` passes. `main` starts no lane.
- `--part main` with a fault planted in `orion-check` fails (at `format`). `--part size` with
  `orion`'s limit set under its size fails:
  `FAIL: orion for this machine is 6310568 bytes, over its limit of 6000000`.
- A part that is not one of the five is refused, with the usage, and exit 2.
- The whole gate, without `--part`, passes and stamps.
