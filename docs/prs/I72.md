## Why

A board reached over its USB link and over Ethernet needs the network and SSH ways in on both.
Each took one interface, so the only way to have both was a wildcard address on every interface.
Addresses on Ethernet change (a late DHCP lease, a new one, a link-local fallback), so the
listeners are kept to interfaces by name, not by address.

There was also a fault, measured in a network namespace of its own before anything was written.
A socket kept to an interface (`SO_BINDTODEVICE`) is kept to its index. When the interface is
taken away and made again under the same name, as a USB gadget's network is when the gadget is
rebuilt, it has a new index. The old socket then takes nothing: connections are refused, and
`accept`, `poll` and `SO_ERROR` all say nothing.

## Built

- **The settings.** `peer.interface` and `ssh.interface` are comma-separated lists, read by
  `Source::interfaces`. Each name is one the kernel takes (1 to 15 bytes, no `/` or space). A
  name said twice is refused.
  - `CommSettings::peer_interfaces`, `SshConfig::interfaces` and `RecoveryConfig::interfaces`
    are `Vec<String>`. Empty means the address alone, as before.
  - The last-good settings write the list.
- **One listener per interface**, each at the way in's address, opened on its own.
  - The network way in: `comm-app/src/network.rs`, one `TcpCarrier` served for each interface.
  - SSH: `orion_ssh::Listeners`, one task for each interface, all feeding one accept. The
    sandboxed server uses the same type.
  - Recovery passes its interfaces on to the SSH it starts.
  - An interface that is not there is tried again and said once, by its name, at warn. It holds
    up neither the others nor the start.
  - The address announced is the first listener's, or the one given while none is open.
- **One listener that follows an interface, for both ways in.** `orion_tcp::kept` opens a
  socket kept to an interface and takes its index; `orion_tcp::still_kept` says whether the
  name still has that index. SSH uses both, and waits for a missing interface with
  `orion_server::open_retrying`, as the network way in does. `open_retrying` now takes a
  closure that gives a future, not an async closure: the future of an async closure held
  across an `.await` is not seen to be `Send` for every lifetime, and SSH's waits run in tasks
  of their own.
- **Following the interface.**
  - Each listener takes its interface's index before the socket is kept to it
    (`rustix::net::netdevice::name_to_index`).
  - It looks again every `Retry::first` for the network way in (5 s by default) and every
    second for SSH.
  - When the name has another index, or none, it says so at warn, by the name, and opens again
    the way a listener that is not there yet does. No restart is needed.
- **The namespace tests must run in the gate.**
  - `scripts/gate.sh` exports `NAMESPACE_TESTS=required`. Not an `ORION_` name, because every
    `ORION_` variable is a setting to the programs the tests start. Not a `GATE_` one, because
    nothing built may read those. Only tests read it, in the main part, which is never reused.
  - Under it, the new test and the sandbox test that checks what each kind of session holds
    fail, saying why, where they could not run. Elsewhere they say so and pass.
  - CI loads the `dummy` module on its runner, which is thrown away after (`next.yml`, beside
    the AppArmor setting).
- **The aarch64 recovery limit stays at 2,760,000** (see Size).
- **The docs** say the listeners are IPv4: IPv6 would take a second listener on `[::]` on each
  interface. They also say discovery announces `peer.listen` as it was given, not each
  interface's address.

The limit was not raised. The known next cut, if the limit is hit again, is one listener type
in `orion-tcp` that accepts and listens again by itself, used by the network way in and SSH
alike, aimed at `serve`'s 5 KB. It would
make the listening again cancellable inside the network way in's `select!`, so a "cannot
open" warning could be said again, unlike today; keeping today's behaviour would take more
code. The limit is not raised without a table like these.

## Proof

`interfaces::each_interface_named_gets_a_listener_that_follows_it_when_it_is_made_again`
(`crates/comm/comm-app/tests/interfaces.rs`) runs itself again under
`unshare --map-root-user --net`. Inside, it makes dummy interfaces `orion0`, `orion1` and
`orion2`, and starts a comm core with both ways in on `orion0, orion1, onever`. Then:

- Each way in takes connections on `orion0` and `orion1`, with SSH's banner on each. Nothing
  listens on `orion2`, which is up but not named.
- After 2.5 s of tries, `onever` is in the log twice: once for each way in.
- `orion0` is deleted (nothing takes connections there) and made again under the same name.
  Both ways in take connections there again; `orion1` went on meanwhile.
- `onever` is made, and both ways in open on it.

It passes 3 of 3, in about 4.2 s each.

Mutations, 3 runs each, every run failing:

| Mutation | Fails at |
|---|---|
| The network way in never sees its interface go | `orion0` made again: nothing takes the connection |
| SSH never sees its interface go (`still_kept` never asked) | `orion0` made again: nothing takes SSH's connection |
| The network way in takes only the first interface | `orion1` |
| `open_retrying` says a missing interface on every try | `onever` said more than twice |

The requirement, with `unshare` and `ssh` off the `PATH`:

- Without `NAMESPACE_TESTS=required`, both tests say why and pass.
- With it, both fail: "this test must run here, and cannot: unshare could not be run" and
  "… OpenSSH is not installed".

The settings tests cover a list, a name said twice, and a name the kernel would not take. The
existing one-interface tests (`orion-tcp`, `orion-ssh`, recovery's) pass on the new types.
**The landing gate passed.**
