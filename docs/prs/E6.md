# E6: Stopping and force remove

**Status:** done

**Group:** E. Node logic

**Wave:** 11

**Needs:** E5

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Creates

`crates/node/workload-stop` was not made. When a stop becomes a kill is a fact about a
tracked run (since when it has been stopping, whether it was told to end), and lives where
the run is tracked: `crates/node/workloads`.

## Read on dev

- `crates/runtime/src/reconcile.rs`

## Build

- Stop, then kill. The record stays through Stopping.
- Force remove is explicit and audited, and says what it left behind.

## Proof

A process that will not die stays in Stopping until force remove.

## Built

- `orion-workloads`: a run asked to stop is told to end after `stop_grace_ms` (10 s), once;
  `next_deadline` includes that time. A forced remove's last change says what it left behind.
- `orion-node-app`: setting `workloads.stop_grace_ms`; the audit line of a forced remove has
  what was left in its result.

## Proved by

- `crates/node/node-app/tests/workloads.rs`: an executor whose workload ignores both stop and
  kill. Removed, the workload is `Stopping`; after the grace time (300 ms in the test) the
  executor is told to end it, once; a second and a half later it is still `Stopping` and its
  record is still in the store. Removed by force: the status is `Gone` with "removed by
  force: a run was left Stopping; its executor was told to end it", the record is gone, the
  executor was told to end it once more, and the audit log has both removes, the forced one
  with `ok: a run was left Stopping`.
- `crates/node/workloads/tests/stopping.rs`: told to end exactly at the grace time and never
  again; not told if it stops in time; a replaced run that will not stop is told too; the
  three things a forced remove can leave behind.

## Different from dev

Dev dropped a record as soon as a stop was asked for. Here it stays, and only force removes
it early.
