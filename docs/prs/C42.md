## Build

Helios overruled C32a's second deviation. A broken `orion.conf` must not decide security. The
record is the one switch, in recovery too:

- the record says off: off;
- the record is malformed or unreadable: on.

Recovery reads the same fail-secure reader. Forcing security on there would lock an operator
out of fixing a board over the network, on a board whose security is off by default. Test: a
broken conf plus a record saying off gives off, and a broken conf plus a malformed record
gives on.

## Built

- `recover` uses the view the settings carry when they were read. When they were not, it reads
  `SecurityView::read(with.security_view)` and logs it as the services do. That one switch goes
  to:
  - the SSH way in;
  - recovery's socket and links (`RecoveryComm::start` now takes it);
  - the settings taken from the last good start (`last_good::read` takes the view, where it set
    security on).
- `RecoverWith` gains `security_view`, `orion_config::SECURITY_VIEW` by default. It is a path
  for tests, not a setting, the same as `from_source_with_view`.
- `lock.md` lists the change under "Since the lock revision", including the break for code that
  builds a `RecoverWith` by its fields.

## Proved by

- `comm-app/tests/recovery.rs`, `each_broken_state_ends_in_recovery_and_still_lets_you_in` now has:
  - with the record on, only the repairer gets in (as before);
  - with the record `off` / `generation 2` and the same broken settings, a login with no key
    gets in;
  - with the record `of`, which is damaged, a login with no key is refused and the repairer
    gets in.
- Mutations, both caught:
  - recovery's switch forced on;
  - a damaged record read as off.
- The comm-app suite passes. The gate passed.
