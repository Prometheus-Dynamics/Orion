Orion Architecture

Orion becomes the one way in and out of a board and the only authority on what runs. It is built around six things, speaks one wire from a microcontroller up to a PC, and gets out of the way of fast data once it has introduced the two sides.

What it is

What Orion is

  • The one way in and out of a board
  • The only authority on what runs
  • The bus that values travel on
  • The open list of actions: whoever connects adds theirs
  • The same thing from an MCU up to a PC, in different sizes

What it knows

  • Names: of nodes, topics, actions, workloads
  • Who is asking, and whether they may
  • What should be running, and what really is
  • Which transports exist and which peers are alive

What it doesn't know

  • What a camera, a pose or a graph is
  • What is inside a topic beyond its type
  • How to encode video: a publisher gives it bytes
  • What FRC is: NT4 topic names come from HeliOS as config
  • How to talk to hardware or update a board: that is Lemnos

Who does what

This is the split you described, and the design now follows it.

The rule: no library needs another one in order to work. Where two meet, the bridge is an optional feature owned by one of them, and the product turns it on. Styx keeps its own way to pass frames for anyone not using Orion, and HeliOS just doesn't use it.

Six things instead of eleven

The biggest change is what Orion is built around. Today every need got its own mechanism with its own messages. Status, streams and NT4 all move values, and each one does it differently. Three kinds of action path exist because the board agent, the update intents and the actions all grew apart.

The whole board

One board, with Orion as the middle of it. The comm core is the only program with a door to the outside. Node logic and every program connect to it once and use the same wire. Big or fast data moves on the side, directly between the programs that want it, with Orion having set it up.

Two programs, five forms

You chose two processes on 2026-11-07, comm core and node logic, so that links stay up no matter what. This design keeps that and makes it simpler than the earlier note did. There is no separate backplane protocol. Node logic is simply the first client of the comm core, on the same wire as everyone else. They ship as one binary with two modes, so they share code pages, and orionctl becomes a third mode of the same file.

If this diesWhat keeps workingHow it comes back
Node logicLinks, SSH, topics, gateways. Requests for records answer "restarting"Reconnects as a client and takes up its work
Comm coreGraphs and every same-board topic, frames included, because those already hold their rings. No new connectionsRestarts. Publishers re-offer their rings. Peers and browsers reconnect, access paths with no backoff
daedalusdEverything else. Its records stay, marked lostOrion restarts all of its workloads
Orion, both partsGraphs keep runningOrion finds them by name and takes them back

One wire

Today there are three separate protocols. The control protocol uses rkyv and demands both sides come from the same build. The link protocol uses postcard, is versioned, and already runs on microcontrollers. A third file-descriptor protocol has no production user.

A daemon loading plugins built somewhere else cannot live with "same build or refused". So the link protocol's rules become the only wire, on every carrier: stable kind numbers, append-only bodies, one revision number agreed at hello, and recorded bytes in tests. rkyv leaves the codebase entirely. The rule already agreed in stable-interface.md is that the stable interface is the link protocol extended, and this finishes the thought.

Network, between nodesSigned rkyv on orion+tcp, over TCP; push is opt-in; watches poll by defaultStays TCP, and this is how nodes talk. Same signed session, always push

Topics: how a value moves

A topic is a named value with a type, and every sample carries the time it belongs to. Types are bool, integers, floats, strings, bytes, arrays and structured values with a pinned type name, so a pose is one sample. One declaration can hold several related fields, the way a stream holds series today.

This one mechanism replaces the status lane, the stream lane, the per-series history, the per-subscriber copies and the 256 messages per second limit. A latest-value topic is a ring two deep with an expiry. A tool or a remote device that cannot write shared memory sends over its socket and the comm core writes the ring on its behalf, so there is still one model.

What you asked forHow this does it
One graph feeds anotherPublish a topic, subscribe to it. Same call on one board or across boards
A graph reads a sensor or a poseSubscribe. The value at or before a given frame time comes straight out of the ring
Waiting for a value that matches a frameAsk for frame time t and how long to wait. Replies are hit, lagged or missing, which is what the engine's pipeline_bus does today
No static 250 ms publishNo timers anywhere on the path. A publish happens when the publisher has something
Costs nothing when nobody watchesSubscriber counts sit in the ring header, so a publisher can skip work with one memory read

Frames: found once, handed over

A camera is a topic like any other. The camera service publishes cam0.frames and a graph subscribes to it, with the same call a graph uses for a pose. Orion gets the buffers once and hands them to whoever subscribes. After that a frame is just a buffer number in the same kind of ring as any value, so there is no second path.

You had the cost right. The only new work is at set-up. Styx does a few things per frame that a plain value ring does not, so a topic has to carry them too:

The graph side needs no camera node. An Orion topic source brings the frame in, and a Styx adapter turns it into a FrameLease with no copy, so the graph looks the same as any other input.

Leaving the board

A buffer number means nothing on another board, so frames stay on the board they were captured on. Off the board, video is an ordinary bytes topic, and Styx already encodes on request. Orion moves bytes and has no idea they are video. One generic flag on a sample, "others depend on this one", lets Orion drop intelligently for a slow reader: it skips forward to the next independent sample.

Workloads: Orion is the authority

This works the way you described Kubernetes. Orion holds what should be running and tracks every run. Asking for a stop does its best, and the record stays until the run is really gone. Force remove exists for when a process will not die, and that is the only way a record leaves early.

PartHow it works
WorkloadA name, a kind such as graph, an opaque spec (a GraphDocument), the files it needs, where it may run and a restart policy
ExecutorAny program that connects and says "I run this kind". daedalusd is the first. It reports state per name and keeps no journal
StartingOrion first makes sure every needed file is on the board, then tells the executor
Across boardsThe peer sync and placement that exist today carry over. They are already used by the robot deployment
FailuresRetry forever with backoff capped at 5-10 s. Auto-off only if someone configured it. Backoff state is a topic anyone can see

Actions and the one check

You asked for one check that nothing can skip. Compile-time is the only place that stays true as the code grows, so the check is built into the types, and it covers every kind of request, more than actions alone.

Actions keep what works today: progress, cancel, and detached running, so a flash carries on if the caller leaves and the caller can reattach. Orion ships almost none of its own. Any program that connects can add actions, and they all go through the same check.

Board management: with Lemnos, details pinned

You want this with Lemnos and we're coming back to the details, so read this section as the direction. Orion should not know how to install a slot on a Pi. That is knowledge about a specific board's storage and boot firmware, and it changes per board family, which is what a driver is for. So the update becomes a Lemnos driver, tagged something like boot.slots/1, one per board family. Lemnos devices already describe their own actions. The Lemnos bridge publishes those to Orion, and Orion then has an update action without having any update code.

JobWho does it
Update, cancel, rollback, slot.*, confirm, rebootLemnos driver, one per board family
locate, usb-route.set, power switches, USB gadgetLemnos drivers. The USB device role is already in the Lemnos design
Board identity and hardware factsLemnos provides them, Orion shows them in hello
The action itself: who may, progress, cancel, reattachOrion
Getting image bytes to the board, once, from any connection or a URLOrion, written straight to where the driver says so a 64 MB board never holds it twice
Boot units, DHCP, hostname, serial console, pstore, netconsoleGaia, because they are the contents of the image
board.live, board.hardware, clock.set, board-stream :5898, board-power-logDeleted

Orion is the standard way to do all of it, with the USB console and then SSH as fallbacks. The five transports Atlas has today collapse to that, and the robot-controller gateway becomes an ordinary Orion peer on SystemCore.

The catch is that updating now needs lemnosd alive, and an update is how you fix a broken lemnosd. Three things cover it. A slot only gets confirmed if Orion and lemnosd came up and the update action answers, so a build with a broken update path rolls itself back. From a broken running slot you still have SSH, served by Orion, and the USB flasher, which needs no running OS. And a bad driver can't take lemnosd down with it.

It also asks two things of Lemnos that its design doesn't have today. Storage is outside Lemnos, so a driver needs to be allowed to work with files and boot config directly. And an update runs far longer than a normal driver call, so drivers need a long-job form with progress and cancel.

On a microcontroller

This side is in good shape, and it becomes the template. crates/link is no_std, builds for Cortex-M and RISC-V, and the STM32G4 example is gated at 9,228 B flash and 1,988 B RAM. It keeps that gate. A device sends topics, takes actions and receives firmware on the same wire as everything else, minus shared memory. No consumer uses it yet, but it is the reason the wire can be one thing.

What could go wrong

  • The ring is the riskiest part. Readers run against a writer they don't trust, on memory that can change underneath them. Every read must be bounds-checked and survive a torn entry. It gets fuzzing and a loom model before anything uses it.
  • One async thread per process. A big SSH copy could delay a topic forward. It has to be measured on a CM5 with a transfer running. More threads are a plain knob if needed.
  • Video in a browser on plain HTTP. WebCodecs only works on secure pages, and robot boards are http://10.te.am.x. JPEG chunks or H.264 through Media Source both work there, so the choice lands with whoever publishes the video.
  • Radio bandwidth on a field. Per-subscriber byte limits and the drop rule have to hold under a real cap.
  • The heap target is a guess until profiled.
  • Postcard for saved records. It is not self-describing, so saved state follows the same append-only rules as the wire.
  • Hold marks. The hold marks are new shared-memory code on the camera path, and the 18 µs was measured without them. Hardware proof has to include them.
  • Update path through two daemons. Covered above, and the confirm check is what makes it safe, so it has to test the real action.

Settled

  • Clean-slate next branch, with dev frozen as the reference.
  • One wire, rkyv gone.
  • Two processes, one binary.
  • Frames are topics, with no second path.
  • Node-to-node traffic stays on orion+tcp.

Pinned and open

  • Board management is pinned. It goes with Lemnos, and the details come back later. What Orion needs for it gets built regardless: the open action list, the check, progress and delivering files.
  • What wakes a graph. Yours to come back to. Every topic gives the subscriber something it can sleep on, so a frame, a topic or a timer all work.
  • Pinning a graph to a core. Also yours. A workload's spec is opaque, and "where it may run" has room for a CPU set, so Orion can carry it either way.

Session rules

The same way of working as Lemnos. Nothing has been started, and no cloud sessions run until you say.

  • One PR per session. Base next, branch pr/<id>
  • The brief at docs/prs/<id>.md is the whole assignment: what it needs, what it creates, what to read on dev, what to build and what proves it
  • python3 scripts/pr-status.py lists what is merged, open, ready and blocked
  • Stay inside the paths the PR creates. That is what lets many sessions run at once
  • A PR merges when scripts/gate.sh passes and its proof is pasted into the PR
  • Board runs happen in a local session after merge, on a CM5. A PR is not held back for one
  • Breaking other repositories is fine, and they send their requests afterward

Where it stands

The repo has main, dev and next. dev is the frozen reference. next holds this design, the shared interfaces, the rules, the gate and every PR brief. Group A, the foundation, is built on it: names and errors, the wire and all 52 message kinds, the compile-time check, the failure rule, config, descriptor passing, measurement, recorded bytes for every kind, and fuzz targets for every decoder. Nothing above the foundation exists yet, so there is no node to run. Seven PRs are ready: B1 (ring), B6 (values), C1 (comm server), C7 (keys), E1 (record store), F6 (NT4 protocol) and H1 (device core). No session has been started on them.
