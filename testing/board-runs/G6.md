# G6: The comm core alone on a CM5, in a root with nothing else in it

Run on a CM5 (Raze #2, image dev.993). `next` is at G5 (8e52f0b) plus this PR.

This is not a boot into the board's initramfs: that needs an image built with
`orion-recovery` in it, which is the image's repository and a reboot of a shared board. What
was run is what such an initramfs holds, put together on the running board: a directory with
`orion-recovery`, a shell, and nothing else, entered with `chroot` as root. It answers what
the proof asks of the binary. Whether the board's bootloader and initramfs start it is still
to be shown, with the image.

## How it was run

`orion-recovery`, built for `aarch64-unknown-linux-musl` with profile `service`: one file of
2,634,088 bytes, statically linked. On the board, with the board lock held, under
`/tmp`:

- A root directory holding `/bin/orion-recovery`, the board's shell with the loader and two
  libraries it needs (the board's busybox is not one file), `/etc/orion/recovery_keys` with
  one public key, `/proc`, and a `devpts` of its own at `/dev/pts`. No other device files:
  no `/dev/urandom`, no `/dev/null`. In the first run no account files either.
- `ORION_SECURITY=on ORION_SSH_LISTEN=0.0.0.0:22 chroot <root> /bin/orion-recovery`. Port 22
  is the board's own SSH server's, so the comm core cannot start as told.
- In the second run a second one beside it, on port 2223, which can start as told, with
  security on and nobody enrolled.
- `ssh` and `scp` from a PC on the SystemCore's network, through the SystemCore.

Each ran for 45 seconds and was then stopped. Nothing on the board was changed: the
directory was unmounted and removed, and nothing was left running.

## What happened

| Check | Result |
| --- | --- |
| The static file runs on the board with nothing beside it | Yes |
| It cannot start as told, and does not end | `the comm core is in recovery: ssh.listen 0.0.0.0:22: Address in use`, then `recovery: SSH is open on 0.0.0.0:2222` |
| SSH in, with the recovery key, as root, with no account files | A shell: `uid=0 gid=0`, `aarch64`, shell `/bin/sh`, home `/` |
| A terminal | A session on a terminal ran and gave its exit code, 5 |
| Who is not let in | A key not in the file, no key, and an account that is not there: each `Permission denied` |
| `scp` up and down | 300,000 random bytes up and back: the same bytes |
| With no `/dev/urandom` | A host key was made: the kernel is asked for random bytes by the call |
| A session as another account (second run, with account files) | `uid=1234(ana) gid=1234(ana) groups=44(video),1234(ana)`, home `/home/ana`; `touch /bin/x`: `Permission denied`; a file it made in `/tmp` is owned by 1234 |
| The child that reads a connection (second run, the one on 2223) | Seen 7 times while clients tried to log in: `Uid: 65534` in all four places, `Gid: 65534`, no groups, `NoNewPrivs: 1` |
| Nobody enrolled, security on | Six logins with a key were each refused |

## What the first run found

The first try did not open at all. The root's `/dev/urandom` was a device file on a
filesystem that does not allow device files, so it could not be opened, and making a host key
read it. That is what an early initramfs can look like. The host key now takes its random
bytes from the kernel's call and falls back to the file. The message also said the address
could not be listened on when it was the key that could not be made; it now says which.
