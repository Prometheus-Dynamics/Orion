# B9: Ring costs on the test board

All numbers are from the test board (an aarch64 Cortex-A76 module, image dev.993, kernel 7.2.9, `performance` governor), with
the image's real services running and no core isolated. `next` is at B5 (8a7016b) plus this PR.

## How it was measured

`orion-ring-bench` (`crates/testing/ring-bench`), built for `aarch64-unknown-linux-musl` in
release, run twice as `orion-ring-bench --frames 1200 --hz 120 --samples 2000 --cpus 2,3`:
publisher pinned to core 2, subscriber to core 3. Times are wall-clock from one monotonic clock.
CPU is each thread's own CPU time. Both runs agree; the tables give the first, and the second
where it differs by more than a few percent.

The board lock was held for the runs. Nothing on the board was changed: the binaries ran from
`/tmp` and were removed.

## The targets

| Target | Result |
| --- | --- |
| About 18 µs per frame with a wake, hold marks included | **10.5 µs** median from publish to the subscriber holding the frame and reading it (9.6 µs in the second run) |
| The publisher makes no system call when the reader is awake | **None** in 100,000 publishes, and none in 100,000 frames on both sides: the code ran in a child that is killed on any system call |
| 0 allocations | **0** in 100,000 value publishes, rings and reads, and 0 in 100,000 frames |

## Memory paths, one thread, no wake

| Path | Cost |
| --- | --- |
| Publish a 64-byte value, nobody subscribed | 53 ns |
| Publish and ring, subscriber awake | 62 ns |
| Publish and `next` | 107 ns |
| `latest` | 47 ns |
| Lookup by frame time, history 64 deep | 239 ns |
| A whole frame, both sides: limits, take a buffer, publish, ring, `next` with marks, release | 445 ns |

A ring to an awake subscriber costs 9 ns on top of the publish: the fence and one memory read.

## A value, subscriber asleep

2000 samples, each published once the subscriber was asleep on its doorbell again. All 2000 were
received, and every publish found the subscriber asleep and rang it.

| | Median | 90% | 99% | Worst |
| --- | --- | --- | --- | --- |
| Publish and ring (the one `write`) | 0.91 µs | 1.09 µs | 2.07 µs | 11.7 µs |
| Publish to the subscriber running with the sample | 2.72 µs | 4.48 µs | 245 µs (404 µs) | 1.11 ms (1.37 ms) |

CPU per sample: publisher 1.4 µs, subscriber 2.8 µs.

The publisher spins between samples in this test, which keeps the cores out of idle states. The
frame test below is the realistic one.

## A frame topic at 120 Hz, with hold marks

1200 frames, 4 buffers of 1 MiB, one subscriber allowed to hold 2 buffers for up to 2 s, asleep
between frames. Published 1200, dropped 0, received 1200; the subscriber was rung for every one.

| | Median | 90% | 99% | Worst |
| --- | --- | --- | --- | --- |
| Publisher, per frame: stamp the buffer, apply limits, write the entry, ring | 2.67 µs | 3.96 µs | 7.9 µs (12.1 µs) | 14.5 µs (226 µs) |
| Publish to the subscriber holding the frame and reading its first bytes | 10.5 µs (9.6 µs) | 13.7 µs | 147 µs (380 µs) | 1.12 ms (1.83 ms) |

CPU per frame: publisher 4.1 µs, subscriber 9.6 µs. At 120 Hz that is 0.05% of a core for the
publisher and 0.12% for the subscriber. Orion is in neither: after set-up no Orion process runs
per frame.

The earlier measurement this replaces: a ring slot and wake without hold marks, 18.1 µs; passing
descriptors on every frame, 34.5 µs; a full-frame copy, 170 µs.

## What the tail is

The 99th percentile and the worst case are scheduling, not the ring: the cores were not isolated
and the board's services were running. The publisher's own cost stays under 15 µs in the first
run; one 226 µs sample in the second is the publisher being descheduled. No sample waited for the
subscriber's 200 ms fallback timeout, which is what a lost wake-up would look like.

## The same code on this hardware

The ring's tests are checked under a model of weak memory on a PC, but a PC's processor orders
memory more strongly than this one. So the test binaries were also built for the board and run
there, ten times each, all passing:

- the ring with three readers racing the writer (no torn sample);
- the no-system-call proofs for the ring and the doorbell;
- the doorbell stress test (no lost wake-up in 200,000 samples);
- hold marks: stuck, slow, dishonest readers and frames held across threads (never torn);
- a reader process killed while holding a frame;
- a pool passed to a second process, and the lookup by frame time.

One test was wrong and the board showed it: in an optimised build the second process kept
reading a slice of a frame nothing was holding, and the compiler may assume a slice does not
change. The test now fetches the bytes again for each look. Frames that are held do not change,
so this does not touch real readers; the doc on `Held` says so.

## Since this run

Hold marks gained a version word (two more stores per mark and per release, and a recount when the
publisher's count races a change; see `docs/ring.md`). The frame numbers above are from before
that.

## Again, on the shared ring crates (J2)

The rings moved out of Orion into the `shm-*` family at a pinned revision (b48efaf of the
device library). Same board, image dev.993, kernel 7.2.9-v8-16k, `performance` governor, board
lock held, same command, binaries in `/tmp` and removed after. The bench was built twice: from
`next` before the move (c669017, Orion's own copies, version word included) and with the move,
and the two run in turn, three times each:

| Build | Publish to subscriber holding the frame, median (90%) | Publisher per frame, median | A whole frame, one thread |
| --- | --- | --- | --- |
| Orion's copies | 11.15 µs (14.59), 11.17 µs (14.50), 14.15 µs (19.06) | 2.96, 3.02, 3.56 µs | 469.5, 470.4, 471.8 ns |
| `shm-*` | 11.11 µs (14.07), 10.46 µs (14.02), 12.87 µs (17.33) | 2.89, 2.80, 3.67 µs | 470.9, 471.3, 474.4 ns |

Two runs of the `shm-*` build before these gave 10.80 µs and 12.35 µs. In every run: 1200
frames published, none dropped, all received; no system call from the publisher in 100,000
publishes and none on either side in 100,000 frames; no allocation.

- **The move costs nothing measurable.** The two builds are the same code under other names, and
  within a few nanoseconds on the one-thread paths.
- **The 10.5 µs target is met in one run of five.** The other medians are 10.8 to 12.9 µs, and
  Orion's own copies measure the same today (11.2 to 14.2 µs). What moved from 10.5 µs is the
  version word on hold marks and the board from one run to the next, not the move. A median from
  this board, with no core isolated and its services running, swings by 3 µs between runs of the
  same binary.

## Not measured

- Buffers from a real camera (dma-bufs). The pool here is a memfd. The path that maps a dma-buf
  is untested on board.
- More than one subscriber, and a subscriber in another process, for the timings. Both are
  tested for correctness.
- Isolated cores.
