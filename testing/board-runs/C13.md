# C13: USB link on the test board

**Not run.** This file says why, and what a run needs, so it is not mistaken for a result.

## What the board has

the test board (kernel 7.2.9) is a USB gadget to its controller. The gadget `g1` has four functions:
two serial (`/dev/ttyGS0`, `/dev/ttyGS1`), ECM and RNDIS. Both serial functions are taken: a
login console on `ttyGS0` and the recovery shell on `ttyGS1`. The network the board is reached
over is the gadget's own. `usb_f_fs` (FunctionFS) is available as a module and not in use.

## Why it was not run

A round trip through the USB link needs both of these, and neither is this PR's to do alone:

1. **A function for the link on the gadget.** Either one of the two serial functions is given up
   for the length of the run, or a FunctionFS function is added. Adding a function means
   unbinding and rebinding the gadget, which takes down the network the board is reached over,
   on the only board that is up. If the rebind went wrong the board would be unreachable.
2. **Something on the controller to be the device.** The far end of the board's gadget is the
   controller. The handoff allows work on the test board only.

## What a run needs

- Leave to stop `serial-getty@ttyGS1` for the run and start it after, and to run a small
  program on the controller that says hello over `/dev/ttyACM1`. That exercises the stream
  handle over a real gadget serial function with no change to the gadget.
- Or leave to rebind the gadget with a FunctionFS function added, with someone at the board in
  case it does not come back. That exercises the endpoints handle.

The run would report: hello and heartbeats crossing the link both ways, the round-trip time of
a heartbeat, and the link recovering when the cable is pulled and put back.
