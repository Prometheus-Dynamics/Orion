# C13: USB link on the test board

**Run** on 2026-11-13 on the test board (kernel 7.2.9) and its controller, over the gadget's
second serial function: the stream handle over a real USB gadget. The endpoints handle
(FunctionFS) and the `bulk` transport were not run; see "Not run".

## Setup

The gadget `g1` as it is on the board's current image: ECM, then `acm.usb0` (`ttyGS0`, the login
console) and `acm.usb1` (`ttyGS1`, the recovery shell). On the controller these are interfaces 2
and 4 of the board's USB device: `/dev/ttyACM0` and `/dev/ttyACM1`.

- `serial-getty@ttyGS1` stopped for the run, and started again after (a trap in the run script;
  it was `active` after each run). Nothing else on either side changed, and the gadget was not
  touched.
- On the board, a comm core from this tree with `links.usb = usb0`, on a socket of its own in
  `/tmp`, beside the board's own Orion, which was left alone. A small program on the board
  opened `/dev/ttyGS1` raw and handed it to the comm core in a `LinkOffer` (the job the program
  that owns the hardware does).
- On the controller, the device end: `orion-device-core`'s `StreamDevice` over `/dev/ttyACM1`,
  raw, saying hello and keeping the heartbeat, plus its own pings every 50 ms stamped in
  microseconds, timed when the pong echoing them came back.

Both programs are throwaway harnesses, not in the tree. Everything was removed from both
`/tmp`s after.

## Results

| | |
| --- | --- |
| Hello | answered at once: `Connected` in the device's first loop after the offer |
| Heartbeats | both ways for the whole run, no session lost while the link was up |
| Round trip, device → comm core → device, 490 pings at 50 ms | min 128 µs, p50 216 µs, p99 1,345 µs, max 2,256 µs |
| The controller's port closed for 3 s | the session survived it: the ping in the gap came back 2,991 ms later, when the port was opened again |
| A new handle offered on the board for the same link, as after a replug | the old stream ended (`link stream failed … error=lost`), the link opened on the new one, and the device was `Connected` again in a new session within one heartbeat timeout (3 s after the offer) |

## What it found

The `orion` binary did not have USB links: `orion-bin` enabled `link-serial` and `link-can`
only, and `links.usb` was logged as a key nobody reads. Fixed in the same commit: `orion-bin`
now enables `link-usb`.

## Not run

- **The cable pulled by hand.** Nobody was at the board, and the board's network is the same
  cable. A replug was stood in for by both of its halves: the controller's port closing and
  opening again, and a new handle offered on the board.
- **The endpoints handle** over a FunctionFS function. The gadget on the board's next image is
  being built new with FunctionFS for the link (with NCM and one ACM console), and the program
  that owns the gadget hands the endpoints over. That is the run that proves it.
- **The `bulk` transport** has still never met a device.
