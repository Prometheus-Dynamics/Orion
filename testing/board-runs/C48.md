7.2.9 with 16 KiB pages; boot id `30bf1097`), with both board locks held, under the no-hands
rules: the watchdog stayed armed, no slot was touched, no service was stopped and no module

removed afterwards, and the board's own Orion service was not touched.

## The setup

`testing/board-runs/C48-run.sh`, run on the board: I6's setup, then I7's kills. The script
in the tree also keeps its logs, in `/run/orion-m2-logs`. The one that ran did not (see below).

- The comm core, with SSH, peers and the WebSocket listening on the loopback, and node logic,
  each its own process of the one binary.
- Around them, each its own process of `orion-drill`:
  - the sample executor;
  - a provider of three actions;
  - a publisher counting at 1 kHz, with two subscribers;
  - a camera of 4 KiB frames at 100 a second, with two viewers.
- Five workloads under the executor, eight more topics each held by a publisher, and one
  action run through the provider.
- Ten seconds steady, with the reference bits cleared at the start, then
  `scripts/memory-report.sh`.
- Then node logic killed with `SIGKILL` and started again, then the comm core.

## What it found

- **One session was dropped for not reading.** The comm core logged that a command-line
  session (`orion-ctl`, as root) "did not take a frame within 5000 ms" and dropped it. That
  is the write deadline working as designed for a client that stops reading. Which of the
  run's command-line calls it was could not be said: the run's logs were removed with its
  directory. The same script on the bench, with the same build for this machine, logged no
  such drop. The next board run keeps its logs.
- Otherwise, the warnings were the expected ones: node logic saying the comm core was gone
  and not there yet, while it was killed.
